## N1 媒体消息收发（图片 / 语音 / 文件 / 视频）

**现状**：只处理 `item_list[].text_item`，其余类型统一回「暂时只支持文字消息」。

**要做的**：

1. 入站：解析 `image_item` / `voice_item` / `file_item` / `video_item` 的 `CDNMedia`，
   用 `encrypt_query_param` + `aes_key` 下载并解密（AES-128-ECB）
2. 语音：SILK/AMR → PCM 转码（官方插件用 `silk-transcode`），再交给 ASR
3. 出站：`getuploadurl` 申请预签名地址 → AES-128-ECB 加密 → 上传 CDN →
   `sendmessage` 带 `image_item`/`file_item`
4. 生产约束：CDN 域名 `novac2c.cdn.weixin.qq.com` 出网、单文件大小上限、失败降级为纯文本告知

**验收**：微信发图 → 助手能描述图片内容；助手能回一张图；语音留言能被转写后正常对话；
非支持格式回落到现有纯文本提示。

**风险**：媒体链路完全依赖微信 CDN 实现细节，官方改版影响面比文本大；建议独立开关 +
灰度（先只做入站图片，再扩语音）。

## N2 长轮询超时跟随服务端建议

**现状**：`GetUpdates` 固定 35s 超时，忽略响应里的 `longpolling_timeout_ms`。

**要做的**：`Client.GetUpdates` 返回值带出 `LongPollingTimeoutMS`，`monitor` 保存为下一次
请求的超时（下限 10s、上限 120s 防呆），并在日志里记录调整。

**验收**：单测覆盖「服务端返回 60000 → 下一轮超时切到 60s」；线上日志能看到超时跟随记录。

**价值**：服务端若因负载主动拉长超时，我们固定 35s 会造成空轮询放大 QPS。

## N3 入站消息串行处理改并发

**现状**：`monitor.dispatch` 在长轮询循环里串行执行 `im.Handler.HandleInbound`，
一个 30s+ 的 agent 任务会阻塞下一轮 `getupdates`（官方插件同款行为）。

**要做的**：

1. 按 peer 建单飞队列（同一对端串行，保证回复顺序），不同对端并发
2. 队列长度上限 + 满时丢弃并回「上一条还在处理中」提示
3. 长轮询与处理解耦：先推进游标落库，再交给 worker

**验收**：连续发 3 条消息，第 1 条跑长任务时第 2/3 条仍被及时拉取（不丢），
回复顺序与发送顺序一致；进程退出时 worker 有 drain 上限。

**风险**：并发后上下文/落库顺序可能乱，需要 per-peer 串行 + Turn 顺序保证，建议独立 PR。
