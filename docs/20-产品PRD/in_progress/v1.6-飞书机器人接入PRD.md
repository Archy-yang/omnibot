## 二、需求背景与目标

### 2.1 背景

OmniBot 当前有两个对话入口：微信公众号、Web 端。架构演进路线图 v3.0 把「接入第三个入口」
列为 v1.6，目标不是单纯多一个渠道，而是**验证平台架构的可扩展性**——加新入口的成本应该
足够低（路线图目标：< 10% 代码改动），复用全部核心能力（Agent、长期记忆、用户自定义 LLM 配置）。

v1.5 已完成 Agent 基本能力（ReAct 多步推理 + Function Calling + 运行链路记录），并在 Web 端
经真实 smoke 验证通过。v1.6 选定**飞书**作为第三个入口（飞书机器人生态开放、IM 异步消息无
微信 5s 超时限制，适合承载 Agent 多步循环）。

### 2.2 行业参考：飞书机器人接收消息的两种模式

| 模式 | 机制 | 是否需公网回调 | 适用场景 |
|------|------|----------------|----------|
| **事件订阅（HTTP 回调）** | 飞书把消息事件 POST 到配置的回调 URL，需公网可达 + HTTPS | 是 | 生产部署，与现有微信回调模式一致 |
| **长连接（WebSocket）** | 应用用飞书官方 SDK 主动连飞书，无需公网地址 | 否 | 开发/内网部署，省去公网域名 |

飞书官方提供 Go SDK `github.com/larksuite/oapi-sdk-go`，两种模式均支持。

### 2.3 决策

本次采用 **长连接（WebSocket）模式**：
- OmniBot 当前为单机 dev / 内网部署形态，省去公网回调地址
- 本地即可联调，无需内网穿透
- 飞书 SDK 封装了重连、心跳，接入成本低

### 2.4 目标

> 让飞书用户能在飞书 IM 中与 OmniBot 机器人对话，复用 v1.5 Agent 能力、长期记忆、用户自定义 LLM 配置，验证「加新入口只改 < 10% 代码」的架构目标。

## 三、产品范围

### 3.1 本次 v1.6 做什么

1. **飞书自建应用机器人接入**：通过长连接接收飞书 IM 文本消息
2. **复用 Agent 能力**：飞书端对话走 v1.5 的 ReAct Agent 同步路径（工具调用 / 多步推理），
   而非降级为普通聊天
3. **用户身份落库**：飞书用户通过 `GetOrCreateByChannel("feishu", open_id)` 落 user_channels，
   与 Web 共享同一套用户体系
4. **跨入口能力打通**：飞书用户的长期记忆、对话上下文、LLM 配置与 Web 端对齐（同 user_id）
5. **飞书 Channel 实现**：实现 `MessageChannel` 接口，注册到 channel factory
6. **配置项**：飞书应用凭证（App ID / App Secret）走 config.yaml

### 3.2 本次 v1.6 不做什么

1. ❌ 不做事件订阅 HTTP 回调模式（仅长连接；如未来生产需要公网回调再补）
2. ❌ 不做飞书富消息卡片（interactive card）——v1.6 只回纯文本
3. ❌ 不做图片/文件/语音等非文本消息（仅文本；非文本消息给统一提示）
4. ❌ 不做飞书端 SSE 流式（IM 不支持 SSE，Agent 多步结果一次性回复）
5. ❌ 不做 Agent 思考过程在飞书端的可视化展示（飞书无 segment 渲染能力，仅回最终文本）
6. ❌ 不做飞书 @ 机器人之外的群聊复杂路由（v1.6 聚焦单聊；群聊留后续）
7. ❌ 不做 v1.8 的 UserChannels 统一重构（飞书复用现有 user_channels 表即可，重构留 v1.8）

### 3.3 与现有系统的关系

```
现有架构                              v1.6 新增
┌─────────────────────┐      ┌──────────────────────────┐
│  WeChat Handler     │      │  Feishu Channel          │
│  (HTTP 回调)        │      │  (长连接 goroutine)      │
│                     │      │  收消息 → 同步 Agent      │
│  Web Handler        │      │  → 发飞书消息 API 回复   │
│  (SSE 流式 Agent)   │      │                          │
└────────┬────────────┘      └──────────┬───────────────┘
         │                              │
         ▼                              ▼
   ┌─────────────────────────────────────────┐
   │  AgentService (v1.5, 复用)              │
   │  ReActAgent + ToolRegistry              │
   ├─────────────────────────────────────────┤
   │  MessageService / MemoryService         │
   │  LLMConfigService (用户自定义配置)       │
   ├─────────────────────────────────────────┤
   │  UserService.GetOrCreateByChannel        │
   │  ("web" | "wechat" | "feishu", id)       │
   └─────────────────────────────────────────┘
```

- 飞书 Channel 在 AgentService / MessageService / MemoryService / LLMConfigService 之上构建，
  与 Web Handler 同层
- **不改** v1.5 的 Agent / 工具 / 消息服务 / 记忆服务任何接口，纯新增
- 用户身份统一走 `GetOrCreateByChannel`，channel_type 加一个 `"feishu"` 值

## 五、核心架构设计

### 5.1 飞书 Channel 在架构中的位置

```
飞书 IM
  │ (长连接 WebSocket，飞书 SDK 主动连)
  ▼
┌─────────────────────────────────────┐
│  internal/channel/feishu/           │
│  Channel                            │
│  ├─ ReceiveLoop() goroutine         │  ← 收消息事件
│  │   ├─ 校验来源                     │
│  │   ├─ GetOrCreateByChannel         │
│  │   ├─ SaveUserMessage              │
│  │   ├─ BuildContextMessages         │
│  │   ├─ AgentService.Run (同步)      │  ← 复用 v1.5 Agent
│  │   ├─ SaveAssistantMessage         │
│  │   └─ SendText (飞书发消息 API)    │
│  └─ SendText() / SendReply()         │  ← 实现 MessageChannel 接口
└─────────────────────────────────────┘
```

### 5.2 长连接接收与回复流程

```
1. 应用启动时（routes.go SetupRouter 之后）启动一个 goroutine 跑 ReceiveLoop
2. ReceiveLoop 用飞书 SDK 建立 WebSocket 长连接，注册 im.message.receive_v1 事件回调
3. 收到消息事件：
   a. 提取 sender open_id + 消息文本
   b. GetOrCreateByChannel("feishu", open_id) → user_id
   c. SaveUserMessage（带飞书 message_id 做去重）
   d. BuildContextMessages（历史 + 长期记忆）
   e. 选 LLM 客户端：用户自定义配置优先，否则系统默认
   f. AgentService.Run() 同步执行 ReAct（复用 v1.5 同步路径，含工具调用）
   g. SaveAssistantMessage
   h. SendText → 调飞书发消息 API 把最终文本回复给用户
4. 长连接由飞书 SDK 维护心跳与重连，应用层不实现
```

### 5.3 复用 v1.5 Agent 的关键点

- 飞书端走 **Agent 同步路径**（`AgentService.Run` / `ReActAgent.Run`），不走 SSE 流式
  （飞书 IM 无 SSE，且 IM 是异步消息，无需实时 token）
- Agent 多步循环可能耗时较长（10 步 × 几秒），飞书 IM 无 5s 超时限制，可承受
- v1.5 的工具注册表（get_current_time / calculator / search_memories / search_history /
  rss_reader）飞书端直接复用，不重新注册
- Agent 运行步骤（agent_steps）按 v1.5.5 同样落库，message_id 锚到飞书这轮的 assistant 消息

### 5.4 MessageChannel 接口实现

飞书 Channel 实现现有 `domain/channel.MessageChannel` 接口：

```go
type Channel struct {
    appID     string
    appSecret string
    // 飞书 SDK client（发消息用）
}

func (c *Channel) ChannelType() string { return "feishu" }
func (c *Channel) IsAsync() bool       { return true }  // IM 异步
func (c *Channel) SendText(channelUserID, content string) error  // 调飞书发消息 API
func (c *Channel) SendReply(channelMessageID, channelUserID, content string) error
```

接收侧（ReceiveLoop）不属于 `MessageChannel` 接口（接口只定义发送），由 channel 包自己
启动 goroutine 驱动。

### 5.5 配置设计

config.yaml 新增 `feishu` 段：

```yaml
feishu:
  app_id: ""        # 飞书自建应用 App ID
  app_secret: ""    # 飞书自建应用 App Secret
  enabled: false    # 未配置时不启动长连接 goroutine（避免空凭证报错）
```

- `enabled: false` 时跳过飞书 channel 初始化，不影响 Web/微信正常启动（开发态友好）
- 凭证不入库、不日志输出（安全红线）

### 5.6 安全边界

| 项 | 处理 |
|----|------|
| 凭证保护 | App ID/Secret 仅 config.yaml 内存，不入库、不日志 |
| 用户输入校验 | 飞书消息文本复用 Agent 层的 JSON Schema 工具参数校验 |
| 工具失败脱敏 | 复用 v1.5.3 sanitizeToolResult，飞书回复不含原始错误细节 |
| 去重 | 飞书 message_id 作为 msgID 传 SaveUserMessage 做去重 |
| 长连接异常 | SDK 内置重连；goroutine panic 由 recover 中间件兜底，不影响主服务 |

## 六、验收标准

### 后端

| 验收项 | 标准 |
|--------|------|
| 飞书 Channel | 实现 MessageChannel 接口，注册到 channel factory |
| 长连接接收 | enabled=true 时启动 goroutine，收到消息事件能驱动 Agent |
| Agent 复用 | 飞书端对话走 v1.5 同步 Agent，工具调用真实生效 |
| 用户落库 | GetOrCreateByChannel("feishu", open_id) 正确创建/复用 user_channels |
| 去重 | 同一飞书 message_id 重复推送不产生重复回复 |
| 配置开关 | enabled=false 时跳过初始化，服务正常启动 |
| 测试覆盖 | `go test ./internal/channel/feishu ./... -count=1` 通过 |

### 跨入口打通

| 验收项 | 标准 |
|--------|------|
| 记忆打通 | 飞书端 #记住 的记忆，Web 端可见（同 user_id） |
| LLM 配置共享 | Web 端配置的自定义 LLM，飞书端对话使用同一配置 |
| 上下文共享 | 飞书端对话历史纳入滑动窗口，Web 端可见同一段历史 |

### 集成验证（真实飞书应用）

1. 在飞书开放平台创建自建应用，开启机器人能力，配置长连接
2. config.yaml 填 App ID/Secret，enabled=true
3. 启动后端，飞书 IM 内 @ 机器人发「现在几点了」→ Agent 调 get_current_time → 回复真实时间
4. 发「帮我算 (123+456)*7」→ Agent 调 calculator → 回复 4053
5. 发「你好」→ 不调工具，正常回复
6. 飞书端发「#记住 我偏好简洁」→ Web 端记忆列表可见该条
7. Web 端配置自定义 LLM → 飞书端对话使用该配置（看日志 model 字段）

## 七、设计决策记录

### 决策 1：为什么用长连接而不是事件订阅回调？

- **背景**：飞书机器人接收消息有两种模式
- **决策**：长连接（WebSocket）
- **原因**：
  - OmniBot 当前单机/内网部署，无公网回调地址
  - 长连接本地即可联调，无需内网穿透
  - 飞书 SDK 封装心跳重连，接入成本低
  - 事件订阅模式留作未来生产部署的可选增强

### 决策 2：为什么飞书端直接上 Agent 而不是先普通聊天？

- **背景**：微信端因 5s 超时暂不支持 Agent（v1.5 PRD 决策4）
- **决策**：飞书端直接启用 v1.5 Agent
- **原因**：
  - 飞书 IM 是异步消息，无 5s 超时限制，能承受 Agent 多步循环耗时
  - 复用 v1.5 已验证的 Agent 能力，无需重新实现
  - 直接验证「跨入口 Agent 能力可用」的架构目标

### 决策 3：为什么飞书端不做流式 / 思考过程可视化？

- **背景**：Web 端 v1.5.3 做了 segments 交错展示 + 点击展开工具结果
- **决策**：飞书端只回最终文本
- **原因**：
  - 飞书 IM 不支持 SSE，无法 token 级流式
  - 飞书消息卡片可做富文本但 v1.6 不引入，保持最小改动
  - 思考过程（agent_steps）仍落库，未来若做飞书卡片展示可复用

### 决策 4：为什么复用 user_channels 而不新建 feishu_accounts 表？

- **背景**：现有有 wechat_accounts 专用表 + user_channels 通用表两套
- **决策**：飞书走 user_channels
- **原因**：
  - `GetOrCreateByChannel(channelType, channelUserID)` 已是通用渠道接口，飞书只是多一个 channel_type 值
  - 复用零表结构改动，符合「加新入口最小改动」目标
  - 为 v1.8 的 UserChannels 统一重构做铺垫（wechat_accounts 届时也会并入）

## 八、风险与应对

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| 飞书 SDK 长连接不稳定 | 收不到消息 | 低 | SDK 内置重连；goroutine recover 兜底 |
| Agent 多步循环耗时过长 | 用户等待久 | 中 | v1.5 已有 maxSteps=10 + 120s 超时；可先回执再异步推结果（留后续） |
| 飞书开放平台审核/权限 | 无法联调 | 中 | 用企业内部应用（无需审核）先验证 |
| 凭证泄露 | 安全风险 | 低 | 仅 config.yaml，不入库不日志；enabled 开关控制 |
| 跨入口 user_id 串 | 记忆/配置错乱 | 低 | 统一走 GetOrCreateByChannel，channel_type 区分 |
