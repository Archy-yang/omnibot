## 一、背景与问题

助手的每一项本领（查时间、算数、读网页、订阅 RSS……）都是出厂固化的。用户想让助手多会一样东西——比如查 GitHub 仓库、连自己的内部系统、用某个在线服务——唯一的途径是提需求、等排期、改代码、发版。

这违背产品愿景：「插件系统，可以自己扩展能力」。用户需要的是**装上就能用**，而不是**提需求等版本**。

## 二、产品目标

1. 助手的能力可以像装插件一样扩展：**接上就用，关掉就停**，不需要改代码发版。
2. 用户对自己助手的"本领清单"有知情权和控制权：**看得见它都会什么，管得住哪些能用**。
3. 无论本领是自带的还是外部接入的，使用体验完全一致——用户不感知差别。

## 三、用户故事

| # | 作为 | 我想要 | 以至于 |
|---|------|--------|--------|
| 1 | 用户 | 在设置里看到助手当前具备的全部技能清单 | 我知道它能干什么、不能干什么 |
| 2 | 用户 | 把某个我不需要/不信任的技能关掉 | 助手不会拿它做我不想让它做的事 |
| 3 | 用户 | 填一个外部能力服务的地址和密钥，助手就自动获得该服务提供的新技能 | 不用等开发者，我自己就能扩展助手的本领 |
| 4 | 用户 | 外部接入的技能默认关闭，由我逐个开启 | 外部东西进门前经过我同意 |
| 5 | 用户 | 密钥被妥善保管（不明文显示、不留痕） | 我敢在助手里配置敏感凭据 |

## 四、功能需求

### 4.1 技能清单与开关

- 设置中提供「技能管理」区，展示助手当前所有技能：名称、一句话说明、来源（内置 / 外部接入）。
- 每个技能可单独 开启 / 停用；停用后助手在该对话中不再使用该技能（用户询问时助手如实回答"此技能已停用"）。
- 关键基础技能（与用户交互、任务汇报相关的生存技能）不可停用，避免助手"自废武功"。

### 4.2 外部能力接入

- 设置中提供「外部能力服务」配置：填写服务地址 + 访问密钥，保存后自动发现该服务提供的技能列表。
- 新发现的技能默认**停用**状态，用户逐个开启后助手才会使用。
- 支持配置多个外部服务；删除某个服务时，其带来的技能一并移除。
- 连接失败时给出可读的失败原因（地址不可达 / 密钥不对 / 服务无响应），不暴露内部细节。

### 4.3 统一使用体验

- 助手使用外部技能与内置技能的表现完全一致：同样的调用展示（"正在调用 xxx"）、同样的结果汇报。
- 外部技能不可用（服务断连、超时）时，助手如实告知用户该技能暂时不可用，不静默失败、不编造结果。

### 4.4 安全与信任

- 访问密钥加密存储，界面只显示掩码，可显式清除重填。
- 助手调用外部技能属于"把用户请求发往外部服务"——技能开启时即视为用户授权；未开启的技能绝不外发任何数据。

## 五、本期边界（明确不做）

| 不做 | 理由 |
|------|------|
| 用户自己编写技能（脚本/代码执行体） | 安全红线，风险远大于当前收益 |
| 技能市场 / 第三方分发 | 无真实场景驱动 |
| 提示词包型技能（教助手"怎么做事"的知识包） | 与工具型技能是两条线，后续按需立项 |
| 外部能力的流式/资源订阅类高级特性 | 先跑通最常用的"调用-返回"模式 |

## 六、已决策的开放问题

| 问题 | 决策 | 理由 |
|------|------|------|
| 技能与外部服务的配置归谁管 | **系统级，Web 端在线配置**（M3 落地：技能抽屉增删改查，密钥加密落库；配置文件仅作首次导入） | 兑现 PRD 4.2"用户自己填地址接入"的完整形态 |
| 外部服务的接入方式 | 第一版 HTTP 流式接口，本地进程方式放二期 | 部署与安全成本最低 |
| 本期技能范围 | 仅"工具型"技能（帮用户做成一件事） | 最小改动，兑现愿景主线 |

## 七、验收标准

1. 用户可在设置中看到完整技能清单并逐个启停，停用立即生效。
2. 配置一个外部能力服务后，其技能出现在清单中（默认停用），开启后助手可正常使用并如实汇报结果。
3. 删除外部服务配置后，对应技能从清单消失且助手不再可用。
4. 密钥不以明文出现在界面、日志、数据库中。
5. 全流程（清单/启停/接入/使用）覆盖 Web 端。
