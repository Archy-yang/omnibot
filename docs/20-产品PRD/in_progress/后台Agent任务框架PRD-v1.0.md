## 二、需求背景与目标

### 2.1 背景

- 现状:Web/飞书/微信三入口都是**同步阻塞**--用户发消息 -> 等 Agent 跑完 -> 回复。
- Agent 多步推理 + 工具调用可能耗时数十秒。微信 5s 超时是死结;Web/飞书虽能等,但用户干等体验差。
- 用户的心智模型是「总管家派活」:跟管家说一件事,管家安排别人去做,自己接着聊,完事管家来汇报。当前做不到--所有事都堵在主对话里同步做。
- 消息表 v1.5.4 已预留「未来 artifact / 异步任务等一等实体改用独立表 + 引用 id」。

### 2.2 目标(用户故事)

- **作为用户**,我希望让助手处理耗时任务时,不用干等,可以继续聊别的。
- **作为用户**,我希望助手安排的子任务完成后,能**自动**把结果告诉我(不用我主动问)。
- **作为用户**,我希望耗时任务的结果是完整的(不是被超时截断的半截)。
- **作为用户**,我希望汇报是以「管家转述」的口吻,而不是干巴巴甩一份报告。

### 2.3 非目标(第一版不做)

- ❌ 主动推送(B 模式,需服务端推送通道)--第一版用前端轮询 + report 接口替代
- ❌ 多个子 Agent 并行编排(第一版一次派一个)
- ❌ 子 Agent 运行时动态配置(第一版固定注册)
- ❌ 用户自定义子 Agent(第一版系统预设)
- ❌ 微信入口接入(微信走 callLLM 非 Agent,5s 超时;第一版只做 Web + 飞书)
- ❌ 「任务面板」UI(用户主动查看全部任务)--第一版靠轮询自动汇报,面板留后续

## 三、产品范围

### 3.1 本期做什么

- **完整异步任务**:主 Agent 派活即返回,子 Agent 后台跑,不阻塞主对话
- **轮询触发汇报(方案B)**:前端轮询发现完成的任务 -> 触发主 Agent 流式汇报 -> 在对话框自动展示
- **兜底前置汇报**:用户发消息时若还有未汇报任务,先汇报再回应(防轮询间隙漏报)
- **框架 + 1 示例子 Agent**:研究员(researcher),验证框架
- **Web + 飞书两入口**接入

### 3.2 本期不做什么

见 2.3。各条理由:
- 主动推送:依赖推送通道(SSE 长连/飞书客服消息配额),第一版用轮询规避
- 并行编排:第一版验证单子 Agent 跑通即可,编排需真实场景驱动
- 微信:callLLM 路径无 Agent,接入需先把微信切到 Agent(独立工作),第一版不做

### 3.3 现有行为变更

- 主 Agent 获得 `delegate` 工具,会主动判断是否派活(用户感知:某些耗时请求会收到「已安排X处理」而非干等)
- 主 Agent system prompt 增补:有子任务回执时先汇报
- 前端新增轮询逻辑(页面打开时定时查未汇报任务)

## 四、用户场景

### 4.1 典型场景:长耗时研究

1. 用户(Web 或飞书):「研究一下 2026 年 Go 1.24 的新特性」
2. 主 Agent 判断该派活 -> 调 delegate(researcher) -> 立即回:「好的,我让研究员去查一下 Go 1.24 新特性,稍后告诉你」
3. 用户继续聊别的(主对话不阻塞)
4. researcher 后台多步检索(RSS/历史) -> 产出结构化报告
5. 前端轮询发现该任务完成 -> 自动调 report 接口 -> 主 Agent 流式汇报:「你让我研究的 Go 1.24 新特性有结果了:① ... ② ...(管家口吻转述)」
6. 汇报作为正常助手消息出现在对话框;用户无需主动问

### 4.2 边界场景

- **用户关闭页面**:前端不轮询,任务结果压在任务表。用户下次打开页面/发消息时汇报(兜底)。
- **子 Agent 失败**(超时/达最大步数/LLM 错误):任务 failed,轮询发现后主 Agent 汇报失败原因(「你让我研究X,但研究员没能完成:超时」)。
- **用户连续派多个任务**:各自独立 task_id,轮询逐个触发汇报,每条独立出现在对话框。
- **简单问题不派活**:主 Agent 直接回(零开销,用户无感)。
- **用户发消息时恰好有未汇报任务**:前置汇报先汇报,再回应当前消息(兜底,与轮询去重)。

## 五、功能描述

### 5.1 派活(主 Agent 委托)

- 主 Agent 据 `delegate` 工具描述(列出已注册子 Agent 能力)判断是否派活
- 派活即返回 task_id,主 Agent 用自然语言告知用户「已安排X处理,稍后汇报」
- 派活后主对话立即继续,不等子 Agent

### 5.2 子 Agent 后台执行

- **独立上下文**:子 Agent 只拿主 Agent 生成的 goal(委托目标),不继承主对话历史
- **独立工具集**:researcher 用 rss_reader / search_memories / search_history
- **用系统默认 LLM**:不占用户自定义配置(用户配置给主对话用;子 Agent 后台跑用默认更稳)
- 子 Agent 运行链路按 task_id 落库,不混入主对话 messages

### 5.3 轮询触发汇报(方案B,主路径)

- 前端定时(约 8s)轮询 `GET /api/v1/agent/tasks?status=completed_unreported`
- 发现有完成的任务 -> 调 `POST /api/v1/agent/tasks/:id/report`
- 后端:取 task.Artifact -> 构造回执上下文 -> 主 Agent RunStream 流式汇报 -> SSE 推前端
- 前端把汇报作为**正常流式助手消息**渲染在对话框(复用现有 ChatMessage 流式逻辑)
- 汇报完标记 reported,不重复

### 5.4 兜底前置汇报

- 用户发消息时,主 Agent Run 前查未汇报任务
- 有 -> 回执注入上下文,主 Agent 先汇报再回应当前消息
- 无 -> 正常流程
- 与轮询通过 `Reported` 字段去重,不会重复汇报

### 5.5 失败处理

- 超时/达最大步数/LLM 错误 -> 任务 failed,ErrorMsg 落库
- 轮询发现 failed_unreported -> 同样触发主 Agent 汇报失败原因
- 用户感知:「你让我研究X,但研究员没能完成:超时」(不泄露内部堆栈)

### 5.6 三入口一致性(Web + 飞书)

- Web(流式 SSE)和飞书(同步聚合)均接入派活 + 前置汇报兜底
- 轮询仅在 Web 前端(飞书无前端轮询能力,靠用户下次发消息的兜底汇报)

> 飞书的汇报路径:飞书用户派活后,子 Agent 完成 -> 飞书用户下次发消息时,前置汇报触发。
> 飞书无轮询(无 Web 前端),但兜底前置汇报保证不会漏报。

## 六、交互流程

### 6.1 派活主流程

```
用户发消息 -> 主 Agent 判断派活 -> delegate(researcher, goal) -> 立即返 task_id
-> 主 Agent 流式回「已安排研究员处理,稍后汇报」-> 用户继续聊
   (并行)子 Agent 后台跑 -> 写 Artifact -> 任务 completed
```

### 6.2 轮询汇报流程(Web)

```
前端轮询 GET /agent/tasks?status=completed_unreported
-> 发现 task 123 completed_unreported
-> POST /agent/tasks/123/report (SSE)
-> 后端:取 Artifact -> 主 Agent RunStream 流式汇报
-> 前端:汇报作为流式助手消息出现在对话框
-> 汇报完 MarkReported(123)
```

### 6.3 兜底汇报流程(飞书 / Web 轮询间隙)

```
用户发消息 -> 主 Agent Run 前置查 completed_unreported
-> 有 task 123 -> 回执注入上下文
-> 主 Agent 先汇报 task 123,再回应当前消息
-> MarkReported(123)
```

### 6.4 失败汇报流程

```
子 Agent 超时 -> 任务 failed,ErrorMsg 落库
-> 前端轮询发现 failed_unreported(或用户发消息兜底)
-> 主 Agent 汇报「研究员没能完成:超时」-> MarkReported
```

## 七、验收标准

- [ ] 主 Agent 派活后**立即返回**(不等子 Agent),用户可继续对话
- [ ] 子 Agent 后台完成,任务表状态正确流转(pending -> running -> completed/failed)
- [ ] Web 前端轮询发现完成任务 -> 自动在对话框展示主 Agent 流式汇报(管家口吻)
- [ ] 飞书用户发消息时,若有未汇报任务 -> 先汇报再回应
- [ ] 汇报不重复(reported 标记;轮询与兜底去重)
- [ ] 失败任务也汇报(汇报失败原因,不泄露内部细节)
- [ ] 简单问题不误派活(主 Agent 直接回)
- [ ] 子 Agent 上下文隔离(不继承主对话历史,只拿 goal)
- [ ] 子 Agent 用系统默认 LLM(不占用户配置)
- [ ] 任务按用户隔离(不串号)
- [ ] Web + 飞书行为一致(除飞书无轮询)

## 八、非功能需求

### 8.1 安全

- 任务按 user_id 隔离,用户只能查/汇报自己的任务
- Artifact 是子 Agent 最终产出(报告),非原始工具结果;脱敏在子 Agent 侧已做(沿用 sanitizeToolResult)
- 失败汇报不泄露内部细节(IP/堆栈/连接错误),统一友好文案
- report 接口需 JWT 鉴权(AuthRequired 中间件)

### 8.2 可靠性

- LLM 派活可靠性靠 system prompt + 工具描述调优,第一版接受偶尔该派不派/误派
- 进程重启丢失运行中任务(第一版接受,任务表留 pending/running 记录但不自动恢复)
- 轮询频率 8s,平衡及时性与后端压力

### 8.3 持久化

- agent_tasks 表持久化任务状态 + Artifact
- report 接口的汇报**不落 messages 表**(不混入用户对话历史),仅作为流式助手消息呈现
- 前置汇报兜底会落 messages(因为是用户发消息触发的正常对话轮次)

## 九、埋点需求

- 派活次数 / 成功率(按子 Agent 类型维度:researcher)
- 任务耗时分布(StartedAt -> CompletedAt)
- 汇报触达路径分布(轮询触发 vs 兜底前置)
- 派活可靠性(该派未派/误派,靠用户反馈或抽样,第一版粗粒度)

> 第一版埋点可后置(先验证功能,埋点随 v1.1 补)。
