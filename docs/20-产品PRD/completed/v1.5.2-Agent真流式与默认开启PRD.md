## 二、需求背景与目标

### 2.1 背景：v1.5.1 决策的修正

v1.5.1 给前端加了「Agent 模式切换开关」，让用户可以在「普通模式」和「Agent 模式」
之间手动选择。

但在确立了《单一长期对话模型》产品基线后，重新评估这个设计：

**「Agent 模式开关」是和单一长期对话模型冲突的**。该模型的产品类比是「微信好友」
——用户和 OmniBot 之间是一个永久对话关系，不是一个「带模式开关的工具」。一个真
正的助手应该自己判断什么时候要调用工具，而不是把判断负担推给用户。

类似的，ChatGPT 后来也合并了 GPT-4 / GPT-4o / Tools 等等模式选择，方向是一致的：
**让 AI 自己决定**，用户只管说话。

### 2.2 当前问题

#### 问题 1：模式开关本身是反产品的

- 用户每次发消息都要先想「这个问题需要工具吗」，决策负担不该由用户承担
- 简单问题误开 Agent 模式 → 体验慢；复杂问题忘开 Agent 模式 → 答得不全
- 和「单一长期对话」的连续关系感冲突

#### 问题 2：Agent 接口不是真流式

`internal/api/web/handler.go` 的 `HandleSendMessageAgentStream`：

```go
// 当前实现：先跑完整个 ReAct 循环拿到完整结果，再一次性吐
result, err := h.agentService.Run(...)
// ...
data, _ := json.Marshal(map[string]string{"content": result.FinalResponse})
fmt.Fprintf(c.Writer, "data: %s\n\n", data)
```

这导致 Agent 模式的体验是「转圈 N 秒后整段文字突然出现」，而普通流式是字符一个个
吐出来。**如果不修真流式直接默认 Agent，所有简单提问都会失去打字机效果**，用户
会感知为「比之前慢」。

#### 问题 3：思考过程 UI 是「思考模式」时代的产物

当前 `ChatMessage.vue` 用一个折叠面板展示「查看思考过程（N 步）」，默认收起。
这个设计假设「用户主动开了思考模式，所以折叠展示思考步骤作为反馈」。

默认 Agent 后，简单对话也会带这个折叠面板（虽然内部为空），UI 会变得啰嗦。

### 2.3 目标

1. 🚀 **后端 Agent 真流式**：让 `/messages/agent/stream` 像普通流式一样字符级吐字
2. 🎯 **默认全 Agent**：所有入口（Web + 微信）默认走 Agent 路径，无需用户切换
3. 🧹 **前端清理 UI**：删除模式切换开关；工具调用时才显示状态条，不调用工具就和
   普通聊天视觉一致

## 三、产品范围

### 3.1 本次 v1.5.2 做什么

#### 3.1.1 后端：Agent 真流式

**核心改动**：让 `AgentService.Run` 从「同步返回完整结果」演进为「边推理边流式吐
token」。具体方式：

- 新增 `AgentService.RunStream(ctx, userID, conversation, llmClient) (<-chan AgentEvent, error)` 流式接口
- `AgentEvent` 是一个 union 类型，包含三种事件：
  - `TokenChunk`：LLM 直接回答时的 token（最常见，等同普通流式）
  - `ToolCallStart`：决定调用工具时，包含 `tool_name` + 简短的展示文本
  - `ToolCallResult`：工具执行结果（可选，用于完整透明度，UI 默认不展示）
- LLM 不调用工具时，输出完全等同 `/messages/stream`（流式 token）
- LLM 调用工具时，先 emit `ToolCallStart` 事件，工具执行完后继续推理，下一段文本
  继续走 `TokenChunk`

`HandleSendMessageAgentStream` 改为消费这个 channel，按 SSE 协议推给前端。

**保留同步接口**：`AgentService.Run`（同步）保留，给非流式场景（API 集成、未来
异步任务等）使用。

#### 3.1.2 后端：保留 `/messages/stream` 作为兼容兜底

- 保留普通流式接口的服务端实现，**但前端不再调用**
- 等到 v2.0 全量验证 Agent 真流式稳定后，再考虑彻底删除
- 这是「渐进式增强」原则的体现，避免破坏性变更

#### 3.1.3 前端：删除模式切换开关

`ChatInput.vue`：
- 删除 `isThinking` 状态
- 删除 `+` 按钮里的模式选择菜单（`mode-menu` / `mode-item`）
- 删除「思考」标签（`thinking-tag`）
- 删除 `localStorage.getItem('chat-thinking-mode')` 持久化逻辑

`chatStore.sendMessage`：
- 永远走 `/messages/agent/stream`，不再分支
- 删除 `useAgent` 参数

#### 3.1.4 前端：思考过程 UI 重新设计

`ChatMessage.vue`：
- **删除**当前的 `<details>` 折叠面板（`agent-steps`）
- **新增**行内工具调用状态条，显示在助手回复正文**上方**（不是折叠在内）
- 状态条样式（参考 ChatGPT 4o / Claude 的「Searching the web」UI）：

```
○ OmniBot
  🔍 搜索了 "RSS 工具最新进展"          ← 浅灰小字一行，工具名转中文友好文案
  ⏰ 查询了当前时间
  ────
  我是 OmniBot，根据搜索结果...          ← 正文，markdown 渲染
```

- 没调用工具的简单对话 → 不显示任何状态条，视觉上和普通聊天完全一致
- 状态条显示规则：
  - 工具调用时直接出现，不可折叠
  - 一条助手回复内多次工具调用，按时序逐条罗列
  - 工具结果默认不展示（用户大多不需要看 JSON）；如果以后需要可再加「展开看详情」

#### 3.1.5 工具名称友好化

后端在 `Tool` 接口增加 `DisplayLabel()` 方法（可选，默认用 `Name()`），返回中文
友好文案：

| Tool Name | Display Label |
|---|---|
| `get_current_time` | 查询了当前时间 |
| `calculator` | 计算了一下 |
| `search_memories` | 翻了翻记忆 |
| `search_history` | 搜索了历史对话 |
| `rss_reader` | 读取了 RSS 订阅 |

前端按这个文案渲染状态条，不再直接显示英文工具名。

### 3.2 微信端处理

**也默认 Agent**——和单一长期对话模型的「跨入口体验一致」原则对齐。

具体改动：
- `internal/api/wechat/handler.go` 把当前调用 `MessageService` + `LLMClient` 的
  路径切换到 `AgentService.Run`（同步版，因为微信不需要流式）
- 工具调用过程不在微信消息中暴露（微信端没有合适的 UI 表达），直接返回最终回答
- 这样 Web 和微信的「智能水平」保持一致，用户在哪个入口都能用工具

### 3.3 本次 v1.5.2 不做什么

1. ❌ **不修改 Agent 推理算法**：ReAct 循环逻辑、tool calling 协议保持不变
2. ❌ **不新增工具**：仅做现有工具的展示文案优化
3. ❌ **不删除 `/messages/stream` 后端实现**：保留作兼容兜底
4. ❌ **不做工具结果详情展开 UI**：本次只展示「调用了什么」，不展示「结果是什么」
5. ❌ **不做工具调用失败的特殊 UI**：失败按现有错误处理流程，状态条直接显示「未能完成 xxx」即可
6. ❌ **不动 LLM 配置逻辑**：v1.5.1 已经把 Agent 接入了用户自定义 LLM 配置，本次复用

## 四、关键设计决策

### 4.1 流式协议设计

后端 SSE 事件类型：

```
event: token         # 普通 token 流，data: {"content": "..."}
event: tool_call     # 工具调用开始，data: {"tool": "rss_reader", "label": "读取了 RSS 订阅"}
event: error         # 错误事件，data: {"error": "..."}
data: [DONE]         # 完成标记（无 event:，沿用现有协议）
```

为什么用 `event:` 字段区分而不是统一 `data:` 内嵌 type？
- SSE 原生支持 named events，前端 `addEventListener('tool_call', ...)` 比手动
  解析 type 字段更清晰
- 和现有普通流式 `data: {"content": "..."}` 兼容（默认 event 就是 `message`）

### 4.2 工具调用与 token 流的交错

ReAct 循环单次迭代：
1. 调 LLM，**流式接收**响应
2. 边收 token 边判断：
   - 如果是普通文本 token → 立即 emit `TokenChunk` 给前端
   - 如果是 tool_call delta → 缓存累计
3. LLM 流结束后：
   - 如果有 tool_call → emit `ToolCallStart`，执行工具，把结果塞回对话，回到第 1 步
   - 如果没有 tool_call → 本轮 ReAct 结束，emit `DONE`

OpenAI Function Calling 的流式 API 本身就支持这种逐 delta 解析，gofeed/gpt 这类
SDK 也都有现成支持。

### 4.3 微信端的同步路径

微信不走流式（微信 API 限制 5 秒响应），直接调 `AgentService.Run` 同步版：
- 工具调用过程在微信消息中**不暴露**
- 返回的 `result.FinalResponse` 直接作为微信回复文本
- 如果工具链耗时超过微信的 5 秒限制，按现有「先回复『正在处理』+ 异步推送结果」
  的客服消息模式（这是已有能力，不在本 PRD 范围）

## 六、验收标准

### 6.1 功能验收

#### 简单提问场景（无工具调用）
- [ ] 用户发「你好」，前端**字符级流式**接收回复
- [ ] 体验与 v1.5.0 之前的普通流式**完全一致**（不能更慢）
- [ ] UI **不显示**任何工具状态条、思考过程相关元素

#### 工具调用场景
- [ ] 用户问「现在几点」，前端先看到「⏰ 查询了当前时间」状态条
- [ ] 然后字符级流式接收最终回复
- [ ] 状态条样式融入对话流，不打扰阅读

#### 多轮工具调用场景
- [ ] 用户问「读一下 xxx RSS 然后总结」，前端按时序看到 `🔍 读取了 RSS 订阅` 等
      多个状态条
- [ ] 最终回复字符级流式

#### 微信端
- [ ] 简单提问行为不变，回复内容不变
- [ ] 工具相关问题（如「现在几点」）在微信端能得到正确回答
- [ ] 微信回复内容**不包含**工具调用过程文本

### 6.2 兼容性验收

- [ ] `/messages/stream` 后端实现仍可访问（curl 直连可正常返回）
- [ ] 历史已存的对话记录正常加载和渲染
- [ ] 已开启过 v1.5.1 思考模式的用户，localStorage 残留不影响新版功能

### 6.3 性能验收

- [ ] 简单提问 TTFB（首字延迟）≤ 当前普通流式的 1.2 倍
- [ ] 工具调用场景，状态条出现 ≤ 工具开始执行后 200ms

## 七、回滚方案

如果上线后发现严重问题：

1. 后端 `/messages/agent/stream` 出 bug：把前端 `chat.ts` 改回调用
   `/messages/stream`，相当于退化到「无工具」体验，但不破坏对话功能
2. 前端 UI 有问题：可以临时把 `ChatMessage.vue` 还原到当前折叠版本，仍能正确展
   示，只是观感退步
3. 微信端 Agent 路径异常：微信 handler 提供 feature flag（环境变量），开关一打
   就退回到非 Agent 路径
