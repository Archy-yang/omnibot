## 二、需求背景与目标

### 2.1 背景

当前 OmniBot 的 LLM 调用模式是「单轮请求-响应」：用户发消息 → 构建上下文 → 调用 LLM → 返回结果。这种模式有明确的局限性：

1. **无法执行操作**：LLM 只能生成文本，不能查询数据库、调用外部 API、执行计算等。
2. **无法自主拆解任务**：复杂问题（如「帮我查一下最近一周的天气，然后根据天气推荐合适的穿搭」）需要多步推理，当前只能一次性回答。
3. **知识有截止日期**：LLM 训练数据有时效性，无法获取实时信息。

### 2.2 行业参考

以下是 2025-2026 年主流 Agent 方案的架构特点：

| 方案 | 核心模式 | 工具调用 | 流式支持 | 适用场景 |
|------|----------|----------|----------|----------|
| **OpenAI Agents SDK** | Agent → Runner 循环：LLM 响应 → 工具调用 → 结果回传 → 继续 | Function Calling 协议，支持 Handoff | 原生支持 streaming events | 通用 Agent 开发 |
| **Anthropic Tool Use** | Claude 返回 `tool_use` block → 客户端执行 → 结果回传 | 扩展的 Function Calling，支持 parallel tool calls | 支持 tool_use 流式增量 | Claude 生态 |
| **LangChain/LangGraph** | StateGraph + ToolNode，条件边路由 | 统一 Tool 抽象，多种调用策略 | 支持 streaming events | 复杂多 Agent 编排 |
| **Google ADK** | Agent → Tool → A2A 协议 | Function Calling + A2A 跨 Agent 通信 | 原生 streaming | Google 生态 |

**共性总结**：所有主流方案都遵循同一个核心循环模式：

```
用户输入 → LLM 推理（思考+决定调用哪个工具）→ 执行工具 → 结果回传 LLM → 继续推理或输出最终答案
```

这就是经典的 **ReAct（Reasoning + Acting）** 模式。

### 2.3 问题

1. LLM 无法获取实时信息（天气、股价、新闻等）
2. LLM 无法执行操作（发送邮件、创建任务、查询数据库）
3. 复杂问题需要多步推理，当前只能一次性回答
4. 没有工具调用能力，所有能力都局限在 LLM 文本生成

### 2.4 目标

> 让 OmniBot 具备 Agent 核心能力：能够调用外部工具、进行多步推理、在 ReAct 循环中自主完成任务。

## 三、产品范围

### 3.1 本次 v1.5 做什么

1. **工具注册机制**：可插拔的 Tool Registry，支持注册/发现工具
2. **Function Calling**：LLM 能够识别需要调用工具的场景，并通过 OpenAI Function Calling 协议发起调用
3. **ReAct Agent 循环**：实现「思考 → 行动 → 观察 → 思考」的完整循环
4. **多步推理**：Agent 能够自动拆解复杂任务，分多步执行
5. **SSE 流式输出**：Agent 思考过程和工具调用结果通过 SSE 实时推送到前端
6. **内置基础工具**：
   - `search_memories` — 搜索用户的长期记忆
   - `search_history` — 搜索对话历史
   - `get_current_time` — 获取当前时间
   - `calculator` — 简单数学计算
7. **安全边界**：最大步数限制、超时控制、工具调用权限控制

### 3.2 本次 v1.5 不做什么

1. ❌ 不做多 Agent 协作/Handoff（如 Supervisor Agent 调度子 Agent）
2. ❌ 不做用户自定义工具（只能使用系统内置工具）
3. ❌ 不做工具调用的持久化存储（本次只记录最终对话结果）
4. ❌ 不做 Agent 配置的可视化管理界面（使用代码配置）
5. ❌ 不做向量检索/RAG 工具（留给后续版本）
6. ❌ 不做异步 Agent 任务（如「帮我每天 9 点查天气」）
7. ❌ 微信端暂不支持 Agent 能力（仅 Web 端先验证）

## 五、核心架构设计

### 5.1 ReAct Agent 循环

参考 OpenAI Agents SDK Runner 和 ReAct 论文的标准模式：

```
┌─────────────────────────────────────────────────────────┐
│                    ReAct Agent Loop                       │
│                                                          │
│  用户输入                                                 │
│     │                                                    │
│     ▼                                                    │
│  ┌──────────────────────┐                                │
│  │ 构建上下文消息        │ ← MessageService               │
│  │ (历史 + 长期记忆)     │                                │
│  └──────────┬───────────┘                                │
│             │                                            │
│             ▼                                            │
│  ┌──────────────────────┐                                │
│  │ LLM 推理              │ ← OpenAI Chat Completions      │
│  │ (带 Function Calling) │   带 tools 参数                 │
│  └──────────┬───────────┘                                │
│             │                                            │
│      ┌──────┴──────┐                                     │
│      │             │                                     │
│  有 tool_calls  无 tool_calls                            │
│      │             │                                     │
│      ▼             ▼                                     │
│  ┌──────────┐  ┌──────────┐                              │
│  │ 执行工具  │  │ 返回最终  │ → 结束                       │
│  │ 获取结果  │  │ 文本回复  │                              │
│  └────┬─────┘  └──────────┘                              │
│       │                                                  │
│       ▼                                                  │
│  ┌──────────────────┐                                   │
│  │ 工具结果回传 LLM   │                                   │
│  │ 作为 tool message │ → 回到「LLM 推理」步骤              │
│  └──────────────────┘                                   │
│                                                          │
│  终止条件：                                               │
│  • LLM 返回无 tool_calls 的文本                           │
│  • 达到最大步数限制（默认 10）                              │
│  • 超时（默认 120s）                                      │
│  • 用户取消                                               │
└─────────────────────────────────────────────────────────┘
```

### 5.2 核心接口定义

参考 OpenAI Agents SDK 的 Agent/Tool 抽象和 Anthropic Tool Use 的消息格式：

```go
// Tool 工具定义（参考 OpenAI Function Calling 格式）
type Tool struct {
    Name        string                 // 工具名称（LLM 用此名称调用）
    Description string                 // 工具描述（LLM 据此判断何时调用）
    Parameters  map[string]interface{} // JSON Schema 参数定义
    Execute     func(ctx context.Context, args map[string]interface{}) (string, error)
}

// ToolCall 表示 LLM 发起的工具调用
type ToolCall struct {
    ID       string                 // 调用 ID
    Name     string                 // 工具名称
    Arguments map[string]interface{} // 调用参数
}

// AgentStep 表示 Agent 循环中的一步
type AgentStep struct {
    StepNumber int        // 第几步
    Thought    string     // LLM 的思考/推理文本
    ToolCall   *ToolCall  // 工具调用（如果有）
    ToolResult string     // 工具执行结果（如果有）
    Final      bool       // 是否为最后一步
}

// AgentResult Agent 执行结果
type AgentResult struct {
    FinalResponse string       // 最终回复文本
    Steps         []AgentStep  // 所有执行步骤（用于展示思考过程）
    TotalSteps    int          // 总步数
    Duration      time.Duration // 总耗时
}
```

### 5.3 Tool Registry 设计

参考 LangChain 的 Tool 注册模式：

```go
// ToolRegistry 工具注册中心
type ToolRegistry struct {
    tools map[string]Tool
}

func (r *ToolRegistry) Register(tool Tool) error
func (r *ToolRegistry) Get(name string) (Tool, bool)
func (r *ToolRegistry) ListAll() []Tool
func (r *ToolRegistry) ToOpenAITools() []map[string]interface{} // 转为 OpenAI tools 格式
```

### 5.4 LLM 交互格式

严格遵循 OpenAI Function Calling 协议（与现有 OpenAIProvider 兼容）：

**请求消息序列（多轮工具调用场景）**：

```
Turn 1:
  system: "You are a helpful assistant with access to tools..."
  user: "帮我查一下今天天气"
  → LLM 返回 tool_calls: [{name: "get_current_time", args: {}}]

Turn 2:
  system: "You are a helpful assistant..."
  user: "帮我查一下今天天气"
  assistant (tool_call): {name: "get_current_time", args: {}}
  tool: "2026-06-14 15:30:00 CST"
  → LLM 返回: "现在是 2026年6月14日下午3点半..."
```

### 5.5 安全边界

参考 OpenAI Agents SDK 的 Guardrails 概念和行业最佳实践：

| 安全机制 | 默认值 | 说明 |
|----------|--------|------|
| 最大步数 | 10 | 超过后强制终止，返回已有结果 |
| 超时时间 | 120s | 超时后终止，返回已有结果 |
| 工具白名单 | 仅内置工具 | 不暴露系统级操作（文件读写、网络请求等） |
| 输入校验 | JSON Schema 校验 | 工具参数必须符合定义的 Schema |
| 错误隔离 | 工具异常不中断循环 | 工具执行失败时，错误信息回传 LLM 让其自行处理 |

## 九、设计决策记录

### 决策 1：为什么用 OpenAI Function Calling 协议而不是自定义格式？

- **背景**：工具调用可以用 OpenAI 原生格式，也可以自己定义 JSON 格式
- **决策**：使用 OpenAI Function Calling 协议
- **原因**：
  - v1.4.1 已将所有 provider 统一到 OpenAI 兼容路由
  - OpenAI 格式是事实标准，百度千帆、字节火山、阿里千问都兼容
  - 不需要额外的协议转换层
  - `LLMProvider` 接口不变，Agent 层在更上层构建

### 决策 2：为什么不修改现有 LLMProvider 接口？

- **背景**：Agent 需要发送带 tools 参数的请求，当前 ChatCompletion 接口不支持
- **决策**：不修改 LLMProvider 接口，在 Agent 层直接构造 OpenAI 请求
- **原因**：
  - LLMProvider 是通用抽象，不应该被 Agent 专用逻辑污染
  - Agent 层直接操作 OpenAI 请求格式，更灵活
  - 未来其他 provider（如 Anthropic 原生）可以有自己的 Agent 适配

### 决策 3：为什么 v1.5 不做用户自定义工具？

- **背景**：是否允许用户在 Web UI 中注册自己的 API 工具？
- **决策**：v1.5 只支持系统内置工具
- **原因**：
  - 用户自定义工具涉及安全沙箱、参数校验、错误处理等大量工作
  - 先验证 Agent 核心循环的可行性，再逐步开放
  - 参考 OpenAI GPTs 的演进路径：先内置工具，再开放自定义

### 决策 4：为什么微信端暂不支持 Agent？

- **背景**：是否在微信对话中也启用 Agent 能力？
- **决策**：v1.5 仅 Web 端
- **原因**：
  - 微信 5 秒超时限制对 Agent 多步循环不友好
  - 需要 v1.8 的统一异步任务抽象后才能支持微信端 Agent
  - Web 端 SSE 可以实时展示 Agent 思考过程，验证体验后再推广

### 决策 5：最大步数和超时如何设定？

- **背景**：Agent 可能陷入无限循环
- **决策**：最大 10 步，超时 120s
- **原因**：
  - 参考 OpenAI Agents SDK 默认 max_turns=10
  - 参考 Anthropic Claude 推荐的工具调用上限
  - 120s 足够 10 次 LLM 调用（每次约 5-10s）+ 工具执行时间
  - 后续可通过用户配置调整

## 十、风险与应对

| 风险 | 影响 | 概率 | 应对 |
|------|------|------|------|
| LLM 不理解工具用途，不调用 | Agent 退化为普通对话 | 中 | 优化 system prompt 中的工具描述；内置工具少而精 |
| LLM 调用不存在的工具 | 工具执行失败 | 低 | 错误信息回传 LLM，让其重新选择 |
| 工具调用参数格式错误 | 执行失败 | 中 | JSON Schema 校验 + 错误回传 |
| 循环不终止 | 用户体验差 | 低 | 硬性步数/超时限制 |
| 工具执行耗时过长 | 超时 | 中 | 每个工具调用设置独立超时（10s） |
| SSE 事件量过大 | 前端性能 | 低 | 限制 step 事件的内容大小 |
