## 二、需求背景与目标

### 2.1 现状

当前微信公众号机器人是「无记忆的」：用户每发一条消息，机器人都当做全新对话处理，完全不知道上一轮说了什么。

**具体表现：**
- 用户说「改成 Go 语言版本」，机器人不知道「改成」指的是什么
- 所有对话都是单轮问答，无法进行连贯的深入讨论
- 用户平均对话轮次低

### 2.2 问题

1. **体验割裂**：多轮对话中机器人无法理解指代性词语（「这个」「那个」「刚才的」）
2. **价值受限**：只能做简单问答，无法完成复杂任务（写代码、方案讨论、学习辅导）
3. **留存差**：用户聊 2-3 轮就没兴趣继续了

### 2.3 目标

> 让机器人可以记住最近 10 轮对话内容，以便用户进行连贯的多轮交流，获得与 ChatGPT 一致的对话体验。

## 三、竞品分析

| 产品 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **ChatGPT** | 多会话 + 手动命名 + 历史搜索 + Token 动态截断 | 功能最完整，用户体验好 | 微信环境无法复刻（没有侧边栏） |
| **Claude** | 单会话 + 超大上下文窗口 + 新开对话按钮 | 简单直接，不用管会话管理 | 用户无法管理历史 |
| **文心一言** | 多会话 + 自动生成标题 + 左侧列表 | 兼顾功能和简洁 | 微信环境下操作复杂 |

### 我们的场景特殊性

1. **纯文本交互**：微信只有聊天框，没有侧边栏、按钮、菜单等 UI 控件
2. **输入成本高**：用户用手机打字，打长命令体验差
3. **轻量使用场景**：公众号对话多为临时、简短交流，很少有人会聊几十轮
4. **技术栈限制**：后端用 Go，要考虑性能和复杂度

**结论：我们做不了 ChatGPT 式的多会话管理，MVP 应该走「单全局会话 + 10 轮记忆」的极简路线。**

## 六、详细功能设计

### 6.1 全局上下文记忆机制

**记忆范围：**
- 同一个微信用户的所有消息共享一个全局上下文
- 不做多会话，用户没有切换会话的概念

**记忆长度：**
- **永久存储**：所有用户与 AI 的对话消息永久保存到数据库，不删除
- **调用上下文**：每次调用 LLM 时，只取最近 10 轮对话拼接到请求中
- 「一轮」= 用户一条消息 + 机器人一条回复 = 最多 20 条消息用于 LLM 调用

**消息过滤规则：**
- 只有**文本消息**进入上下文
- 图片、语音、视频、位置、链接、事件消息不进入上下文

### 6.2 消息拼接流程

```
用户发送新消息
    ↓
查询该用户最近 N 条历史消息（按时间倒序）
    ↓
按时间正序排列，拼接到 messages 数组
    ↓
在最前面插入 system prompt
    ↓
调用 LLM 生成回复
    ↓
把用户新消息和机器人回复都写入数据库
```

**System Prompt 策略：**
- 每次 LLM 调用都在最前面重新插入系统提示词
- 不依赖历史消息中的 system prompt

### 6.3 微信交互

**V1.2 MVP 不提供任何上下文相关的微信命令**

用户无感知：
- 不需要学习任何新命令
- 不需要手动管理上下文
- 发消息就自动有记忆

## 八、异常与边界处理

| 场景 | 处理方式 |
|------|----------|
| LLM 调用失败，机器人返回「服务暂时不可用」 | 这条失败回复仍然写入数据库，进入上下文 |
| 微信服务器重试发送同一条消息（MsgID 相同） | 按 MsgID 去重，不重复写入数据库 |
| 用户超过 10 轮继续对话 | 数据库中永久保存所有消息，但调用 LLM 时最旧的消息自动移出上下文，滑动窗口向前滚动 |
| 新用户第一条消息 | 无历史消息，只有 system prompt + 当前消息 |
| 上下文查询数据库失败 | 自动降级为单轮对话模式，对用户无感知，只记录错误日志 |
| 非文本消息（图片/语音等） | 正常回复用户，但该消息不写入上下文数据库 |
| 同一条消息包含多条回复（微信客服消息） | 按实际返回的内容写入，不做合并 |

## 九、非功能需求

| 项 | 要求 | 说明 |
|----|------|------|
| **性能** | 上下文查询 + 拼接总耗时 < 100ms | 不明显增加用户等待时间 |
| **可靠性** | 上下文模块降级率 < 0.1% | 不能因为记忆功能影响基础对话能力 |
| **安全** | 日志中不输出完整对话内容 | 只输出消息 ID、长度、角色等元数据 |
| **兼容性** | 完全向后兼容 | 不影响 v1.1 已有的自定义模型配置功能 |
| **可观测性** | 埋点统计：平均携带消息数、降级率、平均对话轮次 | 上线后可以量化评估效果 |

## 十、验收标准

- [ ] 用户连续发 10 轮对话，每一轮机器人都能准确理解上一轮的指代内容
- [ ] 用户第 11 轮对话时，第 1 轮的消息自动移出上下文，不影响后续对话
- [ ] 微信服务器重试同一条消息（MsgID 相同），数据库中不会出现重复记录
- [ ] LLM 调用失败返回系统提示时，该提示仍然出现在下一轮的上下文中
- [ ] 数据库查询失败时，机器人仍然可以正常回复（降级为单轮对话），用户不会看到任何错误
- [ ] 非文本消息（图片、语音、位置等）不会出现在上下文历史中
- [ ] 响应时间相比 v1.1 增加不超过 100ms
- [ ] 用户自定义模型配置功能完全不受影响，可以正常使用

## 十一、对当前项目的影响

### 需要新增/修改的模块

1. **新增消息存储模块**：负责读写用户对话历史
2. **修改微信消息处理流程**：处理消息前先查询历史，回复后写入新消息
3. **新增 LLM 消息拼接逻辑**：把历史消息按格式拼接到请求中

### 不影响的模块

- ✅ 用户自定义模型配置功能（完全不变）
- ✅ 微信服务器验证逻辑
- ✅ 各类消息类型的处理逻辑
- ✅ 管理后台 API
- ✅ 数据库迁移框架

## 十二、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 上下文记忆增加 Token 消耗，导致成本上升 | 中 | MVP 只存 10 轮，后续根据成本数据调整 |
| 历史消息太长导致 LLM 请求超时 | 中 | 增加简单的长度截断，超过阈值时从前往后删 |
| 用户聊了很多轮后想清除上下文，但没有命令 | 低 | V1.2.1 增加 `#新建会话` 命令，MVP 期先观察用户反馈 |
| 上线后对话质量反而下降（旧上下文干扰新话题） | 高 | 密切观察埋点数据，如果质量下降明显，快速减少记忆轮数或增加手动清除命令 |
