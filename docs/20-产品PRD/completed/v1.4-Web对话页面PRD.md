## 二、背景与目标

### 2.1 现状

目前 OmniBot 只有微信公众号一个对话入口，存在以下问题：
1. **平台依赖**：用户必须关注微信公众号才能使用，有门槛
2. **通道受限**：微信订阅号有 5 秒响应限制，无法做流式输出、长任务处理
3. **能力受限**：纯文本交互，无法做富媒体、文件上传、复杂配置等

### 2.2 核心目标

> **让用户可以通过浏览器直接和 OmniBot 对话，不需要关注公众号，同时验证多通道架构的通用性。**

具体目标：
1. 验证多通道架构：接入第二个通道（Web），证明核心服务 100% 复用
2. 打通跨通道记忆：用户在微信和 Web 对话，两边的上下文完全一致
3. 验证异步能力：Web 端可以做 WebSocket 流式输出，摆脱 5 秒限制
4. 为后续 Web 管理后台打基础

## 四、功能详细设计

### 4.1 核心交互流程

```
用户打开 /chat 页面
    ↓
浏览器生成临时会话 ID（UUID）
    ↓
用户发送第一条消息
    ↓
后台根据会话 ID 创建或获取用户（匿名用户）
    ↓
调用 LLM 生成回复
    ↓
消息保存到数据库（和微信用户的消息表同一张）
    ↓
返回回复给前端
    ↓
展示对话气泡
```

### 4.4 接口设计

#### POST /api/v1/chat/messages

发送消息，获取回复。

**请求体**：
```json
{
    "session_id": "uuid-string",
    "content": "你好，请介绍一下你自己"
}
```

**响应**：
```json
{
    "success": true,
    "data": {
        "id": 123,
        "role": "assistant",
        "content": "我是 OmniBot，一个自带记忆的全平台智能助手...",
        "created_at": "2026-05-16T12:00:00Z"
    }
}
```

#### GET /api/v1/chat/messages

获取历史消息列表。

**请求参数**：
- `session_id`: 会话 ID
- `limit`: 数量限制，默认 50
- `before`: 游标，取某个 ID 之前的消息

**响应**：
```json
{
    "success": true,
    "data": {
        "messages": [
            {"id": 1, "role": "user", "content": "...", "created_at": "..."}
        ],
        "has_more": false
    }
}
```

## 五、技术方案要点

### 5.1 架构复用

**100% 复用现有服务，不需要改任何业务逻辑**：
- ✅ 用户服务：增加一个新的 channelType = "web"
- ✅ 消息服务：完全复用，不需要改一行代码
- ✅ LLM 配置服务：完全复用，不需要改一行代码
- ✅ 上下文记忆：完全复用，不需要改一行代码

只需要新增：
1. Web 前端页面（纯静态 HTML + JS，不需要复杂框架）
2. 两个新的 HTTP 接口（发送消息、获取历史）
3. Web Channel 的 MessageChannel 实现

### 5.2 用户识别策略

**方案：匿名会话 + 浏览器本地存储**

- 首次访问页面时，前端生成 UUID 作为 `channel_user_id`
- 存入 `localStorage`，刷新页面不会丢失
- 后台调用 `GetOrCreateByChannel("web", session_id)` 获取或创建用户
- 简单可靠，不需要注册登录，没有隐私问题

### 5.3 通道特性

| 特性 | 微信通道 | Web 通道 |
|------|---------|---------|
| 异步发送 | ❌ 不支持 | ✅ 支持 WebSocket |
| 流式输出 | ❌ 不支持 | ✅ 支持 |
| 富媒体 | ❌ 只有纯文本 | ✅ 支持 Markdown、代码高亮 |
| 5 秒限制 | ✅ 有 | ❌ 没有 |

## 十、风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 前端引入复杂框架导致维护成本上升 | 高 | 强制用纯 HTML + CSS + 原生 JS，不引入任何框架 |
| XSS 安全问题 | 中 | 所有用户输入和 AI 输出都做转义处理 |
| 匿名用户数据太多，数据库膨胀 | 低 | 可以加定时任务清理 30 天不活跃的匿名用户（v1.5+） |
| 会话 ID 被篡改 | 低 | 只是匿名会话，即使被篡改也只是看到别人的消息，没有敏感数据，未来可以加签名验证 |
