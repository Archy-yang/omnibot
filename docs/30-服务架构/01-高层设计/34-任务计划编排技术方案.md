## 1. 背景与目标

### 1.1 现状

后台任务框架是**单任务模型**：主 Agent 调一次 `delegate` 建一个任务，子 Agent 在 180s 预算内跑完，产出一个 artifact。

- `delegate` 无批次概念（`internal/service/agent/builtin_tools.go`）
- `AgentTask.ParentTaskID` 注释写着「预留：动态编排/任务链；当前 delegate 派出的为 nil」
- 08 号方案 §1.3 非目标：「❌ 多个子 Agent 并行编排（第一版一次派一个）」

### 1.2 要解决的场景

用户说「帮我做云南 7 天行程，含攻略/住宿/餐饮/预算」，正确的形态不是"一个 180s 的大任务"，而是：

```
1. 查目的地基础信息（攻略/季节/交通）
2. 排 7 天路线骨架        ← 要用第 1 步结果
3. 每天配住宿候选          ← 要用第 2 步结果
4. 每天配餐饮             ← 要用第 2 步结果
5. 汇总预算
6. 合成最终方案
```

后一步依赖前一步产出，**串行是需求本身，不是实现选择**。用户要的是"进度可见、一件一件来"，而不是并发刷屏。

### 1.3 目标 / 非目标

**目标**

- 主 Agent 可在派活时声明 2~9 个有序步骤，后台自动逐步执行
- 每步完成把产物摘要注入下一步背景（信息不断链）
- 失败即暂停并告知用户，不静默吞掉后续步骤
- 全程可见：任务中心显示 `3/9` 与每步状态，点得进单步执行流水
- 取消可级联；进程重启后可恢复或明确告知停在哪

**非目标（v1 明确不做）**

- DAG 依赖图 / 并行步骤 / 条件分支
- 计划中途增删步骤
- 计划模板、计划复用
- 用户确认后再执行的 gate（自动推进已确认；后续要加是 P3 开关）

## 2. 为什么不用其它做法

| 方案 | 为什么不行 |
|------|-----------|
| A. prompt 里一轮连调 N 次 delegate | 任务并发起跑，第 2 步拿不到第 1 步结果；汇报刷屏 |
| B. 把 N 步写进一个 goal 交给子 Agent | 不可见不可干预；单任务 180s 超时会砍掉第 3 步；一步失败整单失败 |
| C. 复用 `persistent_task` 的 cron | 语义是周期性触发；每步等 30s tick，节奏失控；完成即停用与"一次性链"语义冲突 |
| **D. 计划实体 + 串行推进（采用）** | 唯一能让"每步是真实任务"的方案，超时/取消/产物/流水/汇报渠道全部复用 |

核心判断：**计划只负责调度与展示，执行仍然是 AgentTask**。任何把步骤塞进单个任务的方案，都会丢掉可观测性和可干预性。

## 3. 设计

### 3.1 领域模型

`internal/domain/agent/task_plan.go`：

```go
type TaskPlan struct {
    ID           int64
    UserID       int64
    Name         string     // 计划短名，如"云南7日行"
    Goal         string     // 总体目标
    Status       string     // pending/running/paused/completed/failed/cancelled
    Steps        []PlanStep `gorm:"serializer:json"`
    CurrentSeq   int        // 当前步（1-based；0=未开始）
    Source       string     // web/feishu/wechat_claw，沿用任务来源
    NotifyTarget string
    OriginTurnID *int64
    Version      int64      // 乐观锁：防双推进
    CreatedAt    time.Time
    StartedAt    *time.Time
    FinishedAt   *time.Time
}

type PlanStep struct {
    Seq                int
    Name               string
    Goal               string
    Deliverables       []Deliverable
    CompletionCriteria []string
    TaskID             *int64  // 派出后回填
    Status             string  // pending/running/completed/failed/cancelled
    Digest             string  // 完成后摘要，注入下一步 background
}
```

`AgentTask` 加两列：`PlanID *int64`（index）、`PlanStepSeq int`。空值 = 普通单任务，完全兼容存量。

计划与步骤的原子性：**步骤状态与 CurrentSeq 只由推进器改写**（计划 owner），任务自身的状态由 SubAgentService 管，两边各自 CAS，互不双写。

### 3.2 状态机

```
计划: pending ──(派第一步)──> running ──全部步骤 completed──> completed
                               │  │
                               │  └──(某步 failed)──> paused ──(resume)──> running
                               └──(cancel)──> cancelled
步骤: pending ─> running ─> completed | failed | cancelled
```

- 拒绝未知迁移（表驱动，照抄 `taskTransitions` 的写法与测试风格）
- `paused` 是唯一可恢复的非终态；`completed/failed/cancelled` 无出边

### 3.3 推进器（`internal/service/agent/plan_runner.go`）

挂到任务终态回调上（现有 `SetFinishedObserver` 是单槽位，被 25 号周期任务占用 → 改为多播 `AddFinishedObserver`，保留原语义）。

一次终态触发：

1. `task.PlanID == nil` → 直接返回（零影响）
2. **步骤成功**：
   - 计算 `Digest`（artifact 截断 1200 字）
   - CAS 推进计划：`UPDATE task_plans SET current_seq=?, steps=?, version=version+1 WHERE id=? AND version=? AND status='running'`
   - CAS 成功才 `StartTask` 下一步；`StartTask` 失败 → 计划落 `paused`（步骤回退 pending），记 ERROR
3. **步骤失败**：CAS 计划 → `paused`，推送「第 3 步卡住了：<原因>，重试还是跳过？」等用户
4. **最后一步成功**：CAS → `completed`，生成一条汇总汇报
5. **步骤被取消**：CAS → 计划 `cancelled`

下一步的 `TaskSpec`：

```
Goal: 步骤 goal
Name: 步骤 name
Deliverables/CompletionCriteria: 步骤自带
Background: {
  "计划":       计划 Name + Goal,
  "进度":       "第 N/M 步",
  "上一步结果": 前一步 Digest（截断 1200 字）
}
```

注入点复用现成的 `buildSubContract`（`internal/agentprompt/sub.go` 已经把 `Background` 渲染进子 Agent prompt），不需要新 prompt 通道。

### 3.4 派活入口

`delegate` 加可选参数：

```json
"steps": [
  {"name": "查目的地信息", "goal": "...", "deliverables": [...], "completion_criteria": [...]},
  ...
]
```

- 传了 `steps`（2~9 条，校验失败直接报错给 LLM 重试）→ 建计划 + 派第 1 步
- 返回：`{"plan_id": 12, "task_id": 88, "steps": 6, "status": "pending"}`
- 不传 → 完全走现有路径（零行为变化，单测锁死）

新增 `manage_plan` 工具：`action = status | cancel | resume`，与 `query_task` 一致——**不凭记忆回答状态，必须查**。

### 3.5 汇报策略（关键，先定死）

| 场景 | 行为 |
|------|------|
| 计划内的步骤任务 | **不进**逐条汇报；推进器接管的步骤任务置 `reported=true`，避免 Web 轮询把 9 步拆成 9 条消息打断对话 |
| 成功步骤 | **不推送**（用户反馈：9 步 9 条太打扰）。进度看任务中心，或问一句由 `manage_plan status` 回答 |
| 步骤失败/暂停 | 推一条「第 N/M 步卡住了 + 原因 + 说"继续"重试」（这是唯一需要立刻打扰用户的时刻） |
| 计划终态 | 汇总汇报一条（完成/取消都推，取消说明停在第几步） |
| 渠道不可用 | 沿用 33 号 `Available()` 门控 + 前置补报兜底，不标记 reported |

汇总汇报复用 `ReportComposer`：各步 Digest 拼成素材交给主 Agent 转述；LLM 失败则模板拼接兜底（消息必达）。

### 3.6 API 与前端

- `GET /api/v1/agent/plans` 列表（含步骤状态与 task_id）
- `GET /api/v1/agent/plans/:id` 详情
- `POST /api/v1/agent/plans/:id/cancel` 取消（级联取消当前步任务）
- `POST /api/v1/agent/plans/:id/resume` 继续（paused 才允许）
- 全部属主校验（非本人 404，与现有任务接口一致）

前端：

- `TaskDialog.vue` 列表上方加「计划」分组卡：名称 + `3/9` + 状态徽标，展开看步骤，点步骤进该任务流水
- 任务详情页显示「属于计划 X · 第 N 步」
- 新增 `frontend/src/services/plan.ts`、`types/api.ts` 的 `TaskPlanItem/TaskPlanDetail`
- 样式沿用现有 scoped CSS + CSS 变量（不引入 Tailwind 混写，保持组件内一致）

### 3.7 Prompt 规则

在「怎么派」段加一节，判据写死防滥用：

- **该拆**：有先后依赖、后一步要用前一步结果、预计 ≥3 个执行单元（行程编排、多轮调研、先查资料再写稿）
- **不该拆**：一次查询能答的；步骤互不依赖的（互不依赖应在一个任务内部处理）
- **表达**：不宣读步骤清单（延续"不要复述执行计划"），只说"我拆成 5 步，做完一件说一件"
- **上限 9 步**，超了先合并

### 3.8 恢复与取消

- **重启恢复**：服务启动时 `PlanRunner.Recover()` 扫 `status=running` 的计划：当前步任务还活着 → 不管；已终态 → 按规则推进；任务不存在 → 标 `paused` 并提示。放在 25 号 `Recover` 同一装配位置，异步执行不阻塞启动
- **取消**：`cancel_task` 取消某步 → 计划整体 `cancelled`（线性链没有可留分支）；`cancel plan` → 取消当前步任务
- **前端轮询**：计划进行中，任务中心详情 5s 轮询已有机制，计划进度随任务状态变化自然刷新

## 4. TDD 顺序

1. domain：`TaskPlan` 状态机 + `ValidateSteps`（0/1 步拒、>9 步拒、空 goal 拒）
2. repository：CAS 推进只成功一次；并发两回调只推进一步；按用户列计划
3. PlanRunner：成功推进 / 失败暂停 / 最后一步汇总 / 取消级联 / `StartTask` 失败回滚 / Digest 注入内容
4. observer：多播后 25 号周期任务回调不回归
5. tool：`delegate` 带 steps 建计划；不带 steps 行为不变
6. API：列表/详情/取消/续跑的属主隔离
7. 恢复：构造 running + 已完成当前步，`Recover()` 后应推进

- `SetFinishedObserver` 保留（内部改为多播的首次注册语义），25 号周期任务不用改

## 6. 风险

| 风险 | 处理 |
|------|------|
| 9 步 × 180s ≈ 27 分钟 | 每步独立超时；成功步骤静默，只在卡住时喊人 |
| 步骤间信息衰减 | Digest 截断 1200 字；不够让它重查，不塞全文 |
| LLM 乱拆计划 | prompt 判据 + 上限 9 步 + 单测锁关键句 |
| 双推进 / 重启重入 | 计划 version CAS + 当前步任务状态检查 |
| 汇总汇报 LLM 失败 | 模板拼接兜底，保证消息必达 |
| 计划跑到一半用户改需求 | 只能取消重派（v1 不支持改步骤） |

### 7.2 与原方案的差异（3 处）

1. **汇总汇报不用 `ReportComposer`**：改为模板拼接（`BuildPlanSummaryText`）。原因：汇总消耗一次 LLM
   而且可能失败，而模板文本确定、免费、必达；各步结论已在步骤摘要里，不需要再转述一遍。
2. **Web 侧不推送**：计划进度/汇总只推 IM（飞书/微信）。Web 通过任务中心计划卡查看，不额外造聊天消息类型
   （避免为"计划"新增一种消息 Kind，改动面大于收益）。后续若要 Web 聊天内提示，需另加消息类型。
3. **步骤任务的 `TaskID` 不落 `task_plans.steps`**：改为接口层按 `(plan_id, seq)` 回查 `agent_tasks` 回填。
   原因：落 ID 需要在派活后二次 CAS，多一次写且失败窗口更难处理；回查天然取到"最新一次重派"。

## 8. v2.12 改造：计划从独立表合并进 agent_tasks

### 8.1 为什么要改

上线后发现三个问题：

1. **Web 没有最终结论**：计划完成只推 IM（`PlanNotifierFor("web")` 为 nil），步骤任务又被标成 reported，
   所以 Web 聊天里空空如也——只有任务中心那张卡片。
2. **`task_plans` 与 `agent_tasks` 高度重复**：14 个字段里 11 个一一对应；两套概念导致汇报只挂在一套上。
3. **任务中心变成两个列表**（计划卡 + 任务列表），用户认知里"计划也是任务"。

### 8.2 新模型

```
agent_tasks
  #70  kind=plan  parent=NULL  "成都三日游攻略"   status=running
  #71  kind=task  parent=70    step_seq=1  "定行程骨架"  reported=true
  #72  kind=task  parent=70    step_seq=2  "定住宿区域"  reported=true
```

- 新增列：`kind`（task/plan）、`step_seq`；复用既有 `parent_task_id`
- 新增状态 `paused`（仅容器使用）：某步失败等用户决定
- **容器终态走普通任务汇报链路**：completed 时写模板汇总进 `artifact`、`reported=false`，
  Web 的 `/report` 会把它转述成对话里的最终结论；IM 由既有 notifier 转述
- 子任务创建即 `reported=true`，永不进汇报轮询（成功步骤也不推消息）
- 删除 `task_plans` 表、`/api/v1/agent/plans` 接口与 `services/plan.ts`

### 8.3 推进规则

- 全部子任务按 `step_seq` 顺序派发；派下一步前把上一步 artifact 摘要写进其 `TaskSpec.Background`
- 某步失败 → 容器 `running→paused`，推一条「卡在第几步 + 原因」；用户说「继续」→ `paused→running`，
  失败子任务重置 pending 后重试
- 全部完成 → 容器 `completed` + artifact 汇总 → 触发汇报
- 重启恢复：扫 `running` 容器，看子任务现状补推进；无子任务/异常 → `paused`
- 幂等：子任务 `pending→running` 与容器状态迁移都走既有 CAS，重复回调不会跑两步

### 8.4 兼容性

- 存量普通任务：`kind` 空值按 `task` 处理，`parent_task_id` 为空 → 行为不变
- 旧的 `task_plans` 数据不再读取（现网仅 1 条）；旧子任务（只有 `plan_id`）会作为普通任务展示
- `agent_tasks` 旧列 `plan_id/plan_step_seq` 与旧表 `task_plans` 由启动迁移清理
  （`cleanupLegacyPlanSchema`：`DROP TABLE IF EXISTS` + `DROP COLUMN`，幂等、只动结构不动数据）

### 8.5 v2.12.1：卡住的三个缺口

1. **Web 暂停无消息**：`PlanNotifierFor("web")` 为 nil，暂停只推 IM。现在 Web 侧落一条 report 消息 +
   WS `plan.paused` 事件；前端收到后刷新历史
2. **一次超时就整单停摆**：对"子 Agent 执行超时"这类环境性失败自动重试该步一次（`Attempts` 计数），
   业务失败不重试
3. **没有继续入口**：任务中心计划详情页加「继续」按钮 → `POST /agent/tasks/:id/resume`（仅容器 + paused）
