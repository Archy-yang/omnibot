## 二、目标与范围

将记忆系统从「显式写入 + 最近 N 条被动注入 + 子串匹配检索」的 MVP，升级为：

1. **三层记忆模型**：短期（最近 N 轮，不动）+ 中期（对话纪要 digests）+ 长期（记忆条目 memories）；
2. **语义检索**：embedding + 余弦相似召回，替代子串匹配；检索通道以 Agent 工具为主、常驻注入收敛为「记忆索引」；
3. **自动沉淀管线**：对话纪要生成 + 长期记忆提取；
4. **EmbeddingProvider 接口抽象**：不绑定本地/云端，支持系统默认 + 用户级向量配置（百度千帆等三方平台）；
5. **可选 Reranker 接口位**：本期不实现，留扩展点。

不在本期范围：记忆分类/评分逻辑、导出迁移、pgvector（理由见 §6.4）、风格画像。

## 三、总体架构

```
┌────────────────────────── 写路径（沉淀） ──────────────────────────┐
│                                                                    │
│  对话轮次结束 → 水位线检查 → 段落摘要(digests) ─┐                    │
│                                             ├→ 提取 LLM 判断      │
│  用户显式 #记住 / Web 创建 ──────────────────┘→ 长期记忆条目         │
│                                                                    │
│  写入后 → EmbeddingProvider.Embed → 向量落库（带模型标记）           │
│          （embedding 失败 → 仅存文本，检索降级，见 §7.4）            │
└────────────────────────────────────────────────────────────────────┘

┌────────────────────────── 读路径（召回） ──────────────────────────┐
│                                                                    │
│  常驻注入：记忆索引（top-N 精选摘要，几行文字，非全量）               │
│                                                                    │
│  Agent 工具召回：                                                   │
│    search_memories → memories 语义检索（长期）                       │
│    search_history  → digests  语义检索（中期）+ 溯源指针             │
│                                                                    │
│  管线：Query → Embed → 余弦 top-K → (可选 rerank) → 结果+溯源       │
└────────────────────────────────────────────────────────────────────┘
```

读路径中短期照旧（`BuildContextMessages` 最近 N 轮），长期/中期以 Agent 工具召回为主体，常驻注入收敛为极小的记忆索引。

## 四、数据模型

### 4.1 `memories`（现有表，加列迁移）

```go
type Memory struct {
    ID              int64
    UserID          int64     `gorm:"index"`
    Content         string    `gorm:"type:text"`        // 现有
    Source          string    `gorm:"size:20;default:manual"` // 新增: manual=显式, auto=自动提取 (PRD AC1.3)
    SourceMessageID *int64                              // 新增: 溯源, manual 可为 NULL
    Embedding       []float32 `gorm:"serializer:json"`  // 新增: JSON 列, SQLite/PG 通吃
    EmbeddingModel  string    `gorm:"size:100"`         // 新增: 生成向量的模型标识 (见 §6.3)
    Category        string    `gorm:"size:50"`          // 新增: 预留列, 本期恒空
    Importance      int                                 // 新增: 预留列, 本期恒 0
    CreatedAt / UpdatedAt                               // 现有
}
```

加列均为可空/带默认值，老数据迁移零风险（老数据 `Source=manual`、`Embedding=NULL`）。

### 4.2 `conversation_digests`（新表，中期）

```go
type ConversationDigest struct {
    ID             int64
    UserID         int64     `gorm:"index"`
    Summary        string    `gorm:"type:text"`
    Embedding      []float32 `gorm:"serializer:json"`
    EmbeddingModel string    `gorm:"size:100"`
    FromMessageID  int64     `gorm:"index"`   // 覆盖区间 [from, to] → messages.id
    ToMessageID    int64     `gorm:"index"`   // ← 溯源指针 (PRD AC2.2)
    MsgCount       int
    Status         string    `gorm:"size:20;default:active;index"` // active / superseded
    CreatedAt      time.Time
}
```

### 4.3 `digest_watermarks`（新表，单行/用户）

```go
type DigestWatermark struct {
    UserID             int64  `gorm:"primaryKey"` // 单用户单行
    LastDigestMsgID    int64  // 摘要管线已处理到的 messages.id
    UpdatedAt          time.Time
}
```

显式水位而非从 digests 派生 `max(to_message_id)`：删除纪要重算时水位不应倒退。

### 4.4 溯源链

```
memory.SourceMessageID ──→ messages.id（单条来源）
digest.[FromMessageID, ToMessageID] ──→ messages.id 区间（时间段来源）
```

单一长期对话模型下 messages 按 user_id 全量有序，id 即时间线锚点，无需 session 概念。

## 五、EmbeddingProvider 接口抽象

### 5.1 接口定义

```go
// internal/service/memory/embedding_provider.go
type EmbeddingProvider interface {
    // Embed 批量文本向量化。返回向量顺序与输入一致。
    // ctx 取消时尽快返回。维度由实现方模型决定，须与声明的 Dim() 一致。
    Embed(ctx context.Context, texts []string) ([][]float32, error)
    // Dim 向量维度（配置声明 + 启动校验）
    Dim() int
    // Name 模型标识（落 EmbeddingModel 列，见 §6.3）
    Name() string
}

// 可选扩展位（本期不实现，管线代码按 nil 处理）
type Reranker interface {
    Rerank(ctx context.Context, query string, candidates []string) ([]float64, error)
}
```

### 5.2 内置实现

| 实现 | 适用 | 说明 |
|------|------|------|
| `OpenAICompatEmbedding` | **百度千帆 v2 / 硅基流动 / 阿里 DashScope / OpenAI 等一切 OpenAI 兼容 `/v1/embeddings`** | 一个实现覆盖绝大多数三方平台（用户点名的千帆 v2 即 OpenAI 兼容端点）；base_url/api_key/model 全配置化 |
| `OllamaEmbedding` | 本地自部署、开发环境 | HTTP 调 `api/embed`，零 cgo；`qwen3-embedding:0.6b` / `bge-m3` |
| （预留）`FastEmbedEmbedding` | 二进制零外部依赖 | fastembed-go + bge-small-zh，需要时再加，接口不变 |

不同实现共用一个装配选择器：按配置 `provider` 字段构造。

### 5.3 配置模型：系统默认 + 用户级覆盖

**系统默认**（`config.yaml`，激活现有死配置 `cfg.Memory`）：

```yaml
memory:
  embedding:
    provider: "openai_compatible"   # openai_compatible | ollama
    base_url: "https://qianfan.baidubce.com/v2"
    api_key: ""                      # 系统级,非用户敏感(用户级 key 才加密)
    model: "bge-large-zh"
    dims: 1024
    timeout: "10s"
  extraction:
    enabled: true
    batch_size: 10
```

**用户级向量配置**（用户 LLM 配置页扩展，`user_llm_configs` 表加列或新表）：

```
embedding_provider / embedding_base_url / embedding_api_key(加密存储) / embedding_model / embedding_dims
```

解析顺序：**用户级 → 系统默认 → 不可用降级**。产品语义：对话模型是用户个性（风格），embedding 是系统能力（检索质量），故默认系统统一；用户想用自己的向量服务时可以覆盖。

### 5.4 可用性降级链（红线：记忆数据永远可用）

```
Embedding 可用   → 写: 文本+向量    读: 语义+子串融合
Embedding 不可用 → 写: 仅文本(EmbeddingModel 空)
                   读: 子串匹配(现有 filterMemories 保留为降级路径)
```

Embedding 是检索增强而非存储前提；`Embed` 失败不阻塞记忆写入。

## 六、关键设计决策

### 6.1 两张表而非一张 + tier 字段

digests（机器生成、可再生、UI 不直接曝光）与 memories（用户资产、可编辑、管理页曝光）生命周期与曝光面不同；且天然对齐既有双工具 `search_memories`/`search_history`，各查各表。

### 6.2 JSON 向量列 + 应用层余弦，不上 pgvector

单用户语料几百~几千条，暴力余弦毫秒级；SQLite/PG 通吃，开发环境零依赖；换模型全库重嵌成本低（语料小）。pgvector 触发条件：单用户语料过万或需要跨用户聚合检索，届时 JSON 列 → vector 列平滑迁移。

### 6.3 向量必须带模型标记（用户级配置的直接后果）

不同 embedding 模型的向量空间**不可互比**。用户切换向量配置后：

- 检索时只与 `EmbeddingModel == 当前生效模型` 的向量比较；
- 模型不一致的存量向量不比较（退化为子串匹配参与融合）；
- 提供**后台重嵌入**入口（管理操作）：按当前生效模型全量重算，完成后旧向量自然被覆盖。语料小（千级），重嵌成本秒级。

`EmbeddingProvider.Name()` 即为该标记（如 `qianfan/bge-large-zh`、`ollama/qwen3-embedding:0.6b`）。启动时校验 `len(vector) == Dim()`，不符立即 fail-fast。

### 6.4 检索融合策略（本期最小）

```
score = 语义分(余弦)      —— 有向量时
      + 子串命中加成       —— 保留现有 filterMemories 作为一路
结果取并集,按 score 排序,语义为主、子串为辅
```

不做多路召回权重体系与 reranker（触发条件见《09-后续能力演进规划》）；`Reranker` 接口位已预留，`nil` 时跳过。

### 6.5 常驻注入收敛为「注入分层」（2026-09-02 修订）

按记忆来源分层交付（原「top-N 索引」方案被本修订替代）：

- **手动记忆（manual）= 常驻**：用户主动交代的是其意志，每轮全量注入（小而有界，200 字/条、人工写入）；
- **自动记忆（auto）= 工具召回**：沉淀管线产出，量无界且有噪声风险，**不进 prompt**，只在注入区出一行存在性提示（条数 + 引导用 `search_memories` 检索），内容全部走工具按需取。

数据来源：`MemoryService.GetMemoryInjection`（manual 全量 + auto 计数）。理由：两类记忆契约不同（用户意志 vs 助手笔记）、成本曲线不同（有界 vs 无界）、出错影响面不同（每轮污染 vs 仅相关话题可见）。

## 七、沉淀管线（写路径）

### 7.1 触发与水位推进

> **修订（2026-09-02）**：纪要与提取**合并为单次 LLM 调用**（`{summary, memories[]}` 一次产出）——LLM 成本减半，且两个产物基于同一次理解。调用失败或 schema 非法 → 整批作废、水位不动、下轮重试（原「提取失败不影响纪要与水位」语义随合并取消）。默认阈值 10 → 20（攒批越大摊销越低，更贴近"按对话段落"）。
>
> **已知局限 / 演进方向（沉淀策略应可动态调整）**：固定条数是"时间切片"而非"语义切片"，批边界可能砍在话题中间，前后两批纪要各半截。候选演进（水位线架构不变，只换切分策略）：
> 1. 空闲切分——轮次间隔超时视为天然段落边界（最便宜的语义信号）；
> 2. 自适应延批——LLM 判断"本批结尾话题未完"则水位只推进到话题结束处；
> 3. 滑动重叠——相邻批共享尾部几条消息衔接上下文。

```
每次对话轮次结束(消息落库后) → 异步检查:
  pending = 查询 messages WHERE id > watermark.LastDigestMsgID
  若 pending 条数 ≥ 阈值(默认 20, 配置化) → 触发一轮摘要+提取
  成功后推进 watermark; 失败不推进(下轮重试), 保留最后处理区间
```

异步 goroutine + 单用户串行（per-user mutex），不阻塞对话响应（PRD 非功能 4）。

### 7.2 中期：纪要生成

输入 `[watermark+1, 最新消息]` 区间的对话原文（含角色），LLM 产出一段纪要（主题 + 结论 + 未决事项），写入 digests（区间=本次处理范围），推进水位。纪要生成用的 LLM 配置：系统默认对话模型（提取属于系统能力，不随用户配置）。

### 7.3 长期：记忆提取

与纪要同批次跑，输入同一区间：

- LLM 按固定 schema 输出候选记忆列表（含来源 message id），schema 校验失败即丢弃本批；
- **去重**：候选与现有记忆做余弦相似比对，相似度 ≥ 阈值（默认 0.92）视为重复，跳过；相似度在 [0.80, 0.92) 视为疑似冲突，按「新事实为准」更新原文并刷新向量（对齐 PRD §五.3 用户当前陈述优先）；
- 候选写入 memories，`Source=auto`、`SourceMessageID=来源`，随写随嵌；
- 提取宁可漏不可错（PRD 红线）：prompt 中明确「只提取确定、稳定、长期有效的信息」。

### 7.4 降级一致性

提取/纪要依赖 LLM（系统默认对话模型），LLM 不可用时本轮跳过、水位不推进——与 embedding 降级链独立，两层都不影响记忆的显式写入。

## 八、读路径改造

| 组件 | 现状 | 改造 |
|------|------|------|
| `BuildContextMessages` 长期记忆注入 | 最近 10 条全文 system message | 改为记忆索引（§6.5），10 条全文注入移除 |
| `search_memories` 工具 | 拉最近 50 条子串匹配 | 语义检索 + 子串融合（§6.4），返回含来源信息 |
| `search_history` 工具 | 占位（返回"待实现"） | 实现：digests 语义检索，返回纪要 + `FromMessageID~ToMessageID` 溯源 |
| 子 Agent 可见性 | search_memories 带 `research` 标签默认可见 | 不变；`search_history` 同打 `research` 标签 |
| 渠道记忆命令（微信） | `#记住/#我的记忆/#清空记忆/#删除记忆 N` | `#我的记忆` 输出增加来源标记与时间线；飞书补齐同套命令（PRD AC4.3） |
| Web 记忆管理页 | CRUD | 列表增加来源标识 + 来源回溯入口（按 SourceMessageID 区间取 messages 明细）；自动沉淀开关 |

新增 API：`GET /api/v1/memories/:id/source`（返回来源对话明细）；`GET /api/v1/digests`（纪要列表，含溯源）。

## 九、实施计划（分期）

### M1：向量地基（先跑通读路径）✅ 已完成（2026-08-31）

1. domain：memories 加列 + digests/watermarks 表 + 迁移
2. `EmbeddingProvider` 接口 + OpenAI 兼容实现 + Ollama 实现 + 装配选择器 + 降级链
3. 检索管线（语义+子串融合）+ `search_memories` 语义化 + `search_history` 落地
4. 配置：`memory.embedding` 激活 + 用户级向量配置扩展

### M2：沉淀管线（写路径）✅ 已完成（2026-09-02）

1. 水位线 + 异步触发框架（per-user 串行）
2. 纪要生成 → digests 落库
3. 记忆提取（schema 校验 + 去重/冲突更新）→ memories 落库
4. 微信/飞书记忆命令补齐（来源标记、飞书命令）

### M3：注入收敛 + 管理面

1. 记忆索引注入替换 10 条全文（联动 11-Prompt管理方案）
2. Web 管理页：来源标识、来源回溯、纪要列表、自动沉淀开关
3. 后台重嵌入管理操作

每期独立可发布、可回滚（M1 上线即语义检索生效，无沉淀也不破坏现状）。

| # | 测试 | 断言 |
|---|------|------|
| 1 | memories 迁移测试 | 老数据迁移后 Source=manual、Embedding=NULL、可正常读写 |
