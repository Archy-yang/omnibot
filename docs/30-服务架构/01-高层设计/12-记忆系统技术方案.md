## 二、目标与范围

将记忆系统从「显式写入 + 最近 N 条被动注入 + 子串匹配检索」的 MVP，升级为：

1. **三层记忆模型**：短期（最近 N 轮，不动）+ 中期（对话纪要 digests）+ 长期（记忆条目 memories）；
2. **语义检索**：embedding + 余弦相似召回，替代子串匹配；检索通道以 Agent 工具为主、常驻注入收敛为「记忆索引」；
3. **自动沉淀管线**：对话纪要生成 + 长期记忆提取；
4. **EmbeddingProvider 接口抽象**：不绑定本地/云端，支持系统默认 + 用户级向量配置（百度千帆等三方平台）；
5. **可选 Reranker 接口位**：本期不实现，留扩展点。

不在本期范围：记忆分类/评分逻辑、导出迁移、pgvector（理由见 §6.4）、风格画像。

> 注：本文所述"中期=digests 纪要"已在 M6 退役（§9.3），中期层职责由 M7 消息级向量层接棒（§10）。

## 三、总体架构

```
┌────────────────────────── 写路径（沉淀） ──────────────────────────┐
│                                                                    │
│  对话轮次结束 → 水位线检查 → 段落摘要(digests) ─┐                    │
│                                             ├→ 提取 LLM 判断      │
│  用户显式 #记住 / Web 创建 ──────────────────┘→ 长期记忆条目         │
│                                                                    │
│  写入后 → EmbeddingProvider.Embed → 向量落库（带模型标记）           │
│          （embedding 失败 → 仅存文本，检索降级，见 §7.4）            │
└────────────────────────────────────────────────────────────────────┘

┌────────────────────────── 读路径（召回） ──────────────────────────┐
│                                                                    │
│  常驻注入：记忆索引（top-N 精选摘要，几行文字，非全量）               │
│                                                                    │
│  Agent 工具召回：                                                   │
│    search_memories → memories 语义检索（长期）                       │
│    search_history  → digests  语义检索（中期）+ 溯源指针             │
│                                                                    │
│  管线：Query → Embed → 余弦 top-K → (可选 rerank) → 结果+溯源       │
└────────────────────────────────────────────────────────────────────┘
```

读路径中短期照旧（`BuildContextMessages` 最近 N 轮），长期/中期以 Agent 工具召回为主体，常驻注入收敛为极小的记忆索引。

## 四、数据模型

### 4.1 `memories`（现有表，加列迁移）

```go
type Memory struct {
    ID              int64
    UserID          int64     `gorm:"index"`
    Content         string    `gorm:"type:text"`        // 现有
    Source          string    `gorm:"size:20;default:manual"` // 新增: manual=显式, auto=自动提取 (PRD AC1.3)
    SourceMessageID *int64                              // 新增: 溯源, manual 可为 NULL
    Embedding       []float32 `gorm:"serializer:json"`  // 新增: JSON 列, SQLite/PG 通吃
    EmbeddingModel  string    `gorm:"size:100"`         // 新增: 生成向量的模型标识 (见 §6.3)
    Category        string    `gorm:"size:50"`          // 新增: 预留列, 本期恒空
    Importance      int                                 // 新增: 预留列, 本期恒 0
    CreatedAt / UpdatedAt                               // 现有
}
```

加列均为可空/带默认值，老数据迁移零风险（老数据 `Source=manual`、`Embedding=NULL`）。

### 4.2 `conversation_digests`（新表，中期）

```go
type ConversationDigest struct {
    ID             int64
    UserID         int64     `gorm:"index"`
    Summary        string    `gorm:"type:text"`
    Embedding      []float32 `gorm:"serializer:json"`
    EmbeddingModel string    `gorm:"size:100"`
    FromMessageID  int64     `gorm:"index"`   // 覆盖区间 [from, to] → messages.id
    ToMessageID    int64     `gorm:"index"`   // ← 溯源指针 (PRD AC2.2)
    MsgCount       int
    Status         string    `gorm:"size:20;default:active;index"` // active / superseded
    CreatedAt      time.Time
}
```

### 4.3 `digest_watermarks`（新表，单行/用户）

```go
type DigestWatermark struct {
    UserID             int64  `gorm:"primaryKey"` // 单用户单行
    LastDigestMsgID    int64  // 摘要管线已处理到的 messages.id
    UpdatedAt          time.Time
}
```

显式水位而非从 digests 派生 `max(to_message_id)`：删除纪要重算时水位不应倒退。

### 4.4 溯源链

```
memory.SourceMessageID ──→ messages.id（单条来源）
digest.[FromMessageID, ToMessageID] ──→ messages.id 区间（时间段来源）
```

单一长期对话模型下 messages 按 user_id 全量有序，id 即时间线锚点，无需 session 概念。

## 五、EmbeddingProvider 接口抽象

### 5.1 接口定义

```go
// internal/service/memory/embedding_provider.go
type EmbeddingProvider interface {
    // Embed 批量文本向量化。返回向量顺序与输入一致。
    // ctx 取消时尽快返回。维度由实现方模型决定，须与声明的 Dim() 一致。
    Embed(ctx context.Context, texts []string) ([][]float32, error)
    // Dim 向量维度（配置声明 + 启动校验）
    Dim() int
    // Name 模型标识（落 EmbeddingModel 列，见 §6.3）
    Name() string
}

// 可选扩展位（本期不实现，管线代码按 nil 处理）
type Reranker interface {
    Rerank(ctx context.Context, query string, candidates []string) ([]float64, error)
}
```

### 5.2 内置实现

| 实现 | 适用 | 说明 |
|------|------|------|
| `OpenAICompatEmbedding` | **百度千帆 v2 / 硅基流动 / 阿里 DashScope / OpenAI 等一切 OpenAI 兼容 `/v1/embeddings`** | 一个实现覆盖绝大多数三方平台（用户点名的千帆 v2 即 OpenAI 兼容端点）；base_url/api_key/model 全配置化 |
| `OllamaEmbedding` | 本地自部署、开发环境 | HTTP 调 `api/embed`，零 cgo；`qwen3-embedding:0.6b` / `bge-m3` |
| （预留）`FastEmbedEmbedding` | 二进制零外部依赖 | fastembed-go + bge-small-zh，需要时再加，接口不变 |

不同实现共用一个装配选择器：按配置 `provider` 字段构造。

### 5.3 配置模型：系统默认 + 用户级覆盖

**系统默认**（`config.yaml`，激活现有死配置 `cfg.Memory`）：

```yaml
memory:
  embedding:
    provider: "openai_compatible"   # openai_compatible | ollama
    base_url: "https://qianfan.baidubce.com/v2"
    api_key: ""                      # 系统级,非用户敏感(用户级 key 才加密)
    model: "bge-large-zh"
    dims: 1024
    timeout: "10s"
  extraction:
    enabled: true
    batch_size: 10
```

**用户级向量配置**（用户 LLM 配置页扩展，`user_llm_configs` 表加列或新表）：

```
embedding_provider / embedding_base_url / embedding_api_key(加密存储) / embedding_model / embedding_dims
```

解析顺序：**用户级 → 系统默认 → 不可用降级**。产品语义：对话模型是用户个性（风格），embedding 是系统能力（检索质量），故默认系统统一；用户想用自己的向量服务时可以覆盖。

### 5.4 可用性降级链（红线：记忆数据永远可用）

```
Embedding 可用   → 写: 文本+向量    读: 语义+子串融合
Embedding 不可用 → 写: 仅文本(EmbeddingModel 空)
                   读: 子串匹配(现有 filterMemories 保留为降级路径)
```

Embedding 是检索增强而非存储前提；`Embed` 失败不阻塞记忆写入。

## 六、关键设计决策

### 6.1 两张表而非一张 + tier 字段

digests（机器生成、可再生、UI 不直接曝光）与 memories（用户资产、可编辑、管理页曝光）生命周期与曝光面不同；且天然对齐既有双工具 `search_memories`/`search_history`，各查各表。

### 6.2 JSON 向量列 + 应用层余弦，不上 pgvector

单用户语料几百~几千条，暴力余弦毫秒级；SQLite/PG 通吃，开发环境零依赖；换模型全库重嵌成本低（语料小）。pgvector 触发条件：单用户语料过万或需要跨用户聚合检索，届时 JSON 列 → vector 列平滑迁移。

### 6.3 向量必须带模型标记（用户级配置的直接后果）

不同 embedding 模型的向量空间**不可互比**。用户切换向量配置后：

- 检索时只与 `EmbeddingModel == 当前生效模型` 的向量比较；
- 模型不一致的存量向量不比较（退化为子串匹配参与融合）；
- 提供**后台重嵌入**入口（管理操作）：按当前生效模型全量重算，完成后旧向量自然被覆盖。语料小（千级），重嵌成本秒级。

`EmbeddingProvider.Name()` 即为该标记（如 `qianfan/bge-large-zh`、`ollama/qwen3-embedding:0.6b`）。启动时校验 `len(vector) == Dim()`，不符立即 fail-fast。

### 6.4 检索融合策略（本期最小）

```
score = 语义分(余弦)      —— 有向量时
      + 子串命中加成       —— 保留现有 filterMemories 作为一路
结果取并集,按 score 排序,语义为主、子串为辅
```

不做多路召回权重体系与 reranker（触发条件见《15-后续能力演进规划》）；`Reranker` 接口位已预留，`nil` 时跳过。

### 6.5 常驻注入收敛为「注入分层」（2026-09-02 修订）

按记忆来源分层交付（原「top-N 索引」方案被本修订替代）：

- **手动记忆（manual）= 常驻**：用户主动交代的是其意志，每轮全量注入（小而有界，200 字/条、人工写入）；
- **自动记忆（auto）= 工具召回**：沉淀管线产出，量无界且有噪声风险，**不进 prompt**，只在注入区出一行存在性提示（条数 + 引导用 `search_memories` 检索），内容全部走工具按需取。

数据来源：`MemoryService.GetMemoryInjection`（manual 全量 + auto 计数）。理由：两类记忆契约不同（用户意志 vs 助手笔记）、成本曲线不同（有界 vs 无界）、出错影响面不同（每轮污染 vs 仅相关话题可见）。

## 七、沉淀管线（写路径）

### 7.1 触发与水位推进

> **修订（2026-09-02）**：纪要与提取**合并为单次 LLM 调用**（`{summary, memories[]}` 一次产出）——LLM 成本减半，且两个产物基于同一次理解。调用失败或 schema 非法 → 整批作废、水位不动、下轮重试（原「提取失败不影响纪要与水位」语义随合并取消）。默认阈值 10 → 20（攒批越大摊销越低，更贴近"按对话段落"）。
>
> **已知局限 / 演进方向（沉淀策略应可动态调整）**：固定条数是"时间切片"而非"语义切片"，批边界可能砍在话题中间，前后两批纪要各半截。候选演进（水位线架构不变，只换切分策略）：
> 1. 空闲切分——轮次间隔超时视为天然段落边界（最便宜的语义信号）；
> 2. 自适应延批——LLM 判断"本批结尾话题未完"则水位只推进到话题结束处；
> 3. 滑动重叠——相邻批共享尾部几条消息衔接上下文。

```
每次对话轮次结束(消息落库后) → 异步检查:
  pending = 查询 messages WHERE id > watermark.LastDigestMsgID
  若 pending 条数 ≥ 阈值(默认 20, 配置化) → 触发一轮摘要+提取
  成功后推进 watermark; 失败不推进(下轮重试), 保留最后处理区间
```

异步 goroutine + 单用户串行（per-user mutex），不阻塞对话响应（PRD 非功能 4）。

**留痕可观测（M5.3）**：每轮沉淀创建一条 `agent_task`（`SubAgentType=digest`，system 发起，`Reported=true` 静默——不进主 Agent 回执轮询、不推送用户），`agent_steps` 锚 `task_id` 记执行链（`llm_call`：对话原文→LLM JSON 产出含耗时；`tool_call/digest.persist`：落库计数）。completed 置 artifact=纪要、failed 置 errorMsg，任务面板可查历史、失败可见。设计取舍：**不子 Agent 化**——沉淀是无工具调用的单次 LLM 调用，走 agent 循环纯属开销；留痕是旁路，留痕失败自动降级为仅日志，绝不阻断记忆生产；用户无可用 LLM 的空转轮完全不留痕（避免每轮刷 cancelled 任务）。

**积压分块（M5.1 硬化）**：单轮最多沉淀 40 条消息（`digestMaxBatchMessages`），积压超过时每轮只处理一块、水位推进到块尾，下一轮继续——首次沉淀/长期停用后的全量积压不再打包成一个巨请求（实测 80 条历史一次喂给 LLM 会触发上游 TTFB 超时）。尾部不足阈值时攒到下一批。

### 7.2 中期：纪要生成

输入 `[watermark+1, 最新消息]` 区间的对话原文（含角色），LLM 产出一段纪要（主题 + 结论 + 未决事项），写入 digests（区间=本次处理范围），推进水位。

**LLM 配置（M5.1 修订，2026-09-10）**：**用户配置优先、系统默认兜底**。原设计"系统默认对话模型（系统能力，不随用户配置）"在单用户部署下直接导致管线不可用（系统默认指向未配置的占位 provider），且沉淀消耗用户配额、产出用户记忆，与对话通道同源才符合"模型管理"的产品语义。装配点实现：用户 Web 端配置了自定义 LLM → 用该配置构造客户端（指纹缓存，改配置免重启）；未配置 → 回落系统默认；两者皆无 → 本轮静默跳过（水位不推进，配置后自动从当前区间开始）。

### 7.3 长期：记忆提取

与纪要同批次跑，输入同一区间：

- LLM 按固定 schema 输出候选记忆列表，schema 校验失败即丢弃本批；
- **溯源多对多映射（M5.2）**：候选带 `source_message_ids: int64[]`（一条提炼常由多轮交叉信息得出，单值指针失真），落 `memory_message_links` 表（memory_id+message_id 唯一索引）。校验：只保留落在本次处理区间的 ID（越界丢弃，全越界置空）；`memories.source_message_id` 保留为首个合法来源（主指针，展示兼容）。疑似冲突原位更新时溯源映射整体替换为新依据；
- **去重**：候选与现有记忆做余弦相似比对，相似度 ≥ 阈值（默认 0.92）视为重复，跳过；相似度在 [0.80, 0.92) 视为疑似冲突，按「新事实为准」更新原文并刷新向量（对齐 PRD §五.3 用户当前陈述优先）；
- 候选写入 memories，`Source=auto`，随写随嵌；
- 提取宁可漏不可错（PRD 红线）：prompt 中明确「只提取确定、稳定、长期有效的信息」。

### 7.4 降级一致性

提取/纪要依赖 LLM（M5.1 起按用户解析：用户配置 → 系统默认 → 皆无静默跳过），LLM 不可用时本轮跳过、水位不推进——与 embedding 降级链独立，两层都不影响记忆的显式写入。沉淀 embedding 同样按用户解析（M5.1：与读取路径共用用户级向量配置缓存），未配置时纪要/记忆无向量落库。

| 组件 | 现状 | 改造 |

## 九、M6：记忆模型重构——助理人视角（2026-09-10 立项落地）

> 产品决策：记忆不该是"对话切片的流水账"，而是助理人对用户世界的持续认知。
> 沉淀从"总结这段对话"改为"**对照已知世界观做增量对账**"。检索从"相似度碰片段"
> 升级为"这件事到哪了 → 命中事项，调出状态与关联事实"。

### 9.1 四层记忆模型

| 层 | 存储 | 语义 |
|----|------|------|
| 事项 matter | 新表 `matters` | 正在推进的事；`StateDesc` 为**当前状态**（覆写式更新，不追加）；`(user_id,title)` 唯一防裂名；status: active/done/archived |
| 事实 fact | `memories.kind=fact` | 关于用户的稳定事实（身份/偏好/家庭/资产） |
| 经历 episode | `memories.kind=episode` | 具体发生过的经历，带时间感，可淡忘 |
| 未决 loop | `memories.kind=loop` | 承诺/待确认的钩子 |

fact/episode/loop 通过可空的 `memories.matter_id` 挂靠事项（挂靠需 title 命中——宁缺毋错）。

### 9.2 对账式沉淀

沉淀输入 = 消息块（≤40 条，分块/水位/留痕机制不变）+ **世界观快照**（活跃事项的 title+StateDesc，
LLM 必须看到已有事项才能增量更新、且 title 从快照引用防裂名）。LLM 输出四路 JSON：

```
matter_updates: [{title, state_desc, status, source_message_ids}]   // 已有事项覆写 / 新建
facts:          [{content, kind, matter_title?, source_message_ids}] // 三种 kind,挂靠可选
```

执行：matters upsert（覆写 StateDesc+向量）→ facts 过滤/溯源校验/余弦去重/挂靠 → links 复用。
闲聊块允许 matter_updates 为空（不硬造事项）；全部为空则本批无产出、水位照常推进。

### 9.3 digests 退役

`conversation_digests` 停止写入、表保留只读（search_history 历史数据仍可查，不做迁移）。
管线内 `digestRepo` 仅保留注入兼容，不再调用 Create。

### 9.4 检索升级（M6.2，已落地）

`search_memories` 两段式：第一段事项检索（向量 + 子串融合打分，标题子串为强信号加成 0.3、
状态子串 0.1，达阈值 0.25 才算命中——避免每个查询都勉强凑事项）；命中 → 返回**事项当前状态 +
挂靠记忆全景**（"这件事到哪了"直接得到完整答案）；第二段散点记忆检索，排除已随事项展示过的
（去重）。前端按事项分组展示（M6.3，延后）。


## 十、M7：中期记忆——消息级向量层（2026-09-11 立项落地）

> 产品认识：中/长期记忆的差异**不在时间，在抽象损失度**。抽象发生在沉淀入库那一刻且不可逆——
> 用时间窗过滤长期记忆，查到的仍是碎片，不是"带事实细节的近期记录"。
> 所以中期层只有两条路：**要么少抽象（存细节），要么可回溯（从碎片回到原文）**。M7 选后者加直达前者。

### 10.1 背景与缺口

M6 落地后的分层覆盖：短期=对话原文窗口；长期=memories 原子事实；事项=matters 状态快照。
缺口是**"最近发生了什么"**——不是稳定事实、也不是进行中事项（"上周试驾了什么""那天具体怎么说的"），
现有检索答不好。旧 digests（低抽象纪要）曾占据此层，退役教训：独立存一层"整理过的纪要"，
质量差且没人检索。

### 10.2 方案选型（含实验验证）

| 方案 | 思路 | 结论 |
|------|------|------|
| A 双写沉淀 | 管线一次出两产物：facts + 本批"具体纪要" | 否——旧 digests 同形态，重蹈覆辙 |
| B 滚动摘要金字塔 | 原文→滚动摘要→蒸馏 facts 随时间升级 | 否——反复重生成，管线复杂且每级都有损 |
| **C 消息级向量（采纳）** | 中期=原文本身，消息级 embedding 直达检索 | 零新增抽象管线、零信息损失、复用全部基建 |

**实验验证**（`cmd/embedexp`，2026-09-11，全量 100 条消息，qwen3-embedding-4b@1024）：
7 个已知答案查询，5 个精确命中（答案消息进 top4，多为第 1）、2 个邻域命中（同话题稀释，
扩 topK + 时间加权可解）；语义改写扛得住（"上个月花了多少钱"命中原文"充电总共花了多少钱"）。
边界：注入型知识（手动记忆，从未出现在对话原文）天然不覆盖——归长期常驻注入，分层各司其职。

### 10.3 分层模型总览（M7 后）

| 层 | 抽象度 | 存储 | 读法 |
|----|--------|------|------|
| 短期 | 零 | 对话窗口 | 上下文 |
| **中期（新）** | **零（原文）** | `message_embeddings` | 向量直达 top8 + 时间加权 |
| 长期 | 高（原子事实） | `memories` | `search_memories` 散点 top5 |
| 事项 | 状态覆写 | `matters` | 事项优先检索（M6.2） |
| 常驻 | 人工注入 | memories(source=manual) | 直接注入（含将来 core 升级，另立项） |

### 10.4 数据模型

新表 `message_embeddings`（消息向量，不存 content——原文在 messages，命中后回表，避免双写）：

| 列 | 说明 |
|----|------|
| message_id | PK，唯一 |
| user_id | 索引 |
| role | user/assistant（冗余小列，免回表即可渲染） |
| embedding | JSON 向量列（serializer:json，与 memories 同款） |
| embedding_model | 模型标识，只比同模型向量（§6.3） |
| created_at | 嵌入时间 |

新表 `embedding_watermarks`（消息嵌入水位，单用户单行）：`user_id` PK + `last_embedded_msg_id`。
**独立于 `digest_watermarks`**——嵌入失败不阻塞沉淀，沉淀失败不回退嵌入水位。

### 10.5 写路径（增量嵌入）

- 嵌入文本：`[role] content`，超 1500 字截断（实验同款）；仅 user/assistant 消息
- 触发：挂现有沉淀触发链路旁异步执行，独立水位独立批（≤8 条/批，实验验证）
- 失败重试：水位不动，下轮重试同区间；embedding 未配置/持续失败 → 中期层静默缺失，
  不影响长期/事项检索（沿用 §5.4 降级链）
- 存量回填：上线时一次性后台回填历史消息（分批，限速）

### 10.6 读路径（search_memories 三段式）

`search_memories` 一个工具，内部分三段（分层复杂性收在工具内部，不外溢为多个工具给 LLM 选择）：

1. **事项区**（不变）：SearchMatters 命中 → 状态全景 + 挂靠记忆
2. **中期区（新）**：query 向量 vs message_embeddings 余弦，**时间加权**：
   `score = 0.8×cos + 0.2×recency`（recency 指数半衰，30 天减半；只加权不硬限窗），
   top8，回表取 content+时间，按时间倒序标注展示
3. **长期区**（不变）：散点记忆 top5

`search_history` **下线**（digests 只读退役，工具检索死数据有误导性）；digests 表数据保留。
中期区与长期区不去重——原文与由它抽象出的 fact 互补而非冲突（fact 带 links 可回溯原文）。

### 10.7 配置与规模

- 复用现有 embedding 配置（用户级优先/系统默认），**零新增配置项**
- 检索仍为 Go 侧全载余弦（与 memories/matters 一致）：单用户数千消息 ≈ 每查几十 MB 内存量，
  当前规模可接受；**语料过万切 pgvector**（`POSTGRES_VECTOR.md` 预留方向）

## 十四、M8：记忆收敛二期——延批沉淀、loop 路与常驻 core（2026-09-26 立项）

### 14.1 背景与现状盘点

M6 拍板（§9）之后，Context Manager/Compact（§7）、Conversation Recall（turn 粒度 chunk）、M7 中期向量层（§10）相继落地。2026-09-26 对代码的盘点结论：

**M6 主体已落地**：matters 表（StateDesc 覆写式、active/done/archived）、对账式沉淀（世界观快照 + 单次 LLM 多路输出 MatterUpdates/Facts，`digest_reconcile.go`）、三段式检索（事项命中返回状态+关联 facts 全景 → 近期原文 → 长期，`memory_tools.go searchMemoriesMatterFirst`）、手动记忆常驻注入 + 自动记忆工具检索分层（`GetMemoryInjection`）。

**剩余缺口**（原 M6 拍板中未落地、或被新架构改写的部分，即本轮范围）：

| # | 缺口 | 现状 |
|---|------|------|
| 1 | 沉淀触发仍是固定 20 条消息计数切批 | 批边界可能砍在话题中间（§7.1 已知局限） |
| 2 | 对账只有 MatterUpdates/Facts 两路 | `memories.kind` 的 loop 枚举存在但无生产方，未决承诺/循环事务无处沉淀 |
| 3 | `memories.kind` 的 episode 枚举无生产方 | 经历层已被 Conversation Recall chunks 覆盖；独立存"整理过的转述"是 digests 教训重演（§10.1） |
| 4 | 自动记忆无常驻 core 机制 | 无 pinned 字段；"手动=常驻/自动=纯工具检索"是硬边界，反复强调的记忆无法浮上来 |
| 5 | digests 死代码 | repo 的 Create/MarkSuperseded/DeleteByID 已无生产调用方，管线仍注入 digestRepo |

### 14.2 设计

#### 14.2.1 沉淀切分：消息间隔延批（解固定 20 切批）

水位架构不变（`(fromID, toID]`、失败不推进下轮重试），只改**批终点选取**：

- 触发仍为 TurnSink 异步（每条助手消息落库后检查），积压 ≥ threshold（20）才启动；
- **批尾延伸**：从 threshold 处向后扫描消息，相邻消息时间间隔 ≥ 静默阈值（默认 10 分钟，可配 `cfg.Memory.Extraction.SilenceGap`）视为段落边界，批尾收在该边界处；上限仍为 `digestMaxBatchMessages=40`；
- 效果：话题中段不再被砍——批尾要么落在自然静默处，要么顶到 40 上限（超长连聊场景接受近似切分）。

明确不做：自适应延批（LLM 判断话题是否结束，多一次调用）、滑动重叠。先用确定性规则看效果，不够再迭代。

#### 14.2.2 对账第三路：loop（未决承诺/循环事务）

- `reconcileResult` 增加 `Loops []loopExtract{content, source_message_ids}` 第三路，允许任意路为空（原则不变）；
- 世界观快照增加「未决 loops」区（kind=loop 且未关闭，上限 20 条）；prompt 指令：对话显示某 loop 已完成/失效时输出 `LoopCloses []int64`（仅允许引用快照中列出的 ID）；
- **loop 关闭非破坏性**：memories 加 `Status` 列（`open/closed`，默认 open，仅 loop 语义使用；与 matters.Status 模式一致），关闭=置 closed，检索过滤 closed，可人工回滚——遵守"宁漏勿错"红线；
- 检索：三段式结构不动，loop 条目随"长期"段自然返回（`memoryAnnotation` 标注 kind）。

#### 14.2.3 episodes 枚举处置

- 沉淀 prompt 不输出 episode（现状也未输出）；枚举值从 `memories.kind` 移除（`NormalizeKind` 非法值仍兜底 fact），存量 episode 行迁移归一为 fact（迁移前查证数量，预计为零）；
- 经历层唯一事实源 = conversation_chunks；「重要经历置顶/锚定」（挂 chunk、不复制内容）列为观察项，本期不做。

#### 14.2.4 常驻 core：pinned 起步（三阶段之第一阶段）

- memories 加列 `pinned bool`（默认 false）+ `pinned_at`；
- 常驻注入列表 = manual 全量 ∪ pinned auto，合计受 token 预算约束（超限截断并保留"另有 N 条…用 search_memories 检索"提示）；`GetMemoryInjection` 改为合并来源；
- 管理面：Web 记忆抽屉增加置顶/取消置顶（API：置顶/取消置顶操作，越权返回 404）；
- 反复强调自动升级（三阶段之第二阶段）不在本期，先看人工置顶的使用效果。

#### 14.2.5 digests 死代码清理

- 删除 repo 的 Create/MarkSuperseded/DeleteByID、domain 的 ConversationDigest/DigestWatermark 及 AutoMigrate 注册、管线的 digestRepo 注入；
- **数据库表保留不删**（历史数据只读留档），仅代码不再引用。
