## 2. 核心设计原则

### 原则1：通道无关，能力通用
- 所有核心能力（对话、记忆、LLM 配置）与具体对话通道（微信/飞书/Web）完全解耦
- 接入新通道只需要实现 MessageChannel 接口，不需要改动任何业务逻辑

### 原则2：分层架构，依赖倒置
- 上层依赖下层接口，不依赖具体实现
- 领域层不依赖任何其他层

### 原则3：渐进式增强，零破坏性升级
- 所有架构调整必须保持向后兼容
- 双写、双读、平滑迁移，禁止一刀切重构

## 4. 各层职责说明

### 接入层
- 唯一依赖：只能依赖服务层接口
- 职责：接收特定通道的请求解析、响应格式化
- 不包含任何业务逻辑

### 服务层
- 依赖：只能依赖仓储层接口和领域模型
- 职责：业务逻辑编排、事务边界、权限校验
- 不包含任何特定通道的逻辑

### 仓储层
- 依赖：领域模型 + 基础设施
- 职责：数据读写、查询构建
- 不包含业务逻辑

### 领域层
- 依赖：无（纯 Go struct + 方法）
- 职责：定义核心业务规则、实体状态机

### 基础设施层
- 职责：数据库连接、外部 API 客户端、工具类
- 纯技术实现，无业务逻辑

## 5. 核心设计决策记录（ADR）

### 决策1：为什么不用微服务？
- **背景**：v1.0 是单体，要不要拆？
- **决策**：保持单体，按分层架构组织
- **原因**：
  - 团队规模小，单体开发效率高
  - 多通道场景下，单体的部署和运维复杂度低
  - 未来如果需要拆分，可以按层拆分，现在的分层架构已经为拆分做好了准备

### 决策2：为什么用 GORM 而不是纯 SQL？
- **背景**：ORM vs 手写 SQL 的永恒争论
- **决策**：用 GORM
- **原因**：
  - 自动迁移能力：表结构变更自动处理
  - 多驱动支持：SQLite / PostgreSQL 无缝切换
  - 开发效率：CRUD 不需要重复劳动

### 决策3：为什么用双写而不是直接数据迁移？
- **背景**：v1.2 只有 WechatAccount 表，v1.3 引入 UserChannel 表
- **决策**：双写新旧两张表，同时支持从旧表自动迁移到新表
- **原因**：
  - 零风险：出问题可以随时回滚到旧表
  - 无停机：不需要停机迁移方案对用户有影响
  - 渐进式：观察 2 个版本后再删除旧表

### 决策4：为什么通道接口是同步响应，而不是全异步？
- **背景**：微信要求 5 秒内必须响应，其他平台可能支持异步
- **决策**：接口层定义 IsAsync() 标识，各通道自己决定同步还是异步
- **原因**：
  - 不同平台能力不同，不能一刀切
  - 接口抽象需要适配各平台的特性

### 决策5：为什么用 Go Embed 做单二进制前后端部署？
- **背景**：前端和后端怎么部署？分开部署还是一起？
- **决策**：前端静态资源用 Go Embed 嵌入到 Go 二进制文件中
- **原因**：
  - 零依赖部署：只有一个二进制文件，`scp` 到服务器直接运行
  - 不需要 nginx、不需要 node、不需要 CDN
  - 前后端版本天然一致，不会出现版本兼容问题
  - 开发时分离，部署时合一，兼顾开发体验和运维体验

## 6. 目录结构映射

| 代码目录 | 架构层 |
|---------|--------|
| `frontend/` | 前端层（Web 通道） |
| `internal/api/` | 接入层 |
| `internal/channel/` | 通道抽象层 |
| `internal/service/` | 服务层 |
| `internal/repository/` | 仓储层 |
| `internal/domain/` | 领域层 |
| `internal/client/` | 基础设施层（外部客户端） |
| `internal/pkg/` | 基础设施层（工具类） |
| `pkg/` | 基础设施层（配置、日志） |
