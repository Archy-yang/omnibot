# 30 - 首周复盘与管家闭环打通技术方案

> **文档版本**：v1.0（2026-10-29 立项）
> **前置**：v2.6.0（29 号四里程碑收官）
> **定位**：不新增管家机制，只做三件事——复盘首周真实裁决效果、补两个用户入口、清日志噪声。
> **决策依据**：29 号 §6「上线后复盘首周裁决记录」+ 28 号 CHANGELOG 挂账「close_suggest 待观察期复盘」。

---

## 1. 背景与立项依据

### 1.1 立项前数据快照（2026-10-29 取自本机运行库）

| 指标 | 实测值 | 说明 |
|------|--------|------|
| `proactive_notes` | 13 条（10-17 01:25 ~ 10-29 01:18） | 6 条 delivered、7 条 skipped |
| `proactive_notes.feedback` | **0 条** | 29 号 N3/N4 的反馈入口上线后无任何反馈 |
| `matters.target_at` | **0 条**（共 11 个档案） | 目标维度无任何真实输入 |
| 容器日志 Error（近 7 天） | 106 条 | **104 条**是飞书 read receipt / recall 事件的 `not found handler` |
| `agent_tasks` | 58 个（52 completed / 3 failed / 3 cancelled） | 本迭代不处理 |

### 1.2 三条结论

1. **裁决链路在跑，但「建议→用户动作」没有可观测闭环。**
   - `matter:8:close`（西双版纳行程，10-23 送达）6 天后档案仍 `active`；
   - `matter:7`（美食清单）10-26 送达后仍无进展；
   - `loop:34`（中国官方对 AI 冷战回应）两次送达，用户 10-29 04:14 在对话里回「不用了」，13:59 loop 被关闭——
     **转化真实发生了，但发生在对话里，记录面和反馈面都没留下痕迹。**
2. **目标维度没有输入口。** `target_at` 全库为零，前端 `JournalDrawer` 只能展示 🎯 徽标、不能设置；
   29 号 N2 的 `goal_nudge` 在真实使用中不可达。
3. **日志噪声淹没真错误。** 7 天 106 条 Error 里只有 2 条是真实 websocket 断连。

**结论**：v2.6.0 之后不应继续堆机制，先验证已有机制、补齐入口。本迭代不调裁决 prompt、不加新机制。

## 2. 设计原则

1. **先验证再扩展**：N1 复盘结论决定 `close_suggest` / `goal_nudge` 的下一步（保留 / 改 / 砍），
   不在本迭代内顺手调裁决参数。
2. **入口最小化**：只补「能看见、能操作」的两个缺口，不新增表、不新增服务、不改 note 存储。
3. **红线不松**：收口必须用户显式操作（21 号纠正口 / 28 号红线），本迭代不提供任何系统自动收口路径。
4. **复盘只读**：N1 不在生产库写入测试数据、不改配置、不触发真实送达。

## 3. N1 首周复盘（只读，无代码）

### 3.1 口径

- 窗口：2026-10-17 01:25 ~ 2026-10-29 01:18（首条 ~ 末条 note）
- 样本：13 条 note 全量，逐条对照——
  - 信号键（`dedup_key`）→ 送达/拦下状态；
  - 送达后 72 小时内是否有相关对话；
  - 关联 matter / loop 的状态是否变化（`matters.status`、`memories.loop_status`）；
  - 用户是否通过 Web 反馈或飞书文本指令反馈。
- 判定三分类：**转化**（有明确动作）/ **无效**（明确拒绝或状态未变且无后续对话）/ **无法判定**（窗口不足）。
- 重点案例：`matter:8:close`（收口建议）、`loop:34`（两次提醒后对话关闭）、`matter:7`（搁置一个月）。

### 3.2 三个必答问题

| # | 问题 | 判定输入 |
|---|------|----------|
| Q1 | `close_suggest` 是否值得继续 | `matter:8` 发出后 6 天仍 active；是否有第二个收口候选 |
| Q2 | `goal_nudge` 是否值得继续 | 零目标日 → 当前不可达；N2 入口上线后需复查，不急着下结论 |
| Q3 | 反馈入口是否可达 | 0 反馈是「没需求」还是「不好找」；对照 29 号 N3 入口位置 |

### 3.3 交付物

`docs/90-迭代记录/复盘-主动管家首周.md`：逐条对照表 + 三个问题的结论 + 后续动作建议（进 backlog 或另起方案）。

### 3.4 红线

复盘不改代码、不改 prompt、不写库。结论若要求调整裁决逻辑，另起方案评审。

## 4. N2 目标日入口（API + 前端）

### 4.1 API

```http
PUT /api/v1/matters/:id/target
Content-Type: application/json

{"target_date": "2026-11-30"}   // 设置（YYYY-MM-DD）
{"target_date": ""}             // 清除（null / "clear" 同义）
```

成功：

```json
{"success": true, "data": {"target_at": "2026-11-30T00:00:00+08:00"}}
```

错误映射：

| 状态码 | 场景 |
|--------|------|
| 400 | 日期格式非法（提示 `YYYY-MM-DD`）；`target_date` 缺省且非显式清除 |
| 401 | 未登录（既有 JWT 中间件） |
| 404 | 档案不存在或属于他人（不区分，防探测） |
| 503 | 个人经历层服务未装配 |

### 4.2 后端

- `internal/api/web/journal_handler.go` 的 `JournalService` 窄接口扩一个方法：
  `SetTargetMatter(ctx context.Context, userID, id int64, target *time.Time) (string, error)`。
- 复用 `memoryService.SetTargetMatter`（28 号 N2 已落地）与 `matterRepo.UpdateTarget`，**不新增 service/repo 方法**。
- 日期解析与 agent 工具同源：`time.ParseInLocation("2006-01-02", s, time.Local)`。
- 清除语义与 29 号 N1 对齐：字段缺省 / 空串 / `clear` → `target=nil`。
- `UpdateTarget` 现状不更新 `updated_at`：保持现状（目标日不改变档案内容新鲜度），在方法注释补一句说明。
- 路由：`mattersAPIGroup.PUT("/:id/target", ...)`，与既有 `/matters/:id` 同组鉴权。

### 4.3 前端

- `services/journal.ts` 增 `setMatterTarget(id: number, targetDate: string | null)`，返回 `{ target_at: string | null }`。
- `JournalDrawer` 档案详情 meta 行：在 🎯 徽标后补「设目标日 / 修改 / 清除」入口；
  编辑态用原生 `<input type="date">`（与 SettingsDrawer「原生控件」范式一致，不引 NaiveUI）。
- 档案列表卡片也显示 🎯 目标徽标（复用既有 `targetDays`），避免用户必须点进详情才知道有没有目标。
- 校验：空日期 → 清除；保存后即时更新本地 `detail.target_at` / 列表项。
- 清除不弹二次确认（可逆：重设即可），与 29 号 N1「清除口」轻量语义一致。

### 4.4 边界与不做

- 不做目标里程碑分解、不做每目标独立提醒开关（28 号边界保持）。
- 不做批量设置 / 从对话外创建目标事项（建档仍走对话工具）。
- 不改变 `goal_nudge` 触发条件；入口是否足够，由 N1 复盘与上线后观察决定。

## 5. N3 主动记录 → 档案直达

### 5.1 现状

`SettingsDrawer` 最近主动记录已由 DTO 暴露 `matter_id`，但记录行没有任何跳转；用户看到建议后要去「经历」抽屉重新找档案，转化路径断裂。

### 5.2 方案

- `SettingsDrawer`：记录含 `matter_id` 时显示「查看档案 →」，点击 `emit('open-matter', matterId)`。
- `ChatPage`：收到事件 → 关闭设置抽屉 → `pendingMatterId = id` → 打开 `JournalDrawer`
  （与 `TaskDialog` 的 `initial-task-id` / `clear-initial` 同款模式）。
- `JournalDrawer`：新增 prop `initialMatterId?: number | null`；`visible` 变 true 时若有值，
  切到「档案」tab 并直接 `openMatter(id)`，随后 `emit('clear-initial')`；`backToList` 行为不变。
- 记录行跳转只对 `matter_id` 非空生效；loop 类记录（无 matter_id）不显示入口。

### 5.3 不做「一键收口」的原因

收口需要看到档案现状（时间线、关联 loop、状态），记录行里只有一个标题片段的上下文不足以做不可逆决策；
21 号纠正口已在档案详情提供状态变更，28 号红线要求用户显式确认。若后续数据证明「跳过去再点两次」成本过高，
再单独评审记录行快捷动作。

### 5.4 测试

- 前端 `npm run build`（含 vue-tsc）通过。
- 手工三路径：记录 → 跳转对应档案 → 返回列表；无 matter_id 记录不出现入口；关闭抽屉后状态不残留。

## 6. N4 飞书杂音事件静默

### 6.1 现状

`chatterEventTypes` 只登记了 `im.chat.access_event.bot_p2p_chat_entered_v1`，采用「dump payload + INFO」语义。
`im.message.message_read_v1`（已读回执）与 `im.message.recalled_v1`（撤回）高频推送，仍走 SDK 默认 ERROR：
7 天 104/106 条错误是它们。

### 6.2 方案

- 新增 `silentEventTypes`：`im.message.message_read_v1`、`im.message.recalled_v1`，注册 **no-op handler**
  （不 dump payload，只吞掉事件）——这两类事件当前无业务语义，payload 也没有排查价值。
- 保留 `chatterEventTypes` 的 dump 语义：低频、未来可能需要照着 payload 实现的类型继续 dump。
- 未登记的新事件类型继续走 SDK `not found handler` ERROR（开发提示，不静默吞掉新事件）。
- 两类清单注释写清准入标准，避免以后把「想做但没做」的事件塞进 silent。

### 6.3 测试

- 两个 silent 类型：响应 200、body 不含 `not found handler`。
- 未登记类型：仍含 `not found handler`（守住显式白名单语义）。
- 既有 `chatterEventTypes` dump 测试不变。

### 6.4 边界

撤回事件只做静默，不处理「消息删除 / 记忆回滚」的业务语义——若需要，单独立项。
