# 28 - 目标闭环与事项完结技术方案

> **文档版本**:v1.0(2026-10-22 立项)
> **前置**:20号路线图第四阶段「Personal Goals」的细化;26号主动管家 5 天复盘的直接产出
> **决策**:按方案 A 执行——**不新建 Goal 实体,目标 = 带 target_at 的 matter**(用户 2026-10-22 拍板)

---

## 1. 背景与问题

### 1.1 26号复盘结论(2026-10-22,数据见 proactive_notes 全量)

26号机制本身零故障(门槛链/冷却/日限全部按设计工作),但暴露**候选对象「有生无死」**:

| 案例 | 现状 | 根因 |
|------|------|------|
| loop:34(AI冷战查证) | open 挂一个月,实际早有结论(10-17 送达内容即完整查证结果) | 完结无对话内出口——`SetLoopStatus` 只在管理面,对话流里没人用 |
| matter:10(父亲诊治) | 10-18 烧退,事项实际结束,仍 active | matter 状态滞留,10-21 继续产出过时提醒 |

5 天里 60% 的裁决调用是无效功(生成→被自己的冷却压掉)。

### 1.2 闭环缺口(20号 §6:记录→行动→反馈→调整)

| 环节 | 底座 | 状态 |
|------|------|------|
| 记录 | matters 档案(M6:状态机/时间线/loop 子项/文档同步) | ✅ |
| 行动 | persistent tasks(25号)+ delegate 派活 | ✅ |
| 反馈 | butler 信号收集 + 主动送达(26号) | ✅ |
| **调整** | **完结裁决 + 对话内收口 + 目标紧迫度** | ❌ 本方案 |

## 2. 设计原则

1. **不建第四实体**:目标 = `target_at` 非空的 matter。复用档案全部底座(时间线/loop/检索/飞书文档/butler 信号)。
2. **完结必须经用户确认**(红线):系统只建议,严禁自动 close——收口是语义破坏性动作,误判「已有结论」的代价是丢失跟进。
3. **复用 26号 克制基建**:收口建议是 butler 裁决的一类输出,共享同一次 LLM 调用、dedup 冷却、日限 1、夜间窗——收口建议也占「今天唯一一件事」名额,不增加打扰面。
4. **一切可逆**:matter done/archived 可 reopen,loop closed 可重开(管理面既有能力);工具返回里说明如何反悔。

## 3. 机制设计

### 3.1 完结裁决(26号 裁决扩展,零增量调用)

`adjudicationSystemPrompt` 的输出空间从「今天有没有真正值得提的一件事」扩展为
「**值得提的一件事 OR 收口建议**」,新增 kind:

```
close_suggest  // 事项/待办实际已有结论,建议收口(对话内确认后执行)
```

- dedup_key 沿信号键加后缀:`matter:10:close` / `loop:34:close`——与普通提醒同一 7 天冷却池
- 裁决指令新增:「对每个活跃事项/挂起待办,判断时间线是否表明它实际已有结论(任务完成、
  事件结束、话题有结果);已有结论且用户尚未收口的,优先给 close_suggest 而非重复提醒」
- 信号增强支撑判断:matter 行加最后动静时间(`最后动静 2026-10-18,距今 4 天`),
  loop 行已有挂起日期——**闲置时长是裁决「该收了吗」的核心证据**

### 3.2 对话内收口工具(新)

| 工具 | 参数 | 行为 |
|------|------|------|
| `manage_matter` | matter_id, action(close/archive/reopen/set_target), target_at? | 档案状态转移 + 目标日设置(见 3.3);matter_id 由 search_matters 查(描述引导) |
| `close_loop` | loop_query(关键词) | 按子串匹配该用户 open loops:唯一命中 → close;多命中 → 返回候选列表让模型确认;零命中 → 提示 |

- **级联**:`manage_matter close`(→done)联动关闭其下全部 open loops,返回里说明
  「已联动关闭 N 条待办」;loop:34 这类 matter_id 为空的孤儿 loop 走 `close_loop` 单独收
- 返回文案带反悔路径:「已完结;说『重新打开XX』或管理面可恢复」

### 3.3 目标维度

- matters 加列 `target_at *time.Time`(null = 普通事项;AutoMigrate)
- `manage_matter set_target` 设/改目标日;**目标必须挂既有档案**——LLM 先 search_matters,
  无档案则提示「先聊聊这件事让管家建档」(v1 不做对话内建 matter,见 §5)
- butler matter 信号行加紧迫度:`- [matter:10] 父亲诊治:...(目标 2026-10-31,剩 9 天)`;
  裁决指令说明临近目标日优先级提升、过期未收口给 close 或调整建议

### 3.4 用户旅程(闭环走通的样子)

1. 用户:「帮我查证 AI 冷战的官方回应」→ 管家派活/自答,loop 落库
2. 查证完成,结论进对话 → 沉淀为时间线记录
3. **次日 9 点 butler 扫描**:裁决发现该 loop 时间线已有结论 → `close_suggest`
   (飞书/Web 送达:「查证这事看起来已经完成了,要我把它收掉吗?」)
4. 用户回复「对,收掉吧」→ 管家调 `close_loop` → 收口 ✅
5. 此后该 loop 不再进候选池——**重复候选噪声根治**

## 4. 数据迁移

- `matters.target_at`(nullable timestamptz),AutoMigrate 自动落
- 无新表、无回填(存量 active matters 默认普通事项)

## 5. 边界与不做

- **不自动收口**:只建议,确认才动(§2 红线)
- **不做对话内创建 matter**:目标挂既有档案;档案仍由沉淀管线按对话段落聚合产生
- **不做目标里程碑分解**:v1 目标只有日期一个维度
- **persistent_tasks 联动不做**:「目标未达成自动派任务」是自然的 v2 延伸,v1 不碰
- **送达反馈 UI(proactive_notes.feedback)不在本方案**:复盘发现的另一缺口,
  独立小迭代(飞书卡片交互成本),挂 backlog

## 6. 风险

| 风险 | 处置 |
|------|------|
| 裁决 prompt 复杂化拖累既有裁决质量 | 金样本断言扩 close_suggest 场景;上线后复盘首周裁决记录 |
| close_suggest 骚扰 | 共享 butler 日限+冷却:收口建议占「今天唯一一件事」名额 |
| LLM 误判「已有结论」 | 只建议不执行;建议文案必须引用时间线证据;用户确认才 close |
| 孤儿 loop(loop_id 无 matter 挂靠)难收口 | close_loop 按内容子串匹配,不依赖 matter 归属 |
