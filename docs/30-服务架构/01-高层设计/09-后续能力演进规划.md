## 一、几条能力线的依赖关系(核心判断)

讨论中确认的关键判断:**这几条线不是平级的,有依赖顺序,且优先级需要重新排**。

```
后台 Agent 任务框架(A2A 委托协议 + 异步执行)
        ↓ (基础设施:任务表/状态机/委托协议/回执回流)
skill 系统(可配置工具,硬编码工具升级)
        ↓ (skill 是"工具"的泛化,Agent 框架是"用工具的人"的泛化)
MCP 协议对接(标准化 skill 接入,外部能力)
        ↓ (有了 skill 抽象,MCP 是"标准协议的 skill 源")
多 Agent 协作(子 Agent 编排,动态委托)
        ↓ (固定子 Agent 跑稳后,才谈动态/并行编排)
```

### 为什么这个顺序

- **后台 Agent 框架先于 skill/mcp**:框架要解决的"异步执行+状态持久化+回执回流"是所有
  后续能力的基础设施。没有它,skill 再多是同步阻塞调用,长任务照样卡死主对话。
- **skill 先于 MCP**:skill 是"工具的泛化"(从硬编码注册到可配置),MCP 是"skill 的标准接入协议"。
  先有 skill 抽象,MCP 才有附着点。
- **固定子 Agent 先于多 Agent 协作**:后台 Agent 框架第一版做固定子 Agent(见
  [08-后台Agent任务框架技术方案.md](./08-后台Agent任务框架技术方案.md)),
  跑稳后才有真实约束去设计动态编排/并行协作。

### 一个被否决的顺序

讨论中曾考虑"先做多 Agent 协作再做后台任务"--**否决**。
理由:多 Agent 协作是编排层,后台任务执行是基础设施。在没解决"任务怎么异步跑、状态怎么存、
结果怎么回"之前做编排,是倒置依赖。且多 Agent 协作对个人助手(单一长期对话模型)价值存疑,
需真实场景驱动,不能为做而做。

## 二、阶段性规划

### 阶段 0:v2.0 正式发布(当前前置)

**依赖**:v1.11 smoke(层 A 已过,P2 已修,层 B 待用户手测)。
**内容**:部署文档、产品介绍页、生产配置。
**地位**:所有后续能力的前置--发布前确认地基稳。

### 阶段 1:后台 Agent 任务框架 v1.0(下一迭代,已出方案)

**文档**:[08-后台Agent任务框架技术方案.md](./08-后台Agent任务框架技术方案.md)
**范围**:
- A2A 协议语义(进程内子集):Agent Card / Task / Artifact / 状态机
- 完整异步任务:delegate 工具派活 -> 子 Agent 后台跑 -> 不阻塞主对话
- 延迟汇报(C 模式):用户下次发消息时主 Agent 先汇报未汇报任务
- 固定子 Agent:框架 + 1 个示例子 Agent(researcher 研究员)
**不做**:主动推送、多子 Agent 并行、动态配置、跨进程 A2A、用户自定义子 Agent
**价值**:解决耗时任务阻塞主对话;为 skill/mcp/多 agent 提供任务基础设施
**风险**:LLM 派活可靠性(Function Calling 调 prompt)、进程重启丢运行中任务(第一版接受)

### 阶段 2:后台 Agent 框架 v1.1(补全 + 主动推送)

**触发条件**:阶段 1 跑稳,且用户反馈"想第一时间收到结果"。
**范围**:
- B 模式主动推送(子 Agent 完成 -> 触发主 Agent 生成汇报 -> SSE/客服消息推)
- 进程重启任务恢复(启动扫描 running 任务 -> 标 failed + 下次汇报)
- 任务查询接口 `GET /api/v1/agent/tasks`(用户主动看后台任务状态)
- 派活可靠性增强(规则层或 few-shot 示例,降低 LLM 乱派/漏派)
**地位**:把阶段 1 的"能用"做到"好用"。

### 阶段 3:skill 系统(工具泛化)

**触发条件**:阶段 1/2 验证了"Agent 派活"模式可用,且硬编码工具的扩展性瓶颈显现。
**范围**:
- Tool 接口从硬编码 `Register` 升级为可配置 skill(描述/参数schema/执行体分离)
- skill 元数据持久化(用户可见已装 skill,可启停)
- 子 Agent 的工具集从"代码写死工具名列表"改为"从 skill 库按权限选"
- 内置工具(get_current_time/calculator/rss_reader 等)迁移为 skill
**与阶段 1 的关系**:阶段 1 的 SubAgentCard.Tools 是工具名列表,阶段 3 让这些名字指向
可配置 skill 而非硬编码。框架不动,工具来源升级。
**价值**:兑现产品愿景「插件系统,可以自己扩展能力」。

### 阶段 4:MCP 协议对接(标准化 skill 接入)

**触发条件**:阶段 3 skill 抽象稳定,且需要接入外部能力(不自己写所有 skill)。
**范围**:
- MCP(Model Context Protocol)客户端:作为 skill 源,把 MCP server 暴露的能力注册为 skill
- 配置 MCP server(用户/管理员在设置里加 MCP server 地址)
- MCP skill 和内置 skill 统一调度(主 Agent / 子 Agent 不感知 skill 来源)
**与阶段 3 的关系**:阶段 3 定义"skill 是什么",阶段 4 定义"skill 从哪来"的一种标准途径。
**价值**:接入 MCP 生态,能力扩展从"自己写"变"接现成"。

### 阶段 5:多 Agent 协作(动态编排,需场景驱动)

**触发条件**:阶段 1-4 跑稳,**且出现真实场景需要"多个不同人格/工具集的 Agent 协作"**。
**范围**(待场景明确后细化):
- 子 Agent 从"固定注册"升级为"主 Agent 动态选择 + 组合"
- 多子 Agent 并行执行 + 结果聚合
- 子 Agent 间通信(一个子 Agent 派另一个)
**地位**:最不确定的一阶段。需真实场景驱动,不能为做而做。
**质疑保留**:个人助手(单一长期对话模型)是否真需要复杂多 Agent 编排?Dify/Coze 那类任务
自动化平台才是多 Agent 主战场。OmniBot 可能"固定子 Agent + 主 Agent 调度"就够了,
阶段 5 不一定启动。**先用阶段 1-4 的能力服务真实用户,看是否自然涌现编排需求**。

## 三、与产品愿景的对齐

产品愿景 v2.0 长期目标:
- ✅ 插件系统 -> 阶段 3 skill + 阶段 4 MCP
- ✅ 完善长期记忆系统 -> 独立线(高级记忆/向量召回,见路线图 v3.0)
- ◻ 多租户 -> 独立线(企业级,见路线图 v3.0)
- ✅ 开放 API -> 独立线(第三方集成,见路线图 v3.0)

本文档覆盖「插件系统」这条线的演进路径,其他线各自独立迭代。
**记忆线**与本文档正交(记忆是 Agent 的输入,Agent 框架是记忆的消费方),
可并行推进。

## 四、优先级总结

| 阶段 | 内容 | 优先级 | 触发条件 |
|------|------|--------|----------|
| 0 | v2.0 发布 | P0 | smoke 层 B 过 |
| 1 | 后台 Agent 框架 v1.0 | P0(下一迭代) | 方案已定,直接做 |
| 2 | 框架 v1.1(推送+恢复) | P1 | 阶段 1 跑稳 + 用户反馈 |
| 3 | skill 系统 | P1 | 阶段 1/2 验证派活可用 + 工具扩展瓶颈 |
| 4 | MCP 对接 | P2 | 阶段 3 稳定 + 需外部能力 |
| 5 | 多 Agent 协作 | P3(待定) | 真实场景涌现,否则不做 |

**核心原则**:
1. 基础设施优先(阶段 1 是所有后续的地基)
2. 每阶段靠真实场景触发,不超前建设(尤其阶段 5)
3. 框架设计预留扩展(阶段 1 的 A2A 语义/任务表/回执格式,后续阶段都不推翻)

## 五、待决策点(后续迭代时再定)

- 阶段 2 主动推送的通道:Web SSE 已有,飞书/微信客服消息需配额评估
- 阶段 3 skill 是否区分"系统 skill"和"用户 skill"(权限/可见性)
- 阶段 4 MCP server 的安全模型(执行外部代码的风险)
- 阶段 5 是否真的启动(强依赖真实场景验证)
