## 1. 问题与根因

**现象**：微信 ClawBot 里派出的后台任务，完成后汇报不会出现在微信。

**根因（两层）**：

1. **推送按渠道硬编码**（`sub_agent_service.go:484`）：
   `if task.Source != SourceFeishu { return }` —— `wechat_claw` 永远进不了推送分支。
   且 `TaskNotifier` 只有一个实现（绑定飞书 `LarkSender`），全局只有一个槽位。
2. **Web 端抢先消费**：微信任务失去推送后，只剩"下次发消息时前置汇报"兜底；
   但 Web 端轮询 `completed_unreported` 会调 `/report`，`SaveReportMessage` + `MarkReported`
   之后，微信侧兜底也查不到该任务 —— 汇报只存在于 Web。

**已有底座（本方案的基础）**：

- `SourceWeChatClaw = "wechat_claw"` 已定义；IM pipeline 已注入正确的 Source 与 NotifyTarget（ilink user id）。
- ClawBot 的 `Sender` 与飞书共用 `feishu.Sender` 接口，`Service.CurrentSender()` 可动态取当前连接。
- 转述逻辑（主 Agent 把回执写成自然语言）只存在于 `FeishuTaskNotifier`，需要抽出来复用。

## 2. 设计

### 2.1 N1：抽出 `ReportComposer`（共用「转述 + 落库」）

新增 `internal/service/agent/report_composer.go`：

```go
type ReportRunner interface { Run(ctx, userID, conv, ...LLMClient) (*AgentResult, error) }
type ReportContextSource interface { BuildContextMessages(ctx, userID, current) ([]llm.ChatMessage, error) }
type ReportMessageStore interface { SaveReportMessage(ctx, userID, taskID, turnID, content, segments, steps) error }

type ReportComposer struct { runner; contextSource; store; llm SubAgentLLMConfigProvider }

// Compose 组装汇报上下文(回执指令 + 对话历史 + 虚拟触发)并让主 Agent 转述。
func (c *ReportComposer) Compose(ctx, task) (content string, records []StepRecord, ok bool)

// Save 落 report 消息(Kind=report,关联 task_id,逻辑归属原始 Turn)。
func (c *ReportComposer) Save(ctx, task, content string, records []StepRecord) error
```

- 转述失败 / 空回复 → `ok=false`，由各渠道回落裸回执（消息必达，不落库）。
- `Save` 复用 `StepRecordsToAgentSteps`；`SaveReportMessage` 失败只记日志，不阻断推送。
- 顺带：把 `im.ToAgentMessages` 的实现下沉为 `agent.ChatMessagesToAgent`，im 版本委托调用（消除重复）。

### 2.2 N2：微信 ClawBot notifier

新增 `internal/channel/wechatclaw/task_notifier.go`：

```go
type TextSender interface { SendText(ctx, openID, content string) error }
type SenderProvider func() TextSender

type TaskNotifier struct { sender SenderProvider; composer *agentpkg.ReportComposer }
```

- 每次推送时动态取 sender（重扫/断线后自动跟随；未连接返回错误，记日志不阻断）。
- ClawBot 不支持卡片：标题 + 正文走 `SendText`，超长由现有 sender 自动分段。
- 转述失败回落 `BuildTaskReceipt` 裸回执。

### 2.3 N3：按来源分派

`SubAgentService`：

```go
notifiers map[string]TaskNotifier   // 受 RWMutex 保护
func (s *SubAgentService) SetNotifierForSource(source string, n TaskNotifier)
```

`notifyCompleted` 改为：

1. web → 实时事件（不变）；
2. 按 `task.Source` 查 notifier；无注册或 `NotifyTarget` 为空 → 返回（保留前置汇报兜底）；
3. 有 → 先 `MarkReported`（防 Web 抢跑），再推送。

装配（`routes.go`）：

- 飞书：`SetNotifierForSource(SourceFeishu, ...)`（原调用点改一行）
- 微信：`SetNotifierForSource(SourceWeChatClaw, wechatclaw.NewTaskNotifier(d.wechatClawSvc.CurrentSender, composer))`

## 3. 为什么不用其它做法

| 方案 | 否决理由 |
|------|----------|
| 只放开 source 判断、复用飞书 notifier | sender 绑的是飞书 SDK，会把消息发错通道或直接报错 |
| 微信侧直接推裸 artifact | 与飞书体验不一致（无自然语言转述、无 report 消息），且重复落库逻辑 |
| 在 Web 端判断"任务来源是微信就不消费" | 把渠道策略塞进 Web，且用户不开 Web 时仍然无推送 |

## 5. 兼容性

- 不改 DB、不改 API、不改前端。
- `TaskNotifier` 接口不变；`SetNotifier` 保留为「默认兜底注册」，新增 `SetNotifierForSource`。
- 飞书行为不变（同一转述逻辑，仅代码位置搬移）。

## 6. 风险

| 风险 | 应对 |
|------|------|
| 转述时主 Agent 调用失败 | 回落裸回执（既有策略不变） |
| 微信未连接时任务完成 | 记录错误日志，保留前置汇报兜底；重连后不影响后续任务 |
| 与 Web 抢跑 | 微信路径先 MarkReported 再推送；失败仍继续推送 |
| 并发写 notifiers | RWMutex 保护（启动期写、运行期读） |

### 7.2 与原方案的差异（2 处）

1. **增加 `Available()` 可选接口**（方案未写）：原方案在推送前统一 `MarkReported`，
   但微信断线时 notifier 必然失败，标记后兜底汇报也查不到。改为：渠道声明不可用 → 不标记、直接返回。
2. **`SetNotifier` 移除**，由 `SetNotifierForSource` 取代（方案里说"保留为默认兜底"，
   实现时发现"默认兜底"会让微信任务落到飞书 notifier 上，属危险行为，故不留）。

## 8. 补充：渠道归属收紧（同日，v2.10.2）

### 8.1 问题

N1~N3 让**推送**按来源分派了，但兜底路径仍会串台：

| 路径 | 原行为 |
|------|--------|
| IM 前置汇报 `GetPendingReportContext(userID)` | 不分来源：飞书任务能在微信里被补报 |
| Web 未汇报轮询 `GET /agent/tasks?status=completed_unreported` | 不分来源：Web 一开就抢报 IM 任务 |
| Web `POST /agent/tasks/:id/report` | 可对任意任务生成汇报并标记 reported |

### 8.2 改动

- 仓储：`ListCompletedUnreported(userID, source)` 增加 `source = ?`（接口签名变更，编译器强制每个调用方选来源）
- 服务：`GetCompletedUnreported(userID, source)`、`GetPendingReportContext(userID, source)`
- IM：传 `h.opts.Source`（飞书 `feishu` / 微信 `wechat_claw`，31 号共享 pipeline 自带）
- Web：未汇报轮询与聊天前置汇报都传 `SourceWeb`
- Web `/report`：非 web 来源直接 409「该任务的汇报归属来源渠道」

### 8.3 边界：展示 ≠ 消费

用户要求「Web 端要能看到所有」，因此严格区分两条路径：

| 路径 | 是否按来源过滤 | 说明 |
|------|----------------|------|
| 任务中心列表（`GET /agent/tasks` 无 status） | **否** | 显示全部渠道任务，含 artifact 全文 |
| 聊天历史 | **否** | IM 渠道推送时已落 `kind=report` 消息，Web 历史里照样能看到 |
| 未汇报轮询（自动生成汇报） | **是** | 这是"消费/推送"路径，只处理本渠道 |
| `/report` 手动生成 | **是** | 防止 Web 代 IM 生成汇报并掐掉来源渠道兜底 |

一句话：**看得见全部，但只替自己汇报。**

### 8.4 测试

- 仓储：混合来源下按 web/feishu 分别查询互不串台
- 服务：`GetPendingReportContext` 按来源返回（web/feishu/wechat_claw 三例）
- Web：未汇报轮询只返回 web 任务；任务中心仍返回全部 3 条；`/report` 对飞书任务 409 且不标记 reported
