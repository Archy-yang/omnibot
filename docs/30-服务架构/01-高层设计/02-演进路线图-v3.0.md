## 版本规划

核心思路：每个版本包含一个用户可见功能 + 必要的架构改进，避免长时间无产出。

---

### v1.5 — Agent 基本能力（1~2 周）

**目标**：让 OmniBot 具备 Agent 核心能力，支持多步推理和工具调用循环。

**用户可见**：
- LLM 能主动调用工具（Function Calling / Tool Use）
- 支持 ReAct 模式：思考 → 行动 → 观察 → 思考 的循环推理
- 复杂任务自动拆解为多步执行
- 对话中可观察 Agent 的思考过程（可选）

**架构改进**：
- 新增 `Agent` 抽象层：`Agent` 接口 + `ReActAgent` 实现
- 工具注册机制（`Tool` 接口 + `ToolRegistry`）
- 内置基础工具：记忆查询、对话历史搜索、计算器等
- Agent 执行结果通过现有 SSE 流式通道返回前端

**关键设计决策**（待讨论）：
- 工具调用走 OpenAI Function Calling 协议还是自定义格式？
- Agent 循环最大步数限制？
- 是否在微信端也暴露 Agent 能力，还是仅 Web 端？

#### v1.5.1（2026-06-16，已上线）

补丁迭代：
- Agent 接口适配用户自定义 LLM 配置，与普通聊天对齐
- 前端「思考模式」开关，用户手动切换 Agent / 普通流式

#### v1.5.2（2026-06-17，已上线）

基于《单一长期对话模型》决策对 v1.5.1 的修正：
- **Agent 真流式**：`/messages/agent/stream` 重构为 token 级流式（之前是同步跑完再
  整段吐），简单提问体验等同普通流式
- **默认全 Agent**：取消「思考模式」开关，所有对话默认走 Agent，是否调用工具由
  LLM 自动判断
- **SSE 协议升级**：`event: agent_step` → `event: token` / `event: tool_call`
- **工具状态条重设计**：折叠面板换成正文上方的行内状态条；`Tool` 加 `DisplayLabel`
  字段，5 个内置工具补中文友好文案
- **范围说明**：本次未改造微信端 Agent 化（涉及客服消息异步推送），保持原行为，
  作为独立小迭代后续完成

#### v1.5.3（2026-06-21，已上线）

基于《单一长期对话模型》对 Agent 展示体验的进一步打磨：
- **思考过程按真实时序交错**：回复中「文本 → 调工具 → 文本」按发生顺序交错渲染，
  前端消息模型从「content + toolCalls 两个桶」改为有序 `segments` 段落序列
- **点击思考条展开看结果**：放开此前被丢弃的 `tool_result` 事件，新增
  `event: tool_result` SSE 协议；展开区限高 240px 滚动
- **工具错误脱敏**：执行失败的结果统一脱敏为「工具执行失败」，不透传内部细节
  （`sanitizeToolResult`），符合安全红线
- **范围说明**：segments 仅本会话内存，不做历史持久化（刷新回退纯文本），历史
  持久化作为独立迭代后续做

#### v1.5.4（2026-06-21，已上线）

补齐 v1.5.3 的历史持久化短板：思考过程不再刷新即丢。

- **segments 落库**：Web Agent 流式回复的 segments（文本 + 工具调用 + 脱敏结果）随消息
  持久化，刷新后历史完整还原思考过程
- **存储方向确立**：采用「JSON 骨架 + 实体表」混合架构。`messages` 加 `segments` JSON 列
  存纯展示碎片，`content` 保留纯文本投影；未来 artifact / 生成文件 / 异步任务等一等实体
  走独立表，段落里放引用 id——届时不动 messages 结构，只多一种 segment type
- **与路线图的衔接**：异步任务表对应 v1.8「统一异步任务抽象」；artifact 等为 v2.x 储备
- **安全**：落库工具结果共用 `sanitizeToolResult` 脱敏，原始 error 不入库
- **范围**：仅 Web Agent 流式端点落库 segments；旧消息 / 非 agent 消息无 segments，前端
  纯文本回退，无需数据迁移；前端零改动（v1.5.3 渲染逻辑天然兼容）

> **混合存储架构备忘**（v1.5.4 确立，供后续迭代参考）：
> - **碎片层**（JSON `segments`）：text / tool / 未来的思考链、引用、内联图——整体读写、
>   有序、异构，加新类型零迁移
> - **实体层**（独立表 + 段落引用）：artifact（版本历史）、生成文件（可重复下载）、
>   异步任务（状态机、后台回填）——有独立身份和生命周期，被多轮引用 / 侧栏聚合

### v1.6 — 第三个入口：飞书/钉钉（1~2 周）

**目标**：接入第三个对话入口，验证平台架构的可扩展性。

**用户可见**：
- 飞书或钉钉机器人接入（二选一）
- 支持文本对话，复用所有核心能力（Agent、记忆、LLM 配置）

**架构改进**：
- 新入口只需实现 `MessageChannel` 接口 + 注册路由
- 目标：加新入口只改 < 10% 的代码

**验收标准**：
- 飞书/钉钉用户可以和机器人正常对话
- Agent 能力在第三个入口可用
- 长期记忆跨三个入口打通
- LLM 配置跨三个入口共享

---

### v1.7 — Web 长期记忆管理（1 周）

**目标**：补齐 Web 端长期记忆管理的缺失，让 Web 用户也能可视化地管理自己的长期记忆。

**用户可见**：
- Web 设置面板新增「长期记忆」Tab/区域
- 查看全部长期记忆列表
- 手动新增一条长期记忆（带字数限制和安全提醒）
- 一键清空全部长期记忆（带确认弹窗）

**架构改进**：
- 无新增架构改动，完全复用现有 `MemoryService`
- Web API 新增 `/api/v1/memories` 路由组（GET/POST/DELETE）
- 前端新增 `MemorySection` 组件 + `memoryStore` + `memoryService`

**PRD**：`docs/20-产品PRD/in_progress/Web端长期记忆管理PRD-v1.0.md` ✅
**实现计划**：`docs/superpowers/plans/2026-05-24-web-long-term-memory-management.md` ✅

---

### v1.8 — UserChannels 统一 + 架构还债（1~2 周）

**目标**：把 `WechatAccount` 重构为统一的 `UserChannel` 模型，为后续多入口扩展打基础。

**用户可见**：
- 完全无感知，所有功能和之前一模一样

**架构改进**：
- `WechatAccount` 表重构为 `UserChannels` 表（user_id + channel_type + channel_user_id）
- `UserService.GetOrCreateByChannel()` 接口统一（目前 Web 和 WeChat 走的是不同路径）
- WeChat Handler 解耦：去掉对微信 XML 回复格式的直接依赖
- 统一异步任务抽象（`Task` 接口 + `TaskRunner`）

**验收标准**：
- Web、微信、飞书/钉钉三个入口的所有现有功能不受影响
- `UserChannels` 模型支持未来加更多入口时只需注册新 channel type

---

### v1.9 — 跨通道记忆打通（1 周）

**目标**：验证 v1.8 的架构改进是否真的有效——同一用户在不同入口看到同一份长期记忆。

**用户可见**：
- 在任一入口添加的记忆，在其他入口都能看到
- 跨通道的对话历史共享

**架构改进**：
- 利用 v1.8 的 `UserChannels` 模型，确认跨通道用户识别正确
- 记忆查询统一走 `UserID`

**验收标准**：
- 同一用户通过各入口登录后，长期记忆列表完全一致
- 任一入口新增/清空记忆，其他入口可见

---

### v1.10 — 统一用户配置中心（1~2 周）

**目标**：Web 端设置面板从「能用」到「好用」，成为用户的统一配置入口。

**用户可见**：
- Web 设置面板整合：LLM 配置 + Agent 配置 + 长期记忆管理 + 通道绑定状态
- 查看自己绑定了哪些通道（微信、飞书/钉钉等）
- 对话历史查看（可选）

**架构改进**：
- 前端 SettingsPanel 组件拆分/重构，支持多 Tab 结构
- 后端「用户配置汇总」API：一次性返回 LLM 配置 + 记忆数量 + 绑定通道列表

### v2.0 — 正式发布（2 周）

**目标**：具备生产可用的完整能力，可以对外宣称「全平台智能助手」。

**用户可见**：
- 完整文档体系：部署文档、使用文档、API 文档

- v2.0 产品主页/介绍

**架构改进**：
- 监控、告警、错误降级完善
- 生产级稳定性验证
