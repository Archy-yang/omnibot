### v1.5 — Agent 基本能力（1~2 周）

**目标**：让 OmniBot 具备 Agent 核心能力，支持多步推理和工具调用循环。

**用户可见**：
- LLM 能主动调用工具（Function Calling / Tool Use）
- 支持 ReAct 模式：思考 → 行动 → 观察 → 思考 的循环推理
- 复杂任务自动拆解为多步执行
- 对话中可观察 Agent 的思考过程（可选）

**架构改进**：
- 新增 `Agent` 抽象层：`Agent` 接口 + `ReActAgent` 实现
- 工具注册机制（`Tool` 接口 + `ToolRegistry`）
- 内置基础工具：记忆查询、对话历史搜索、计算器等
- Agent 执行结果通过现有 SSE 流式通道返回前端

**关键设计决策**（待讨论）：
- 工具调用走 OpenAI Function Calling 协议还是自定义格式？
- Agent 循环最大步数限制？
- 是否在微信端也暴露 Agent 能力，还是仅 Web 端？

#### v1.5.1（2026-06-16，已上线）

补丁迭代：
- Agent 接口适配用户自定义 LLM 配置，与普通聊天对齐
- 前端「思考模式」开关，用户手动切换 Agent / 普通流式

#### v1.5.2（2026-06-17，已上线）

基于《单一长期对话模型》决策对 v1.5.1 的修正：
- **Agent 真流式**：`/messages/agent/stream` 重构为 token 级流式（之前是同步跑完再
  整段吐），简单提问体验等同普通流式
- **默认全 Agent**：取消「思考模式」开关，所有对话默认走 Agent，是否调用工具由
  LLM 自动判断
- **SSE 协议升级**：`event: agent_step` → `event: token` / `event: tool_call`
- **工具状态条重设计**：折叠面板换成正文上方的行内状态条；`Tool` 加 `DisplayLabel`
  字段，5 个内置工具补中文友好文案
- **范围说明**：本次未改造微信端 Agent 化（涉及客服消息异步推送），保持原行为，
  作为独立小迭代后续完成

#### v1.5.3（2026-06-21，已上线）

基于《单一长期对话模型》对 Agent 展示体验的进一步打磨：
- **思考过程按真实时序交错**：回复中「文本 → 调工具 → 文本」按发生顺序交错渲染，
  前端消息模型从「content + toolCalls 两个桶」改为有序 `segments` 段落序列
- **点击思考条展开看结果**：放开此前被丢弃的 `tool_result` 事件，新增
  `event: tool_result` SSE 协议；展开区限高 240px 滚动
- **工具错误脱敏**：执行失败的结果统一脱敏为「工具执行失败」，不透传内部细节
  （`sanitizeToolResult`），符合安全红线
- **范围说明**：segments 仅本会话内存，不做历史持久化（刷新回退纯文本），历史
  持久化作为独立迭代后续做

#### v1.5.4（2026-06-21，已上线）

补齐 v1.5.3 的历史持久化短板：思考过程不再刷新即丢。

- **segments 落库**：Web Agent 流式回复的 segments（文本 + 工具调用 + 脱敏结果）随消息
  持久化，刷新后历史完整还原思考过程
- **存储方向确立**：采用「JSON 骨架 + 实体表」混合架构。`messages` 加 `segments` JSON 列
  存纯展示碎片，`content` 保留纯文本投影；未来 artifact / 生成文件 / 异步任务等一等实体
  走独立表，段落里放引用 id——届时不动 messages 结构，只多一种 segment type
- **与路线图的衔接**：异步任务表对应 v1.8「统一异步任务抽象」；artifact 等为 v2.x 储备
- **安全**：落库工具结果共用 `sanitizeToolResult` 脱敏，原始 error 不入库
- **范围**：仅 Web Agent 流式端点落库 segments；旧消息 / 非 agent 消息无 segments，前端
  纯文本回退，无需数据迁移；前端零改动（v1.5.3 渲染逻辑天然兼容）

> **混合存储架构备忘**（v1.5.4 确立，供后续迭代参考）：
> - **碎片层**（JSON `segments`）：text / tool / 未来的思考链、引用、内联图——整体读写、
>   有序、异构，加新类型零迁移
> - **实体层**（独立表 + 段落引用）：artifact（版本历史）、生成文件（可重复下载）、
>   异步任务（状态机、后台回填）——有独立身份和生命周期，被多轮引用 / 侧栏聚合

#### v1.5.5（2026-06-21，已上线）

「实体层」的首次落地——Agent 运行链路记录（trace）：

- **`agent_steps` 独立表**：把一轮对话的完整执行链按顺序记下来——不只工具调用，连每次
  LLM 调用（发出的 messages、模型回复/决定调的工具、耗时、模型名）也记。一轮 ReAct 由
  有序步骤组成（llm_call / tool_call），`message_id + seq` 一句 SQL 还原完整时序
- **为什么记整条链**：只记工具是残缺的——看不到「模型为什么这么走、发了什么 prompt」。
  按模型调用链依次记录才能完整复盘
- **运行时与记录两条路分离**：运行时上下文由滑动窗口（最近10轮、纯文本）框住，工具结果是
  轮内消耗品、跨轮只留文本结论；`agent_steps` 纯离线，不进上下文、不影响模型看到什么、
  不影响上下文成本。所以记录表按「分析最好查」设计，放开手记全
- **展示/记录职责分离**：`segments.result` 脱敏展示，`agent_steps` tool 步骤 response 存
  完整原始（含真实错误）。曾考虑截断大结果省空间，但「记录+分析」要求完整数据，截断即
  自断后路——正解是两条路分离
- **衔接**：分析能力（按 kind/status/tool/耗时聚合、token 成本）对接 v1.8+；本次只保证
  数据落地可查。token 列留位本轮不填（将来加 `stream_options.include_usage`）
- **范围**：前端无改动（内部表）；仅 Web Agent 流式端点产生记录；AutoMigrate 自动建表

### v1.6 — 第三个入口:飞书(2026-06-22,已上线)

**目标**:接入第三个对话入口,验证平台架构的可扩展性。

**用户可见**:
- 飞书机器人单聊接入(长连接,无需公网回调地址)
- 复用 v1.5 全部 Agent 能力(工具调用 + 多步推理)、长期记忆、用户自定义 LLM 配置
- 跨入口 user_id 打通:同一用户在 Web 和飞书侧记忆/配置一致

**架构核心(本版关键决策)**:
- **底层只剩一个真实流式实现,同步 Run 是 RunStream 之上的聚合层**——流式/同步只是
  返回形式不同,数据存储与运行链路记录完全一致,记录逻辑只在 `RunStream` 单一来源,
  同步入口天然继承。这条架构定义把 v1.5.5 的「运行时与记录分离」推进一步:不仅记录
  不进运行时,**记录本身也只有一份产生路径**,堵死「同步/流式两条路径行为漂移」的口子。
- agent_steps 现在两条入口都落库——同步 `AgentService.Run` 通过聚合产出 `Records`,
  handler 转 `conversation.AgentStep` 走和流式 handler 同一个
  `SaveAssistantMessageWithSegments`。Web 同步端点和飞书都受益。

**架构改进**:
- 新增 `internal/channel/feishu/` 包(config / interfaces / handler / sender / channel)
- 新增 `agent.StepRecord` 中性记录类型 + `AgentResult.Records` 字段
- `pkg/config` 加 `FeishuConfig{AppID, AppSecret, Enabled}`
- routes.go 在 enabled 时启动飞书长连接 goroutine,enabled=false 不动其他入口(开发态友好)
- 加新入口的实际代码改动落在「< 10% 代码」目标内(主要是新增飞书包 + routes 一处注册,
  agent 包改动是顺带的架构提升,服务 v1.6 之后所有入口)

**验收标准**(已完成):
- 飞书 IM 单聊正常对话
- Agent 工具调用在飞书端可用,真实驱动 get_current_time / calculator / 不调工具三场景
- 长期记忆跨入口可见,LLM 配置跨入口共享
- enabled=false 时服务正常启动,飞书不连
- `go test ./... -count=1` 全绿;`go build ./...` 通过

### v1.9 — WeChat Handler XML 解耦(2026-06-24,已上线)

**目标**:把微信 XML 协议从 handler 业务逻辑里抽出去,让 wechat handler 与 web / feishu handler 结构对齐——三入口都遵循「业务出纯文本,通道层负责承载格式」的统一模式。

**背景与决策**:
- v1.6 飞书接入完成 + v1.8 UserChannels 统一之后,**三入口里唯独微信 handler 还在内联 XML 解析/序列化**——`buildResponse` 调用 11 处,XML 模板硬编码在 handler 业务函数里。
- 跨通道记忆验证拆出去:v1.8 完成后,所有入口共用 `user_channels.user_id`,记忆已在统一 `MemoryService` 上跨入口共享——**功能已具备,无需独立验证迭代**;真实运营 e2e 留 v1.10+/v2.0。
- 范围**精准缩到「XML 解耦」一件事**,不夹带 MessageChannel 接口扩展、跨通道 e2e 测试。

**用户可见**:无,所有微信外部协议(签名、XML in/out)不变。

**架构改进**:
- 新增 `internal/channel/wechat/types.go`:`InboundMessage` 中性 struct(handler 业务路径只看这个,不感知 XML)+ `Parse(body []byte) (*InboundMessage, error)` 函数
- 新增 `internal/channel/wechat/types_test.go`:5 个 Parse 解析单测(text / image / event / invalid xml / empty body)
- `internal/channel/wechat/channel.go`:`Channel` 改为纯无状态,`BuildResponseXML(toOpenID, fromGhID, content)` 改为纯函数(三参,toUserName 从入站请求 ToUserName 字段拿,不再持字段),删除 `SetToUserName` / `NewChannel` 构造参数
- `internal/api/wechat/handler.go`:
  - 删除内联的 `Message` struct 和 `parseMessage` / `buildResponse` 函数
  - Handler 持 `wechatChannel *channelwechat.Channel`(routes.go 装配时通过 optional service 注入)
  - HandleMessage 顶层:`channelwechat.Parse(body)` → 中性 InboundMessage → dispatch → `wechatChannel.BuildResponseXML(...)` 包装
  - 所有 dispatch 函数签名改为 `(in *channelwechat.InboundMessage) (string, error)`,返回纯文本;`""` 表示「不回复」(unsubscribe / view 事件)
- `internal/api/routes.go`:`channelfactory.Register(channelwechat.NewChannel())`(对齐 web channel);wechat handler 装配时注入 channel 实例

**验收标准(已完成)**:
- `go test ./... -count=1` 全绿(含 5 个新 Parse 测 + 现有 9+ 个 HTTP 端到端测)✅
- `go build ./...` 通过 ✅
- `grep -E "xml|XML|CDATA" internal/api/wechat/handler.go` 仅余顶层 HTTP 响应 `c.Header("Content-Type", "application/xml")` 一处和注释 ✅
- 微信回调外部协议无变化(签名校验 / XML in / XML out) ✅

**关键设计决策**:
- `channelwechat.Channel` 改为无状态(删除 `toUserName` 字段):公众号微信号是请求自带的(入站 XML 的 `<ToUserName>`),响应时从入站请求里取即可,不需要 channel 预存。这也避免了多公众号场景下的 `SetToUserName` 切换状态。

**留给后续迭代**:
- `MessageChannel` 接口扩展(目前 `BuildResponseXML` 是 wechat 特有,不进通用接口)→ 若 v2.0+ 多通道协议适配统一时再考虑
- 真实公网回调 e2e smoke → 留待生产部署时

### v1.10 — Web 设置面板 Tab 化重构(2026-06-24,已上线)

**目标**:Web 端设置面板从「能用」到「好用」,把堆在 500px 单层 modal 里的内容分类成 Tab,并为后续扩展(配置中心/账户体系)打好结构。

**背景与决策**:
- v1.7(已在 v1.3 完成)以来,设置面板平铺了主题 + LLM 配置 + 长期记忆管理三块内容,接近视觉密度上限,加新内容必须换结构。
- 原 v1.10 设想里的「通道绑定状态」展示有产品本质问题:`UserChannels` 是单向身份解析(入口 → user_id),Web 用户和他自己的微信用户是两个独立 user_id,展示「绑定了 1 个通道 = web」无价值。**跨入口主动绑定**需要验证码/账户体系一起做,**留 v2.x 账户体系**。
- 原 v1.10 设想里的「用户配置汇总」单端点 API 不需要:LLM 配置 / 记忆都是按需独立加载,前端已经足够好,合并成单端点是过度设计。
- 范围**精准缩到「Tab 重构 + 关于页」**,几天工作量,作为 v2.0 发布前的最后一次可见迭代。

**用户可见**:
- 设置面板从单层平铺改为 3 Tab(模型 / 记忆 / 关于),modal 宽 500 → 640px
- 「关于」Tab 新增:版本号 / 应用标语 / 主题切换(从 LLM 区域挪过来) / 三入口接入状态卡片 / 源码仓库链接
- 底部按钮上下文化:模型 Tab 显示「保存/取消」,记忆和关于 Tab 显示「关闭」(因为记忆是即时保存,关于是只读)
- 切 Tab 不丢未保存的 LLM 改动(本地 ref 自然保留)
- 每次打开面板默认进模型 Tab,避免上次停留在「关于」造成困惑

**架构改进**:
- 纯前端改造,后端零改动
- 新增 `frontend/src/constants/about.ts`:版本号 / 应用名 / 标语 / 三入口接入状态常量 / 源码链接(纯静态数据,不向后端要)
- `SettingsPanel.vue` 内嵌 NTabs + 三个 NTabPane;`activeTab` ref 驱动底部按钮上下文化显示

**验收标准(已完成)**:
- `npm run build` 通过(含 vue-tsc 类型检查) ✅
- TypeScript 严格类型,无 any ✅
- 三个 Tab 切换 / 各 Tab 业务能力(LLM 保存、记忆 CRUD、主题切换)行为不变 ✅
- 后端代码、API、数据库无任何变化 ✅

**留给后续迭代**:
- 跨入口主动绑定流程(生成验证码 → 微信/飞书端发码 → 合并 user_id)→ v2.x 账户体系
- 对话历史查看页面(本次决策为「Tab 重构」方向,不走历史页方向)→ v2.x+
