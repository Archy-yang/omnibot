## 1. 方案概述

把 Web 端身份从「localStorage 匿名 session」升级为「邮箱密码真实账号」。

核心三件事:
1. **新增邮箱身份**:复用 UserChannels(`channel_type="email"`)+ 新增 `user_credentials` 表存密码哈希(方案甲)
2. **JWT 登录态**:注册/登录签发 JWT;新增 JWT 鉴权中间件,解析 `user_id` 注入 `gin.Context`
3. **Web 身份解析迁移**:13 处 `GetOrCreateByChannel("web", sessionID)` 改为从 `gin.Context` 取中间件注入的 `user_id`

技术选型(已确认):
- JWT:`github.com/golang-jwt/jwt/v5`(新增依赖)
- 密码哈希:`golang.org/x/crypto/bcrypt`(go.mod 已有,无需新增)
- 身份传递:JWT 中间件 → `gin.Context` → handler

## 2. 身份模型设计(方案甲落地)

### 2.1 整体关系

```
users (1) ──< user_channels (N)     channel_type ∈ {email, wechat, feishu}
  │
  └──(1:1)── user_credentials        仅 email 账号有,存密码哈希
```

- 注册邮箱账号 = 建 1 条 `users` + 1 条 `user_channels(email)` + 1 条 `user_credentials`
- 邮箱作为一个 channel,与 wechat/feishu 在身份层完全对称,v2.2 飞书绑定零阻力

### 2.2 user_channels(复用,不改表结构)

邮箱账号写入一条:

| 字段 | 值 |
|------|-----|
| `channel_type` | `"email"` |
| `channel_user_id` | 邮箱地址(小写归一化后) |
| `user_id` | 关联用户 |

现有唯一索引 `(channel_type, channel_user_id)` 天然保证**同一邮箱不重复注册**——
归一化为小写后,`Foo@X.com` 与 `foo@x.com` 落到同一 `channel_user_id`,索引冲突即拒绝。

### 2.3 user_credentials(新增表)

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `id` | bigint | PK, auto | |
| `user_id` | bigint | unique, not null, index | 关联 users.id,一对一 |
| `password_hash` | varchar(255) | not null | bcrypt 哈希(含 salt) |
| `created_at` | timestamptz | not null | |
| `updated_at` | timestamptz | not null | |

- 领域模型:`internal/domain/user/credential.go`,`UserCredential` 结构 + `TableName()`
- **密码明文绝不落库、绝不进日志**(安全红线)
- 为什么独立表而非塞 users:认证数据与身份映射解耦;users 保持极简(见 user-service.md 设计哲学)

### 2.4 AutoMigrate

`internal/db/database.go` 的 AutoMigrate 增加 `&user.UserCredential{}`。

## 3. 分层落点

严格遵守 API → Service → Repository → Domain。

| 层 | 新增/改动 | 文件(建议) |
|----|----------|-------------|
| Domain | `UserCredential` 实体 | `internal/domain/user/credential.go` |
| Repository | 凭证仓储(Create/GetByUserID/Update) | `internal/repository/user/credential_repo.go` |
| Service | AuthService:Register/Login;复用 UserService + 新 CredentialRepo | `internal/service/user/auth_service.go` |
| Pkg | JWT 签发/校验工具 | `internal/pkg/auth/jwt.go` |
| Middleware | JWT 鉴权中间件 | `internal/middleware/auth.go` |
| API | 注册/登录 handler | `internal/api/web/auth_handler.go`(或并入现有 web handler) |
| API | 13 处 handler 身份解析迁移 | `internal/api/web/handler.go` |

### 3.1 AuthService 职责

```
Register(email, password) → (token, error)
  1. 归一化邮箱(trim + 小写)、校验格式与密码长度(8~64)
  2. 事务内:
     a. 创建 users
     b. 创建 user_channels(email)  ← 唯一索引兜底重复
     c. bcrypt 哈希 → 创建 user_credentials
  3. 签发 JWT 返回

Login(email, password) → (token, error)
  1. 归一化邮箱 → 查 user_channels(email) → user_id
  2. 查 user_credentials → bcrypt.CompareHashAndPassword
  3. 校验 users.status 正常
  4. 签发 JWT 返回
  失败统一返回「邮箱或密码错误」(不区分,防枚举)
```

- AuthService 依赖:`UserRepository`、`UserChannelRepository`、`CredentialRepository`、JWT 工具
- 事务:注册的三步写入用 GORM 事务包裹,任一步失败整体回滚(PRD 7.3「不产生半个账号」)

### 3.2 JWT 工具(internal/pkg/auth)

```
GenerateToken(userID int64) (string, error)   // 签发,含 user_id + exp(30天) + iat
ParseToken(token string) (userID int64, err error)  // 验签 + 验过期 → user_id
```

- 算法:HS256(对称,单服务足够)
- 密钥:从 config 读 `auth.jwt_secret`,不硬编码
- 有效期:30 天(PRD 4.3),从 config 读 `auth.token_ttl` 或常量

## 4. JWT 鉴权中间件

`internal/middleware/auth.go`:

```
AuthRequired(jwtSecret) gin.HandlerFunc:
  1. 取 Authorization: Bearer <token>
  2. 无 token / 格式错 → 401
  3. ParseToken 失败(验签/过期)→ 401
  4. 成功 → c.Set("user_id", userID) → c.Next()
```

- 注册顺序:在 `CORS / Logger / Recovery` 之后,**按路由组**应用(不是全局)——
  注册/登录接口不挂此中间件,业务接口挂
- 401 响应体保持与现有错误格式一致(前端 `request.ts` 已处理 401 跳 `/login`)

## 5. 路由调整(routes.go)

### 5.1 新增鉴权接口(不挂 AuthRequired)

```
authGroup := r.Group("/api/v1/auth")
authGroup.POST("/register", webHandler.HandleRegister)
authGroup.POST("/login",    webHandler.HandleLogin)
```

### 5.2 业务接口挂中间件

现有 `/api/v1/chat`、`/api/v1/memories`、`/api/v1/user` 三个组,统一加
`.Use(middleware.AuthRequired(cfg.Auth.JWTSecret))`。

> `/api/v1/health`、`/metrics`、`/config`(admin)是否鉴权:本期保持不变(不挂),
> 它们不涉及用户身份。

### 5.3 依赖装配

`SetupRouter` 内新增:CredentialRepository、AuthService 的初始化,注入 webHandler。

## 6. Web Handler 身份解析迁移(改动主体)

### 6.1 现状 → 目标

**现状**(13 处):
```go
user, _, _, err := h.userService.GetOrCreateByChannel("web", req.SessionID)
```

**目标**:
```go
userID := c.GetInt64("user_id")   // 中间件已注入
// 直接用 userID,不再 GetOrCreate,不再依赖 session_id
```

### 6.2 改动清单

- 13 处调用点(handler.go: 155/230/316/418/516/783/825/873/918/972/1094/1151/1199)
- 各请求结构体删除 `SessionID string` 字段(及 `binding:"required"`)
- handler 改为从 `c.GetInt64("user_id")` 取身份
- `GetOrCreateByChannel` 方法**保留**(wechat/feishu 仍用),仅 web 不再调用它做匿名建号

### 6.3 注意

- `HandleGetHistory` 等 GET 接口原来从 query 取 session_id,一并改为 context 取 user_id
- SSE 流式接口(agent/stream)同样改造,注意 SSE 的鉴权也走同一个中间件(EventSource
  默认不带自定义 header — 见 8.1 风险)

## 8. 前端

### 8.1 鉴权管道(已就绪 + 待补)

- ✅ `request.ts`(axios 实例)已实现:请求注入 `Authorization: Bearer <localStorage.token>`、401 跳 `/login`
- 待补:`/login`、`/register` 路由 + 页面;路由守卫(无 token → `/login`)

**流式接口鉴权**:现状流式对话(`chat/messages/agent/stream`)用的是**裸 `fetch` +
ReadableStream**(`services/chat.ts`),**不是 EventSource**。fetch 支持任意 header,
因此鉴权无障碍——不需要改传输方式,也不存在 EventSource 带不了 header 的问题。

需做三处小改:
1. fetch 的 `headers` 加 `Authorization: Bearer ${localStorage.token}`
2. 请求 `body` 去掉 `session_id`(配合后端 6.2 身份迁移)
3. 手动处理 `response.status === 401` → 清 token 跳 `/login`(裸 fetch 不经 axios 拦截器,
   需在此单独补一次,与 axios 拦截器行为对齐)

### 8.2 页面与守卫

- `views/LoginPage.vue`、`views/RegisterPage.vue`
- `router/index.ts`:加 `/login`、`/register` 路由;`beforeEach` 守卫:无 token 且访问受保护页 → `/login`;有 token 访问 `/login|/register` → `/`
- auth 状态:复用或新建 store 管理 token + 当前用户(技术评审定;倾向新建 `stores/auth.ts`)
- 各业务请求不再传 session_id(配合后端 6.2)

## 9. 开发顺序(TDD)

按依赖自底向上,每步红绿:

1. **Domain + Repository**:`UserCredential` 实体 + credential_repo(CRUD)+ 单测
2. **JWT 工具**:`pkg/auth/jwt.go` GenerateToken/ParseToken + 单测(签发→解析往返、过期、篡改)
3. **AuthService**:Register/Login + 单测(成功、重复邮箱、错误密码、归一化、事务回滚、状态校验)
4. **JWT 中间件**:AuthRequired + 单测(无 token/过期/篡改 → 401;有效 → 注入 user_id)
5. **Auth handler**:HandleRegister/HandleLogin + handler 测试
6. **routes 装配** + 业务接口挂中间件
7. **13 处 handler 迁移**:session_id → context user_id(逐个改,跑回归)
8. **config**:AuthConfig + example
9. **前端**:登录/注册页 + 路由守卫 + 流式接口补 Authorization header / 去 session_id / 401 处理(8.1)
10. **清库** + 全量回归 + 手测

## 10. 安全要点(对齐安全红线)

- 密码 bcrypt 哈希(默认 cost),明文不落库、不进日志
- 登录失败统一「邮箱或密码错误」,不区分邮箱是否存在(防枚举)
- JWT secret 从 config 读,不硬编码、不入 git
- 日志不输出密码、不输出完整 token
- 邮箱在日志中按需脱敏
- 注册三步写入事务化,失败回滚

## 11. 设计决策记录

### 决策1:为什么邮箱复用 UserChannels 而非 users 加字段?
保持 UserChannels 作为唯一身份解析模型。邮箱、微信、飞书在身份层对称,v2.2 飞书绑定
就是"给同一 user_id 加一条 channel",逻辑统一。users 保持极简(见 user-service.md)。

### 决策2:为什么密码单独存 user_credentials 而非放 user_channels?
user_channels 是身份映射表,语义是"哪个外部身份对应哪个 user"。密码是认证凭据,
与映射解耦更清晰;且未来改密码/找回只动 credentials,不碰身份表。

### 决策3:为什么 JWT 而非 server session?
与现有"无服务器端 session 状态"的风格一致(现在就是无状态的 session_id)。JWT 无需
session 存储(内存/Redis),部署简单。代价是无法主动吊销 —— 本期可接受(过期重登)。

### 决策4:为什么中间件按路由组挂而非全局?
注册/登录接口本身不能要求已登录;health/metrics/config 不涉及用户身份。按组挂更精确。

### 决策5:GetOrCreateByChannel 为什么保留?
微信、飞书仍用它做身份解析(飞书的建号行为变更在 v2.2 处理)。本期仅 Web 入口
停止用它做匿名建号。
