# 架构演进路线图 v2.0

本文档描述从 v1.x 单入口微信机器人，演进到 v2.0 全平台智能助手的路径。

---

## 演进总览

```
v1.2 (当前)                    v2.0 (目标)
┌───────────────┐          ┌───────────────────────┐
│  微信入口     │          │   统一对话核心        │
│  (硬编码)     │          │   (记忆 + 对话 + 配置)│
└───────┬───────┘          └───────┬───────┬───────┘
        │                          │       │
┌───────▼───────┐          ┌───────▼───┐ ┌─▼───────┐
│  业务逻辑     │          │  微信入口  │ │ Web入口 │
└───────────────┘          └───────────┘ └─────────┘
                                  │
                            ┌─────▼──────┐
                            │ 飞书/钉钉..│
                            └────────────┘
```

## 阶段一：架构准备（v1.3，2~3周）

### 目标
不改变任何用户可见功能，只调整代码结构，为多入口做准备。

### 核心工作

| 工作项 | 说明 | 验收标准 |
|--------|------|---------|
| **抽象 MessageChannel 接口** | 定义统一的消息发送接口，把微信 XML 回复逻辑包装成实现 | 加新入口不需要改任何 Service 层代码 |
| **重构用户通道关联** | 把 `WechatAccount` 表重构为 `UserChannels` 表，支持多通道身份关联 | 同一个 UserID 可以绑定多个不同通道的身份 |
| **统一异步任务抽象** | 把消息处理流程从"同步调用LLM直接返回"改成"任务+状态机"模式 | 核心逻辑不依赖微信 5 秒超时限制 |

### 用户影响
完全无感知，所有功能和之前一模一样。

### 在 v2.0 路线图中的位置
这是整个平台化的基础，也是唯一"只改代码不加功能"的迭代。做完这一步，后续加任何新入口的成本都会非常低。

---

## 阶段二：第二个入口验证（v1.4，3~4周）

### 目标
证明平台架构真的能用，验证"加一个新入口只需要写 Handler"的假设。

### 核心工作

| 工作项 | 说明 | 验收标准 |
|--------|------|---------|
| **Web 对话页面开发** | 实现基础的 Web 端对话界面，支持登录、发消息、看历史 | 浏览器里可以正常和机器人对话 |
| **记忆跨通道打通** | 同一个用户在微信和 Web 里的对话历史是打通的，两边都能看到完整上下文 | 在微信说"我叫张三"，Web 里机器人知道我叫张三 |
| **Web 端配置页面** | 在 Web 端可以配置 LLM API Key、模型参数等 | 配置在两边通用 |

### 用户影响
- 微信用户：完全无感知
- 新增：Web 端用户可以使用

### 在 v2.0 路线图中的位置
这是架构的"验证点"——如果加 Web 入口只改了 10% 的代码，说明平台化抽象是成功的；如果改了超过 30%，说明抽象有问题，需要回头调整。

---

## 阶段三：平台能力完善（v1.5 ~ v1.6，1~2个月）

### 目标
把"多入口"从"能用"做到"好用"，完善平台级能力。

### 核心工作

| 工作项 | 说明 | 验收标准 |
|--------|------|---------|
| **统一用户配置中心** | Web 端完整的配置界面：查看记忆、管理配置、绑定多个通道 | 用户可以自己管理所有数据 |
| **异步策略矩阵** | 每个通道可以有自己的异步回复策略：<br>- 服务号：客服消息推送<br>- 订阅号：超时降级 + 重试拾取<br>- Web：WebSocket 流式推送 | 每个通道都能发挥自己的最大能力 |
| **第三个入口支持** | 飞书或钉钉二选一，接入第三个对话入口 | 证明平台架构可以轻松扩展 |
| **统一管理后台** | 管理员可以查看所有用户、通道、对话统计 | 有基本的运维能力 |

### 用户影响
- 功能越来越丰富，体验持续提升
- 开始支持企业级场景

---

## 阶段四：v2.0 正式发布（v2.0，1个月）

### 目标
可以对外宣称是"全平台智能助手"了，具备生产可用的完整能力。

### 核心工作

| 工作项 | 说明 | 验收标准 |
|--------|------|---------|
| **完整文档体系** | 部署文档、使用文档、API 文档、二次开发文档 | 新人可以照着文档 30 分钟内部署完成 |
| **官方 Demo 站** | 公开的 Demo 网站，用户可以直接体验，不用先关注公众号 | 任何人都能马上体验产品 |
| **v2.0 产品介绍** | 产品主页、功能介绍、使用场景说明 | 可以对外宣传了 |
| **生产级稳定性** | 完善的监控、告警、错误降级 | 可以支撑真实用户量 |

## 后续：v2.x 增强功能

v2.0 发布之后的可选方向，根据实际需求选择优先级：

| 方向 | 说明 |
|------|------|
| **插件系统** | 支持工具调用、第三方插件，让智能助手可以做事 |
| **多租户支持** | 支持企业级隔离、权限管理、配额控制 |
| **开放 API** | 提供 REST API，第三方可以基于平台开发自己的应用 |
| **更多入口** | 支持 Telegram、Discord、企业微信、Slack 等 |
| **高级记忆** | 记忆总结、记忆分类、重要记忆置顶等增强功能 |

## 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|---------|
| 阶段一的抽象过度设计，反而增加复杂度 | 中 | 严格控制范围，只抽象必须的部分，不过度设计 |
| 阶段二发现抽象有问题，需要大改 | 中 | 阶段二做完就回头评估，不行就及时调整，不要硬往下走 |
| 多入口导致测试复杂度飙升 | 中 | 从 v1.3 开始引入自动化测试，每个入口都有独立的测试套件 |
| 战线拉太长，用户看不到进展 | 低 | 保持每个迭代 2~3 周就发版，每个版本都有可见的改进 |
