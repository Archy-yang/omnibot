# 29 - 管家深化技术方案：目标推进、对话建档与反馈闭环

> **文档版本**:v1.0(2026-10-23 立项)
> **前置**:20号路线图四阶段收官(v2.5.0)后的深化阶段;26号主动管家/28号目标闭环的直接延伸
> **决策**:A+B+C+D 四项全做(用户 2026-10-23 拍板);A 走**建议式**(与 close_suggest 同红线);
> C v1 只做 negative 抑制、冷却 30 天固定参数

---

## 1. 背景与定位

28号 收官后,管家闭环仍剩三个缺口:

| 缺口 | 现状 | 根因 |
|------|------|------|
| 目标只有「提醒」没有「推进」 | 临近/过期时管家只会说"快到期了"(28号 N2 信号行) | 派活的**裁决出口**缺失——对话内派活工具早已有(delegate/persistent_task),但裁决不知道该用它 |
| 目标旅程第一公里断裂 | 「我要在月底前完成体检」若无档案,只能提示"先聊聊让管家建档" | 28号 §5 边界:对话内建 matter 不在 v1 |
| 主动送达是单向广播 | 用户觉得有用/没用没有回流,重复打扰只能等 7 天冷却自然过期 | `proactive_notes.feedback` 列 26号 留好后一直没消费方 |

定位:**不新建实体、不新建机制**,复用 28号 工具面 + 26号 裁决面/冷却池;唯一的新机制是 C 的 feedback 写入与消费。

## 2. 设计原则

1. **建议式不动手**:派活与收口同一红线——系统只建议,用户确认才执行;严禁系统侧自动创建任务。
2. **负反馈优先**:v1 只做 negative 抑制,不做 positive 加权——正反馈通胀会让裁决越来越啰嗦。
3. **幂等友好**:`create_matter` 同名回落既有档案,重复立目标不产生重复档案。
4. **共享克制基建**:goal_nudge 与 close_suggest 一样占「今天唯一一件事」名额,同一冷却池。

## 3. 机制设计

### 3.1 D 目标清除(顺手项,N1 先做)

- `manage_matter set_target` 的 `target_date` 支持**留空或传 `clear`** → `UpdateTarget(nil)` 清除
- 返回文案「已清除 XX 的目标日」
- repo 层 `UpdateTarget(nil)` 28号 N2 已落地(typed-nil 归一已锁注释),本项纯工具参数面

### 3.2 B 对话内建档(create_matter)

| 参数 | 必填 | 说明 |
|------|------|------|
| `title` | ✅ | 档案标题(唯一键) |
| `state_desc` | — | 当前状态一句话,缺省空(沉淀管线后续补) |
| `target_date` | — | YYYY-MM-DD,顺手挂目标(等价 create + set_target 一步到位) |

- **幂等回落注意**:`UpsertByTitle` 是沉淀管线语义(冲突时**覆盖** StateDesc/Status/Embedding,
  M6.2 向量换新),**不能直接复用**——service 层先 `GetByTitle` 判存:已存在 → 不写库,
  返回既有 matter_id 与幂等提示(「已有档案『XX』,直接在它上面继续」);未命中才创建
  (repo 补一个纯 `Create`,或落 `UpsertByTitle` 未命中分支,落地时定)
- 28号 `manage_matter set_target` 无档案时的引导语升级:从「先聊聊让管家建档」改为「我可以直接给你建一个,要吗?」
- **红线注释同 manage_matter**:仅对话内由用户确认触发;沉淀管线(digest_reconcile)照旧自治,工具建档只承接用户显式意志

### 3.3 A goal_nudge 目标推进建议(裁决扩展,零增量调用)

`adjudicationSystemPrompt` 输出空间扩第 5 个 kind:

```
goal_nudge  // 目标临近/过期未推进,给具体可执行的推进建议(派活需用户确认)
```

- **触发条件**(裁决指令):目标 matter 剩 ≤3 天或已过期、状态仍 active、时间线表明无实质推进
  → 优先给 `goal_nudge` 而非重复提醒;建议内容必须具体可执行(「要我派个活去查附近的体检机构吗?」),
  禁止空泛的"注意进度"
- **执行路径**:送达 → 用户回复确认 → 主 Agent 走**既有派活工具**(delegate / persistent_task),
  产出按 25号 链路汇报——系统侧零新代码,派活行为天然带用户确认
- dedup_key 加 `:goal` 后缀(`matter:10:goal`),与普通提醒/close_suggest 同一 7 天冷却池;
  `matterIDFromKey` 兼容 `:goal` 后缀(28号 已兼容 `:close`,同构扩展)
- **半自动派活明确挂起**:过期 N 天自动 StartTask(source=butler)不做——等 C 的 feedback
  数据攒够,能度量打扰成本后再评估(§5)

### 3.4 C feedback 反馈闭环(两段走)

**写入口(Web 先行,N3;飞书卡片,N4)**:

- Web:proactive-notes 列表项加 👍/👎,`PUT /api/v1/proactive-notes/:id/feedback`
  (body:`{"feedback":"positive|negative|clear"}`;clear=撤销反馈)
- 飞书:送达卡片加「有用/没用」按钮 → 卡片回调路由 → 写同一 service(Web/飞书同一存储,
  同一条 note 两端都能改)
- 单条覆盖写(可改主意);归属隔离同既有 notes 查询语义

**消费面(v1 最小)**:

- **negative → 冷却延长**:信号键冷却判断从固定 7 天改为——该 dedup_key 最近一条
  note 的 feedback 为 negative → 冷却窗 **30 天**,否则 7 天;同一件事反复打扰的根治
- **positive 不改变任何行为**(v1,防正反馈通胀);数据先积累,后续观察期再定用途

## 4. 数据迁移

**零迁移**——`proactive_notes.feedback` 列 26号 建表已留(positive/negative,空=未反馈),
无新表新列。

## 5. 边界与不做

- **半自动/自动派活不做**(source=butler 自动 StartTask):等 feedback 数据支撑成本度量
- **positive 加权、反馈学习不做**:裁决 prompt 不按反馈自调优,先攒数据
- **feedback 自由文本评论不做**:只有 👍/👎 两个动作
- **create_matter 不做**批量建档、不做既有档案合并/改名(21号:title 不可改边界不变)
- **N3 只做 Web 反馈面**,飞书卡片独立 N4(卡片回调是新风险面,独立回归)

## 6. 风险

| 风险 | 处置 |
|------|------|
| 裁决空间 5 kind 复杂化拖累裁决质量 | 金样本断言扩 goal_nudge 场景;上线后复盘首周裁决记录(26/28号 同款纪律) |
| goal_nudge 骚扰 | 共享日限+冷却;`:goal` 后缀独立键,与 `:close` 互不挤占 |
| create_matter 造重复/垃圾档案 | GetByTitle 判存幂等回落(勿直用 UpsertByTitle——沉淀管线覆盖语义);建档仅用户显式对话意志 |
| 飞书卡片回调安全/复杂度 | 独立 N4 里程碑;复用既有 lark 长连接回调链路,失败仅记日志不阻塞送达主链路 |

## 7. 里程碑

| 里程碑 | 内容 | 交付物 |
|--------|------|--------|
| N1 | D 目标清除 + B create_matter 工具 | §3.1~3.2 + 测试(纯工具面,小) |
| N2 | A goal_nudge 裁决扩展 | §3.3 + 测试(薄,28号 N1 同构) |
| N3 | C Web 反馈面 + negative 冷却消费 | §3.4 + 测试(新 API 面) |
| N4 | C 飞书卡片交互按钮 | §3.4 + 回调路由(独立风险面) |

## 8. 测试计划

1. 工具:set_target clear 各态;create_matter 新建/幂等回落/target_date 顺手挂/归属隔离
2. 裁决:goal_nudge 解析/dedup_key `:goal` 后缀/matterIDFromKey 兼容/缺字段沉默(26号同款纪律)
3. feedback:写入三态(positive/negative/clear)/覆盖写/归属隔离;冷却判断 negative→30 天、无反馈→7 天
4. 红线:goal_nudge 全链路无任何自动任务创建;create_matter 仅对话工具可达,系统侧无调用点
