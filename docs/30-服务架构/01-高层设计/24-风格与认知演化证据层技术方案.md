# 24 - Style/Context Evolution 证据层技术方案：风格画像与认知变化

> 2026-10-14 立项。目标：让管家**积累**对用户沟通风格与偏好变化的长期证据（20 号 §7 演化稳定
> 要求：基于长期证据缓慢更新，不自我强化、不突变）。
> **本方案只做证据层 + 用户确认后的参考注入；自动演化机制明确不做**（外部建议与 20 号路线图一致：
> 第一轮不实现自动演化）。

## 1. 这个文档解决什么问题？

1. **风格无证据**：当前表达方式是写死的通用管家 persona（`MainResponseStylePrompt`）+ 手填
   persona_hint；用户长期相处形成的真实偏好（称呼习惯、长度偏好、正式度、幽默感）没有任何积累。
2. **认知变化无轨迹**：记忆冲突更新会覆写旧认知（M6），但"用户**为什么/何时**改变想法"这一层
   叙事没有记录——回答"上次为什么这么决定"缺关键素材。
3. **注入无通道**：即便有画像，现在的全局 prompt 也注入不了按用户的内容。

### 1.1 关键设计决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 抽取挂载点 | **沉淀管线顺带抽取**（digest 输出增加 `style_notes`/`preference_changes` 两段） | 复用区间/水位/溯源/LLM 调用,零新基建;风格信号本就该在真实对话里观察 |
| 抽取频率控制 | 常态空数组:LLM 仅在出现**明显风格信号**时输出,单轮上限 3 条 | 防噪声刷屏;风格是慢变量 |
| 证据溯源 | 两表各存 `source_message_ids`(JSON 数组) | 展示"依据哪段对话";量级小,不建独立多对多表 |
| 注入闸门 | **默认关闭**;用户在设置里显式开启后才注入,单条证据可删,关闭即回到通用 persona | 20 号红线:风格/画像严禁自动注入 prompt,必须显式确认机制 |
| 注入通道 | **per-user prompt 装配**(M2):`RunStream` 已有 userID,prompt 改为 `promptFor(userID)` = 全局基座 + 按用户风格段;风格段缓存随开关/新证据失效重建 | 复用 skill_catalog 的重建先例;基座不变,只追加段 |
| 注入内容形态 | 最近 ≤10 条观察的原文拼接(截断),**不加 LLM 聚合环节** | 证据直读零失真;聚合属"演化机制",明确不做 |
| 认知变化展示 | 画像视图只读列表(从 X → Y + 依据);**不进检索/不进注入**(v1) | 展示层先跑通,是否值得进检索看真实使用 |
| 评估 | 金样本确定性测试(脚本化 LLM fixtures) + 可选真实回放 `make eval-memory`(手动) | 20 号 §7 质量验证的落点;真实回放不进 CI(依赖外部 LLM) |

## 3. 数据模型

```go
// internal/domain/memory/style.go — TableName: style_observations
type StyleObservation struct {
    ID        int64  `gorm:"primaryKey;autoIncrement"`
    UserID    int64  `gorm:"index;not null"`
    Dimension string `gorm:"size:20;not null"` // tone|length|formality|humor|format|address
    Content   string `gorm:"type:text;not null"` // 观察描述(带依据的陈述句)
    SourceMessageIDs []int64 `gorm:"serializer:json"` // 依据消息(溯源展示用)
    CreatedAt time.Time `gorm:"not null"`
}

// TableName: cognition_changes
type CognitionChange struct {
    ID        int64  `gorm:"primaryKey;autoIncrement"`
    UserID    int64  `gorm:"index;not null"`
    Content   string `gorm:"type:text;not null"` // "从 X 改为 Y"叙事
    SourceMessageIDs []int64 `gorm:"serializer:json"`
    CreatedAt time.Time `gorm:"not null"`
}
```

- users 表加 `style_injection_enabled bool`(default false,M2 用)。
- 管线重复观察同一维度 → 允许多条并存（风格随时间演化本身就是信号）；去重交给展示层按时间分组。

## 4. 沉淀管线扩展

- digest prompts 输出增加两段（空数组常态）：
  - `style_notes`：`[{dimension, content, source_message_ids}]`——对**用户侧表达**的观察
    （"用户习惯用'老铁'开头""回复偏好短句"），必须引用依据消息；禁止对助手侧输出做观察。
  - `preference_changes`：`[{content, source_message_ids}]`——用户明确表达的偏好/决策改变
    （"以前喝美式现在改燕麦拿铁"）；普通事实进 facts，不重复记。
- 解析容错同既有纪律：未知 dimension 归 `tone`；缺 source_message_ids 允许（溯源空显示）。
- 落库后触发 `OnChange`（M2 注入缓存的失效信号；M1 期间为 no-op）。

## 5. 画像视图（M1）

- API：`GET /api/v1/style-profile`（observations + changes 两个列表,按时间倒序,各限 50）；
  `DELETE /api/v1/style-profile/observation/:id`、`/change/:id`（用户删除错误证据=纠正口）。
- 前端：设置抽屉新增「风格与认知」区——观察列表（维度徽标 + 内容 + 时间 + 依据消息片段）、
  认知变化列表（从 X → Y）、空态文案；风格注入开关（M2 接线,M1 先渲染禁用态）。

## 6. 按用户注入（M2,架构改动）

- `AgentService`：`SetPromptDecorator(func(userID int64, base string) string)`——`RunStream` 内
  `SystemPrompt: s.promptFor(userID)`（decorator nil → 现行为,零回归）。
- 装配点 decorator：基座（全局 prompt,不变）+ 用户开启注入时追加：
  ```
  == 用户的沟通风格(参考)==
  以下是对该用户近期表达方式的观察,回复时自然参考,不要机械执行:
  - [formality] 用户偏好直接、少客套
  - [address] ...
  ```
  无观察 → 不追加该段。段落缓存 per-user（开关翻转/新证据落库时经 OnChange 失效重建）。
- **可回滚**：关开关即恢复通用 persona,无残留。

## 7. 评估（M3,贯穿要求 #3 的落点）

- **金样本确定性测试**：3-5 组对话区间 fixtures + 期望抽取断言（facts/style_notes/preference_changes）,
  脚本化 LLM 输出跑管线——回归护栏。
- **真实回放（手动）**：`make eval-memory`——对金样本用真实 LLM 跑沉淀,输出抽取准确性报告
  （命中/漏抽/误抽清单）。不进 CI；结果人工审阅并反哺提示词。

## 9. 风险

| 风险 | 处置 |
|------|------|
| LLM 抽取噪声(过度观察) | 单轮上限 3 条 + 常态空数组提示词约束 + 单条可删 + `make eval-memory` 抽样审计 |
| 注入后风格漂移/自我强化 | 只注入**原始观察**(不注入任何生成结论);开关默认关;关即回滚 |
| per-user prompt 改动波及主链路 | decorator 为 nil 时逐字节同现状;现有 prompt 测试守护 |
| 观察过时(风格变了) | 展示按时间分组可见演化;删除口;v1 不做自动过期(M3 评估后定) |

## 11. 边界与不做

- **自动演化机制不做**：不用 LLM 聚合画像、不自动改写 persona、不按"风格相似度"改写回复——
  v1 只把原始证据摆出来、经确认后供参考。
- 认知变化不做检索/注入（v1 展示层）；不做风格 A/B 或效果度量。
- 多用户共享画像、跨用户迁移：不做。
