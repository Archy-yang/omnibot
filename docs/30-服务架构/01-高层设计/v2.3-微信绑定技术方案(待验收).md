# v2.3 微信账号绑定 - 技术方案

| 项 | 内容 |
|----|------|
| 版本 | v2.3 |
| 状态 | ✅ 已实现(feat/v2.3-wechat-binding) |
| 关联 PRD | `docs/20-产品PRD/in_progress/v2.3-微信账号绑定PRD.md` |
| 前置 | v2.2 已实现(BindingService + 绑定码机制) |

## 1. 核心思路

v2.3 = v2.2 的泛化 + 微信入口对称改造。

**泛化**:v2.2 的 BindingService 写死了 `feishuChannelType="feishu"`,v2.3 把它提成方法参数,
一套绑定逻辑服务所有渠道。绑定码本身不区分渠道(通用码),在哪个渠道发就绑哪个渠道。

**微信改造**:微信 handler 从 `UserService.GetOrCreateByChannel` 切到 `BindingService`,
和 v2.2 飞书 handler 改造同款,但要处理微信独有的「关注事件」和「命令系统」。

## 2. BindingService 泛化

### 2.1 签名变更

`internal/service/user/binding_service.go`:

```go
// 旧(v2.2,飞书专用)
func (s *BindingService) BindFeishu(code, openID string) error
func (s *BindingService) ResolveFeishuUserID(openID string) (int64, bool, error)
func (s *BindingService) IsFeishuBound(userID int64) (bool, error)
func (s *BindingService) GenerateCode(userID int64) (string, time.Time, error)

// 新(v2.3,渠道通用)
func (s *BindingService) BindChannel(channelType, code, openID string) error
func (s *BindingService) ResolveUserID(channelType, openID string) (int64, bool, error)
func (s *BindingService) IsChannelBound(userID int64, channelType string) (bool, error)
func (s *BindingService) GenerateCode(userID int64) (string, time.Time, error)  // 不变,通用码
```

- 删除 `const feishuChannelType = "feishu"`,channelType 全部走参数
- `BindChannel` 校验顺序同 v2.2:码有效 -> open_id 未占 -> 账号未绑该渠道 -> 建绑定 + 删码
- `GenerateCode` 不变:一个账号同时只有一个有效码,通用,不区分渠道

### 2.2 表重命名

`feishu_bind_codes` -> `bind_codes`(不再飞书专属)。

- domain 实体 `FeishuBindCode` -> `BindCode`,表名 `bind_codes`
- repo `FeishuBindCodeRepository` -> `BindCodeRepository`
- AutoMigrate 更新
- **DB 迁移**:项目 dev 期,旧 `feishu_bind_codes` 表数据无价值,启动时 AutoMigrate 建新表,
  旧表留库不动(或手工 drop)。不写迁移脚本。

### 2.3 调用点更新

| 调用方 | v2.2 调用 | v2.3 调用 |
|---|---|---|
| 飞书 handler | `BindFeishu(code, openID)` | `BindChannel("feishu", code, openID)` |
| 飞书 handler | `ResolveFeishuUserID(openID)` | `ResolveUserID("feishu", openID)` |
| web handler | `IsFeishuBound(userID)` | `IsChannelBound(userID, "feishu")` + `IsChannelBound(userID, "wechat")` |
| web handler | `GenerateCode(userID)` | 不变 |

## 3. 微信 handler 改造

`internal/api/wechat/handler.go`:

### 3.1 接口替换

```go
// 旧
type UserService interface {
    GetOrCreateByChannel(channelType, channelUserID string) (*user.User, *user.UserChannel, bool, error)
}

// 新(复用飞书同款 BindingService 接口契约,但 wechat 包内独立定义)
type BindingService interface {
    BindChannel(channelType, code, openID string) error
    ResolveUserID(channelType, openID string) (userID int64, bound bool, err error)
}
```

Handler struct 字段 `userService` -> `bindingService`,`NewHandler` 签名相应调整。

### 3.2 HandleMessage 顶层

删除 line 237 的"兜底建号"(每条消息先 GetOrCreateByChannel)。身份解析下沉到 handleTextMessage。

### 3.3 handleTextMessage 重写

```
取 text = TrimSpace(in.Content)
1. parseBindCode(text) 命中 -> handleBindCode(in.FromUserName, code) -> 返回回复 XML
2. ResolveUserID("wechat", in.FromUserName):
   - bound=true -> userID 走原命令系统/对话路径
   - bound=false -> 返回 unboundGuide 引导文案(不建号不进对话)
3. 命令系统(#模型设置等):仅 userID > 0 时可用;未绑直接回引导(不到命令层)
```

### 3.4 handleBindCode(新增)

和飞书 `handleBindCode` 同款,按 errors.Is 映射 PRD 5.1 文案:
- nil -> `绑定成功!现在可以在微信跟我聊了`
- ErrCodeInvalid -> `绑定码无效或已过期,请在 web 端重新获取`
- ErrFeishuAlreadyBound -> 复用通用名 `ErrChannelAlreadyBound` -> `该微信号已绑定其他账号`
- ErrAccountAlreadyBound -> `你的账号已绑定微信,如需更换请稍后(暂不支持)`

> 注:sentinel error 也需泛化命名(见 3.6)。

### 3.5 handleSubscribeEvent 重写

```
// 旧:关注即建号 + 欢迎语
// 新:不建号,回欢迎语 + 绑定引导
return subscribeGuide  // 固定文案:欢迎语 + 绑定操作步骤
```

### 3.6 sentinel error 泛化

`binding_service.go`:
- `ErrFeishuAlreadyBound` -> `ErrChannelAlreadyBound`(该渠道号已绑其他账号)
- `ErrAccountAlreadyBound` 保留(账号已绑该渠道)--语义不变,文案由调用方填渠道名

### 3.7 微信特有:5 秒超时

绑定操作 = 1 次码查询 + 1 次 channel 查询 + 1 次 create + 1 次删码,DB 读写 < 100ms,
5 秒超时绰绰有余。无需异步化。

## 4. web 端改造

### 4.1 后端 handler

`internal/api/web/feishu_bind_handler.go` 重命名/泛化为 `channel_bind_handler.go`:
- `HandleGetBindingStatus` 返回**两个渠道状态**:`{feishu_bound, wechat_bound}`
- `HandleGenerateBindCode` 不变(通用码)
- 路由 `/api/v1/user/feishu/binding` -> `/api/v1/user/channel-binding`(或保留旧路径返扩展字段)

### 4.2 前端

`SettingsDrawer.vue`「飞书账号绑定」区块改为「渠道绑定」:
- 展示两行状态:飞书(已绑/未绑)、微信(已绑/未绑)
- 绑定码通用,操作说明改为"在你要绑定的渠道(飞书或微信)发送:绑定 <码>"
- `services/feishu.ts` -> `services/channelBinding.ts`,接口返两渠道状态

## 5. 装配(routes.go)

- `bindCodeRepo` 不变(泛化后类型名变)
- `bindingSvc` 不变
- 微信 `NewHandler` 注入 `bindingSvc`(替换原 `userSvc`)
- 飞书 `NewMessageHandler` 调用更新为 `BindChannel`/`ResolveUserID`
- web 路由更新

## 6. TDD 开发顺序

1. **泛化 BindingService**:签名改 channelType 参数 + sentinel error 重命名 + 表/实体/ repo 重命名 + 单测适配
2. **飞书 handler 适配**:BindFeishu->BindChannel 等,测试适配
3. **web handler 适配**:状态接口返两渠道,测试适配
4. **微信 handler 改造**:BindingService 注入 + 绑定码解析 + 未绑引导 + 关注事件 + 命令系统守卫 + 单测
5. **前端**:渠道绑定区块 + service 重构
6. **回归 + 合并**:go test ./... + npm build + 端到端(与 v2.1/v2.2 一起手测)

## 7. 不做(PRD 3.2)

解绑/换绑/多微信号/企业微信/扫码/web 实时状态 -- 均不在本期。

## 8. 风险与注意

- **微信命令系统**:`#模型设置` 等命令在未绑定时不能执行,handleTextMessage 要在命令分发前先判绑定状态
- **关注事件文案**:微信被动回复有长度限制,欢迎语+引导要精简
- **表重命名**:`feishu_bind_codes` -> `bind_codes`,AutoMigrate 建新表,旧表残留无害(dev 期可手工 drop)
- **向后兼容**:v2.2 的 `/api/v1/user/feishu/binding` 路径若已前端调用,改路径要同步前端;或保留旧路径返扩展字段(推荐改路径,前端反正要改)
