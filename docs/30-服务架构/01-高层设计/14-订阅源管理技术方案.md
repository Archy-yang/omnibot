## 1. 背景与目标

### 1.1 问题

用户会关注一些持续更新的信息源(博客、周刊、专栏)。当前对话里谈到这些,只能沉淀为
自然语言记忆(「他订阅了阮一峰的博客」)——助理*知道*,但*行动不了*:

- 查信息时不知道从哪些源取
- 用户给出网站地址,没法自动变成可用的订阅
- 订阅关系散落在对话流里,无法枚举、无法管理

### 1.2 目标(用户模型)

> 「帮我把阮一峰的博客订阅上」(只给网站地址) → 助理自动找到 RSS 地址 → 入库 → 回执。
> 「最近 AI Agent 领域有什么动态」 → 助理先看订阅清单 → 挑主题相关的源 → 抓取 → 综合回答。

三条设计决策(已与用户对齐):
1. **查询时按需取**:订阅 = 信息源登记簿,不做定时抓取、不做主动推送(用户明确否定)
2. **RSS 自动发现**:用户只给网站/博客地址,助理负责找到 feed 地址并验证
3. **对话即管理界面**:无独立管理页,全走 `manage_subscriptions` 工具

### 1.3 非目标(本方案不做)

- ❌ 定时抓取、后台轮询、新内容推送(用户明确否定;将来若做,走 08 框架 + 汇报锚定,本方案留路不占位)
- ❌ 全文抓取/网页监控(无 RSS 的网站怎么盯,另行立项)
- ❌ 订阅内容入库/向量化(按需现抓,不落正文)
- ❌ 海量订阅优化(单用户量级 <100,全量给 LLM 选源即可,不需要检索索引)

## 3. 总体设计

```
【订阅】用户:"订阅阮一峰的博客"(网站地址)
  └ Agent → manage_subscriptions(add, url=网站)
      └ SubscriptionService.Add
          ├ ① RSS 自动发现(见 §5):head 声明 → 约定路径 → gofeed 验证
          ├ ② 生成主题描述(一句话:这个源是关于什么的)
          ├ ③ 恰一个 feed → 直接入库;多个 → 列出让用户挑;零个 → 如实报告
          └ ④ 回执:订了什么、主题描述是什么

【查询】用户:"最近 AI Agent 领域有什么动态"
  └ Agent 查询流程(提示词规则驱动,见 §6):
      ├ ① manage_subscriptions(list) 全量拿订阅清单(含 feed 地址 + 主题描述)
      ├ ② LLM 按问题语义挑相关源(几十条量级,不需要检索算法)
      ├ ③ rss_reader(url=清单里的 feed 地址) 逐源抓取最新条目
      └ ④ 兜底:清单无命中 → 中期记忆搜"订阅/源/RSS"相关原文 → 通用搜索
```

**设计要点**:选源智能在 LLM + 主题描述,不在基础设施。订阅表只做两件事:
枚举(给 Agent 看)和去重(防重复订阅)。

> ⚠️ 实施约束(task#18 事故教训,2026-09-14):
> 1. list 输出**必须含 feed 地址**——只有标题/主题描述会逼模型从标题脑补 URL
>    (AIHOT 被推算成 aihot.com,真实订阅是 aihot.news,全部 DNS 失败)。
>    提示词已配"feed 地址只能来自 list 结果,严禁自行推算或拼凑 URL"。
> 2. 抓取类工具(rss_reader/web_read)是**子 Agent 专属**(MainVisible=false)。
>    曾因 GORM `default:true` 标签 + 零值省略使 seed 的 false 永远写不进库,
>    主 Agent 越界亲自抓取;已去掉标签修复,勿再加回。

## 4. 数据模型

```go
// internal/domain/subscription/subscription.go
type Subscription struct {
    ID          int64     `gorm:"primaryKey"`
    UserID      int64     `gorm:"not null;uniqueIndex:idx_user_feed"`
    SiteURL     string    `gorm:"size:500;not null"`  // 用户给的网站地址
    FeedURL     string    `gorm:"size:500;not null;uniqueIndex:idx_user_feed"` // 发现并验证的 feed 地址
    Title       string    `gorm:"size:200;not null"`  // feed 自带标题
    TopicDesc   string    `gorm:"size:500"`           // 主题描述(订阅时生成,选源依据)
    Status      string    `gorm:"size:20;not null;default:active"` // active / paused
    CreatedVia  string    `gorm:"size:20;not null;default:manual"` // manual / auto(将来自动建议)
    CreatedAt   time.Time `gorm:"not null"`
    UpdatedAt   time.Time `gorm:"not null"`
}
```

- 唯一索引 `(user_id, feed_url)`:同源防重订
- 不存订阅内容/摘要(按需现抓);不存抓取水位(无定时任务)
- AutoMigrate 注册进 `internal/db/database.go`

**API 层(v1.1 修订:增加页面管理入口)**:管理走双入口——对话(`manage_subscriptions`
工具)与订阅管理弹窗(REST)。REST 复用同一 SubscriptionService,是薄壳:

```
GET    /api/v1/subscriptions              清单(含暂停,带状态)
POST   /api/v1/subscriptions              {url, topic_desc?} → 自动发现
       ├ 单候选/直连 feed → 入库返回 {subscription}
       └ 多候选 → 返回 {candidates},前端让用户挑(feed 地址再 POST)
DELETE /api/v1/subscriptions/:id          退订
PUT    /api/v1/subscriptions/:id/status   {status: active|paused}
```

全部挂 AuthRequired;前端「订阅」弹窗(侧栏第五导航项)+ 侧栏导航高亮联动。

## 5. RSS 自动发现(`internal/service/subscription/discovery.go`)

确定性三步,无 LLM 参与:

```
Discover(siteURL) → (*FeedInfo, error)

① head 声明:抓取页面 HTML,解析 <link rel="alternate">
   type ∈ {application/rss+xml, application/atom+xml, application/feed+json}
   命中 → 候选(可能多条,如博客+评论 feed)
② 约定路径:①无命中,则对 siteURL 逐个尝试
   /feed /feed/ /rss /rss/ /atom.xml /index.xml /feed.xml /rss.xml /?feed=rss2
③ 验证:候选逐个用 gofeed ParseURL 真抓一次,能解析出 ≥1 条目才算数
   (防止把普通页面/失效地址当 feed)
```

- 超时 10s/请求(与 rss_reader 一致),整体发现流程 ≤30s
- HTTP Client 复用 rss_reader 的 gofeed.Client 配置(UA、重定向跟随)
- HTML 解析用 `golang.org/x/net/html`(gofeed 传递依赖,无新增三方包)
- `FeedInfo{FeedURL, Title, Description}`:Title/Description 取 feed 元数据

**结果语义**(宁漏勿错,不硬造):
| 情形 | 行为 |
|------|------|
| 验证通过恰 1 条 | 直接入库,回执告知 |
| 验证通过 ≥2 条 | 返回列表,Agent 让用户挑,选定后入库 |
| 0 条 | 明确报错「该站点未发现可用 RSS」,不猜、不硬造 |

## 6. Agent 工具(`internal/service/agent/builtin_tools.go`)

### 6.1 新增 `manage_subscriptions`

```
name: manage_subscriptions
display_label: 管理了订阅源 / 查看了订阅清单(按 action 区分)
capabilities: 复用现有能力标记(与 rss_reader 同组)
parameters:
  action: add | list | remove | pause | resume   (required)
  url:    网站或 feed 地址(action=add 必填,支持网站地址自动发现)
  id:     订阅 id(remove/pause/resume 必填,来自 list 结果)
  topic_desc: 可选,用户对源的补充描述;缺省由 feed 元数据生成
```

- add:`SubscriptionService.Add(userID, siteURL)` → 内部走 §5 发现 + 去重
  (已订阅同 feed_url → 返回"已订阅"而非报错)+ 回执带 Title/TopicDesc
- list:全量返回 `id / title / topic_desc / status`,供选源;**这是查询流程的入口**
- remove/pause/resume:按 id 操作(pause 保留登记但选源时跳过)
- 层级:工具 → SubscriptionService → SubscriptionRepository,遵守分层约束

### 6.2 `rss_reader` 微调(仅描述文案)

描述补充一句:「查询用户关注领域的信息时,先用 manage_subscriptions(list)
获取订阅清单,挑主题相关的源再调用本工具」。

### 6.3 主 Agent 提示词(`agentprompt/content.go`)追加规则

- 查信息类请求:**先看订阅清单**,主题相关的源优先于通用搜索
- 订阅类请求:用户给网站地址即可,自动发现由工具完成;多个候选时让用户挑;
  发现失败如实说,不硬造
- 用户提到自己常看的源但尚未订阅时,可建议订阅(建议,不擅自添加)

### 6.4 查询三级兜底(提示词规则,非硬编码)

1. 订阅清单主题匹配 → `rss_reader` 抓取
2. 清单无命中 → `search_memories` 近期对话原文区(搜"订阅/博客/源"相关消息)
3. 仍无 → 通用网络搜索;命中好源可建议订阅

## 7. 与记忆体系的关系

- **叙事层零开发**:「帮老爷订阅了阮一峰的博客」这类对话会被 M6 沉淀管线自然
  摘成 loop/fact(「我持续跟进这些信息源」),不需要专门写提取逻辑
- **职责切分**:订阅表 = 程序消费的结构化实体(给 Agent 枚举/去重);
  记忆 = 人看的自然语言叙事。二者不互相同步,各走各的写入路径
- 将来「反复强调的记忆升级」若立项,订阅建议(从对话识别"常看 X")可复用其
  建议-确认环,本方案预留 `created_via=auto` 枚举值
