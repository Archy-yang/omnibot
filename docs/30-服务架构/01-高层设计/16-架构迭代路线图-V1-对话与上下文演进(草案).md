## 1. 文档目标

本文档用于指导 OmniBot 在现有代码基础上的下一阶段架构迭代。

当前 OmniBot 已经具备：

- Main Agent
- Generic Sub Agent
- 异步 AgentTask
- Task Report
- Tool / MCP / Skill
- Memory Pipeline
- Message History
- Web / Feishu / WeChat 等 Channel
- Agent Runtime Hook
- 流式 LLM Loop

当前不建议：

- 重写 Agent Framework
- 引入新的 Agent 编排框架替换现有 Runtime
- 为每个 Agent / User 动态启动 Pod
- 提前构建复杂的分布式 Agent 平台

下一阶段重点应放在以下四个方向：

1. 对话数据模型完善：Conversation → Turn → Message
2. Context Manager：Compact + Recent Raw
3. Conversation Recall + Memory Search 分层
4. Task Runtime 可靠性与权限安全

整体目标是将 OmniBot 从：

一个具备较完整功能的个人 Agent

演进为：

一个可以长期持续运行、长期对话、支持异步任务并具备可靠 Context / Memory / Task Runtime 的个人 Agent Harness。

## 3. 核心设计原则

### 3.1 Context 不等于 Storage

必须始终区分：

- **Storage** = 完整信息长期保存的位置
- **Context** = 当前模型运行所需的 Working Set

因此：

- Raw Conversation 永久保留
- Task Artifact 永久保留
- Memory 永久保留
- Context 可以有损压缩
- Compact 不需要保存所有历史细节

这是后续 Context Manager 的基础原则。

### 3.2 Compact 和 Memory 是不同概念

**Compact** 解决：当前这场持续对话聊到了哪里？

- 属于：Runtime / Context Manager
- 始终进入模型上下文

**Memory** 解决：过去还有什么信息值得找回来？

- 属于：Agent Capability
- 默认不主动注入 Context
- 通过 `memory_search(...)` 由 Agent 根据需要主动检索

### 3.3 Conversation Recall 和 Memory Search 分层

增加两个不同层级：

**Auto Conversation Recall**

- 由 Runtime 自动执行
- 输入：Current User Question
- 搜索：Raw Conversation History
- 作用：防止 Compact 遗漏近期或具体历史对话细节
- 属于：Cheap / Shallow Retrieval

**memory_search**

- 由 Agent 在 Loop 中主动执行
- 作用：深度查询长期记忆、用户偏好、历史决策、跨会话知识
- 属于：Agentic / Deep Retrieval

## 5. P0-1：正式引入 Conversation / Turn / Message 模型

### 5.1 当前问题

目前代码实际采用：

```text
User
Assistant
User
Assistant
Assistant Report
```

数据库知道：Report Message → Task
但是不知道：Task → 哪一次用户请求、Report → 哪一个逻辑 Turn。

同时当前存在：

```text
ContextRounds = 10
ContextMessagesPerRound = 2
MaxContextMessages = 20
```

但实际上 Repository 使用的是：最近 20 条 Message。
已经不是真正的"最近 10 Turn"——因为异步 Task Report 会额外增加 Assistant Message。

### 5.2 新模型

正式定义：`User → Conversation → Turn → Messages`

**Conversation** 表示用户与 OmniBot 的长期关系。

产品层面：一个 User 通常只有一个 Active Main Conversation，
但数据库不能假设全系统永远只有一个 Conversation。

建议表：

```text
conversations

id
user_id
agent_id
status
created_at
updated_at
```

约束可考虑：`(user_id, agent_id)` 最多一个 active conversation。

**Turn** 表示一次用户意图的逻辑执行单元，通常由 User Message 发起。

例如：

```text
Turn #100

User: 帮我调研 Claude Agent SDK
Assistant: 好的，已经安排。
Task #888

10 分钟以后：

Assistant Report: 调研完成……
```

即使 Report 在时间上晚于 Turn #101、#102，`turn_id` 仍然 = 100。

**Message** 表示用户真正看到的时间线消息。

增加字段：`conversation_id` / `turn_id` / `message_type` / `task_id nullable`。

例如：

```text
message #1001  role=user       turn_id=100
message #1002  role=assistant  turn_id=100  message_type=normal
message #1050  role=assistant  turn_id=100  message_type=task_report  task_id=888
```

### 5.3 AgentTask 增加 OriginTurnID

AgentTask 增加 `origin_turn_id`：

```text
Turn
 ├── Message
 ├── Message
 └── AgentTask
       │
       └── Report Message
```

### 5.4 TurnID 传递方式

当前已经有类似 `WithSource(ctx, ...)` / `WithNotifyTarget(ctx, ...)`，
增加 `WithTurnID(ctx, turnID)`。

流程：

```text
收到 User Message
        ↓
创建 ConversationTurn
        ↓
SaveUserMessage(turnID)
        ↓
WithTurnID(ctx, turnID)
        ↓
Agent Runtime
        ↓
delegate
        ↓
StartTask(originTurnID)
```

### 5.5 时间顺序与逻辑顺序必须分开

必须保留两个维度：

**Temporal Order**（`message.created_at` / `message.id`）

- 用于：UI Timeline、Recent Raw Context

**Logical Ownership**（`message.turn_id`）

- 用于：Conversation Recall、Embedding、Compact、Task Tracking、Debug

Recent Context 不能为了 Turn 重排时间线。例如：

```text
Turn100 User
Turn100 Assistant
Turn101 User
Turn101 Assistant
Turn100 TaskReport   ← 时间线仍然排在这里
```

进入 Recent Raw 时仍然保持这个顺序。

### 5.6 验收标准

完成后必须满足：

- 每个 User Message 都有 Turn
- Main Agent 普通回复关联当前 Turn
- delegate 创建 Task 时保存 origin_turn_id
- Task Report 保存原始 TurnID
- Report 即使晚于后续 Turn，也能找到原始请求
- UI 时间线顺序不受 Turn 影响
- 原有 Task / Message 查询兼容

## 6. P0-2：实现 Context Manager

这是当前最重要的 Agent Runtime 演进之一。

### 6.1 删除固定 Recent 10 Rounds 思维

逐渐淘汰：

```text
ContextRounds = 10
ContextMessagesPerRound = 2
```

改为 **Token Budget Based Context**。

原因："你好"是一轮，一个 10K token 的代码分析也是一轮。
Turn 数不能正确代表 Context 大小。

### 6.2 Context Manager 职责

Context Manager 只负责 Conversation Context，不负责：

- Memory Search
- Web Search
- Tool Selection
- Agent Reasoning

接口可以类似：

```go
type ContextManager interface {
    Build(
        ctx context.Context,
        conversationID int64,
        currentMessage Message,
    ) (*ContextResult, error)
}
```

输出：

```go
type ContextResult struct {
    Compact        string
    RecentMessages []Message

    TokenCount     int
    CompactVersion int
}
```

### 6.3 Prompt 结构

推荐：

```text
Stable System Prompt
History Compact
Recent Raw Messages
Auto Recall
Current User Question
```

注意：Compact 不要直接拼到 System Prompt 字符串内部。

不要：

```text
systemPrompt = basePrompt + compact
```

推荐：

```text
Message 1   role=system                        stable system prompt
Message 2   role=context/developer/synthetic   history compact
Message 3+  role=user/assistant...             recent raw
...
            role=user                          current question
```

具体 Role 由 Provider Adapter 决定。
目的：保持 Stable System Prefix 不变，提高 Prompt Cache 命中率。

## 7. P0-3：实现 History Compact

### 7.1 Compact 模型

不采用无限级联：

```text
Compact A → Compact B → Compact C → Compact D
```

而采用：

```text
Current History Compact + Recent Raw Messages

Compact(n+1) = Compact( Compact(n) + Old Raw Messages )
```

保留 Recent Tail 不压缩。

### 7.2 Compact 表达的是 Working State

Compact 不应只是普通聊天摘要。建议定义为 **Conversation Working State**，建议结构：

```text
<conversation_state>

Current Topics:
- ...

Current Goals:
- ...

Decisions:
- ...

Rejected Approaches:
- 方案
- 被否决原因

Constraints:
- ...

Open Questions:
- ...

Pending Work:
- ...

Important Task / Artifact References:
- ...

Current State:
- ...

</conversation_state>
```

核心目标：保留未来继续对话所需要的信息，而不是最大程度缩短 token。

### 7.3 Compact 状态

建议保存表 `conversation_context_state`：

```text
conversation_id
compact_content
compact_until_message_id
compact_version
compact_count
token_count
updated_at
```

其中 `compact_until_message_id` 表示：`<= 此 Message ID` 已经进入 Compact。

Context Manager 查询：

```sql
Compact
+
SELECT * FROM messages WHERE id > compact_until_message_id ORDER BY id
```

### 7.4 Compact Trigger

按 Token 触发，不按 Turn 数。例如：

```text
Model Context:        128K
CompactTriggerTokens:  60K
TargetCompactTokens:    8K
KeepRecentTokens:      15K
ReservedOutputTokens:  20K
```

当 `Compact + Recent > 60K`：

```text
Compact + Recent 中较旧部分
        ↓
     LLM Compact
        ↓
     New Compact
```

最近约 15K Raw 保留。

### 7.5 Context Rebase 暂不做 P0

长期连续 Compact 会有 `S1 → S2 → S3 → S4` 不断有损压缩的问题。
未来可以增加 Context Rebase：

```text
Raw Conversation + Current Compact + Task / Artifact State + 必要 Memory
        ↓
   重新构建 Clean Compact
```

但第一阶段不要实现。先观察：

- Compact 次数
- 信息遗漏率
- 用户纠正率
- Memory Search 使用率

再决定是否加入 Rebase。

### 7.6 验收标准

必须满足：

- Recent 不再固定 20 messages
- Context 使用 Token Budget
- Compact 自动生成
- Recent Tail 保留原始 Message
- Compact 更新后继续正常对话
- Compact 前后的 Task Report 不丢失
- Stable System Prompt 不随 Compact 更新
- Compact 发生频率低于普通 Agent Loop

## 8. P1-1：Conversation Recall

Context Compact 是有损的，因此增加 Auto Conversation Recall。

### 8.1 定位

Conversation Recall 不是 Memory。

作用：根据当前用户问题，从 Raw Conversation 中自动找到可能被 Compact 掉的相关历史原文。
它属于 Runtime Automatic Retrieval。

### 8.2 初始流程

```text
Current Question
      │
      ▼
Conversation Recall Search
      │
      ▼
Top-K Conversation Chunks
      │
      ▼
score threshold
      │
      ▼
Auto Recall
```

然后 Context：

```text
System
Compact
Recent Raw
Auto Recall
Current Question
```

### 8.3 Recall 必须靠后放置

不要：

```text
System → Recall → Compact → Recent → Question
```

因为 Recall 每轮变化，会破坏 Prefix Cache。

推荐：

```text
System → Compact → Recent Raw → Recall → Current Question
```

这样 `System + Compact + Recent` 仍具有较高 Cache 复用。

## 9. P1-2：历史索引从 Message 升级为 Turn / Chunk

### 9.1 当前 Message Embedding 可以保留作为过渡

当前 Message Embedding 不需要立即删除。
但长期方向不要继续：每一条 user/assistant message 独立 embedding。

原因："所以还是第二种？" "对。" "跟刚才那个一样。"
单条 Message 没有完整语义。

### 9.2 推荐索引粒度

优先：Complete Turn。

例如：

```text
Turn #100

[User]        帮我调研 Claude Agent SDK
[Assistant]   已安排后台任务
[Task Report] 最终结论……
```

整体作为一个 ConversationChunk。

### 9.3 Chunk 表

建议表 `conversation_chunks`：

```text
id
user_id
conversation_id
turn_id
start_message_id
end_message_id
content
embedding
created_at
updated_at
```

### 9.4 检索后展开邻居

不要：vector 命中 Chunk100 → 只返回 Chunk100。

推荐：

```text
Vector Search
     ↓
定位 Chunk
     ↓
查询邻居
     ↓
Chunk99 + Chunk100 + Chunk101
     ↓
merge / dedup
```

原则：**Vector 用于定位，Conversation Store 用于恢复完整局部语境。**

### 9.5 长 Turn 切分

不要固定 1500 字符截断，改为 Token-based Chunk（例如 500~1500 tokens / chunk）。

对于同一个长 Turn：

```text
turn 100
 ├── chunk A
 ├── chunk B
 └── chunk C
```

均保留 `turn_id` / `start_message_id` / `end_message_id`。

### 9.6 检索方式

V1 可以 Vector Search。后续建议 Vector + Keyword/BM25 + Recency：

```text
final_score =
    vector_score  * A
  + keyword_score * B
  + recency_score * C
```

原因：用户历史搜索经常出现强关键词（WorkBuddy、Redis Pipeline、NAS、Claude SDK），
Hybrid Search 通常比纯 Vector 更可靠。

## 10. P1-3：Memory 改为 Agent Tool

Memory 不再由 Context Manager 自动注入。

### 10.1 推荐 Runtime 模型

```text
Context Manager
      ↓
Compact + Recent + Recall
      ↓
LLM
      ↓
Agent Loop
      ├── memory_search(...)
      ├── web_search(...)
      ├── task_query(...)
      └── ...
```

### 10.2 Memory Search 定位

**Memory 保存**：长期值得沉淀的知识（用户长期偏好、项目长期状态、稳定决策、人员关系、重复使用的信息）。

**Raw Conversation 保存**：实际发生过什么。

### 10.3 Memory Tool V1

先只暴露 `memory_search(query)`，不要一次暴露太多复杂 Memory CRUD Tool。
Memory 写入继续由现有 Memory Pipeline 自动完成即可。

### 10.4 Tool Description

需要明确告诉模型：

```text
Use memory_search when:
- the user refers to a previous discussion
- a previous preference may affect the answer
- historical decisions are needed
- the current context is insufficient
- you are unsure whether something was previously agreed

Do not call memory_search when the information
is already clearly available in the current context.
```

### 10.5 与 Auto Recall 的关系

两者必须保持不同：

```text
Conversation Recall          Memory Search
━━━━━━━━━━━━━━━━━━━          ━━━━━━━━━━━━━━━━━━━
Runtime 自动                 Agent 主动
一次 shallow retrieval       可以多轮搜索、可以修改 query
搜索原始 conversation        搜索长期 semantic memory
```

## 11. P1-4：Task Runtime 状态机

完成 Context / Turn 后，再处理 Task Runtime。

### 11.1 当前问题

现在本质是：DB Task + 本进程 goroutine（`go s.executeTask(context.Background(), task)`）。

存在：

- Pod Restart 后 Task 永远 Running
- Cancel 绑定本进程
- 多 Pod 无法可靠 Cancel
- 没有 Worker Concurrency Control
- Task Completion / Cancellation 存在 Race

### 11.2 不需要动态 Pod

暂时不要：每任务创建 Kubernetes Pod。

推荐：

```text
AgentTask → DB Durable Queue → Worker Pool
```

### 11.3 Task 字段

增加：

```text
status
lease_owner
lease_until
attempt
next_run_at
version
```

### 11.4 Task Claim

```text
pending → (CAS) → running + lease_owner + lease_until
```

Worker 定期 Heartbeat。如果 `lease_until < now()`，允许其他 Worker 重新 Claim。

## 12. P1-5：Task 状态必须 CAS

当前：

```sql
UPDATE agent_tasks SET status = ? WHERE id = ?
```

存在 `cancelled → completed` 被覆盖的可能。改为：

```sql
UPDATE agent_tasks SET status = 'completed'
WHERE id = ? AND status = 'running'
```

检查 `RowsAffected == 1`。

### 12.1 正式状态机

```text
pending        → running | cancelled
running        → completed | failed | input_required | cancelled
input_required → running | cancelled
```

业务代码以后不允许 `SetStatus(...)`，而是 `Transition(from, to)`。

## 13. P1-6：Runtime Control Signal

当前类似 `request_input` 只通过 Prompt 告诉模型"调用后停止"，这是不可靠的。

### 13.1 Tool Result 增加 Control

```go
type ToolResult struct {
    Content string
    Control ControlSignal
}
```

定义：`Continue / Stop / Suspend / Cancel / Fatal`。

`request_input` → `Control = Suspend`。
Agent Runtime 收到 Suspend 后：

- 停止剩余 Tool Calls
- 停止下一轮 ReAct
- 更新 Task 状态
- 等待恢复

## 14. P2-1：Task Event 真正事务化

目前 Task 状态和 Event 不是同一事务。
未来如果 Event 要用于 Notification / LISTEN-NOTIFY / Event Driven，必须：

Task Transition + Append Event 同一事务。

```text
task.version += 1

task_event:
  task_id
  version
  event_type
  payload
  created_at

唯一约束: (task_id, version)
```

不要再依赖进程内 `eventSeq map`。

## 15. P2-2：Report 与 Delivery 分离

当前 `reported` 同时承担：Main Agent 是否生成过 Report、是否已推给 Feishu、是否需要重试——职责过重。

未来建议三层：Task Execution Status / Report Status / Delivery Status。

例如表 `notification_outbox`：

```text
id
user_id
task_id
channel
content
status: pending | delivering | delivered | failed
attempt
next_retry_at
```

支持 Web / Feishu / WeChat / Slack / Push。

## 16. P2-3：权限边界

### 16.1 MCP / Skill

目前 MCP / Skill 为系统级资源，但管理 API 主要依赖普通 JWT。

必须明确：

- System MCP：Admin only
- User MCP（如果未来支持）：`mcp_servers.user_id`

Tool Resolution：

```text
Global Tools + User Tools = ResolvedToolSet
```

### 16.2 AgentExecutor Status 权限

所有 Task Get / Task Cancel / Task Status / Task Message 必须基于 `user_id` 做 ownership check。

## 17. P2-4：密钥安全

禁止生产环境 fallback 到固定 AES Key。当前类似：

```go
if key == "" {
    return defaultKey
}
```

必须改为：

```text
production + missing encryption key → startup failed
```

JWT Secret 同样处理。

原则：配置不安全时系统无法启动，而不是继续工作。

```go
type Message struct {

    Reasoning  string

    ToolCallID string
```

```text
       ↓

```

此项暂时不阻塞前面的 Context / Task 演进。

## 21. 暂时明确不做

为了避免 Agent 开发过程中扩大范围，以下事项暂时不做：

- **不做 Kubernetes Dynamic Agent Pod**：Agent 正常运行 Worker Runtime；只有真正需要 shell / code execution / browser / filesystem / build 才调用 Sandbox Execution Service / MCP。
- **不重写 Agent Framework**：现有 Agent Runtime / ReAct / Hook / Tool Provider / Sub Agent 继续演进。
- **不引入复杂固定 Role Agent**：继续保持 Generic Sub Agent + TaskSpec + Capabilities + Persona Hint + Deliverables + Completion Criteria。
- **不让 Context Manager 负责 Memory Search**：Context Manager 管 Compact / Recent / Conversation Recall；Memory 是 Agent Tool。
- **不追求 Compact 100% 信息保真**：完整信息存在 Conversation Store / Memory Store / Task Store / Artifact Store；Context 只需要保证当前 Agent 足够继续正确工作。

## 22. 最终概念模型

建议后续开发过程中始终按照下面的定义理解。

| 概念 | 定义 |
|------|------|
| Conversation | 用户与 Agent 的长期对话空间。通常一个用户 + 一个 Agent = 一个长期 Active Conversation |
| Turn | 一次用户意图及其后续执行的逻辑单元。可包含 User Message / Main Agent Response / AgentTask / Async Report |
| Message | 真实出现在用户聊天时间线中的消息，按 created_at 排序 |
| Task | 由某个 Turn 触发的异步执行任务，通过 origin_turn_id 建立因果关系 |
| Compact | 当前 Conversation 的 Working State。回答"这场对话现在进行到了哪里？" |
| Recent Raw | 最近发生的、尚未 Compact 的原始对话。确保近期上下文 100% 保真 |
| Conversation Recall | 自动从 Raw Conversation 中召回与当前问题相关的历史片段，用于补偿 Compact 的有损性 |
| Memory | 跨时间长期沉淀的用户、项目、偏好、决策知识，通过 memory_search 由 Agent 主动获取 |

## 25. 最终目标

完成以上演进后，OmniBot 应具备：

- 长期 Conversation
- 逻辑 Turn
- 异步 Task
- Context Compact
- Prompt Cache Friendly Context
- Conversation Auto Recall
- Agentic Memory Search
- Reliable Task Runtime
- Multi-channel Notification

最终形成 Conversation Runtime + Context Runtime + Agent Runtime + Task Runtime + Memory Runtime
五个相互独立但能够组合的核心能力。

其中最重要的边界是：

| Runtime | 职责 |
|---------|------|
| Conversation | 负责"发生了什么" |
| Context | 负责"模型现在必须知道什么" |
| Memory | 负责"过去还有什么值得重新找回来" |
| Agent | 负责"现在应该做什么" |
| Task Runtime | 负责"这件事情如何可靠地执行完" |

后续所有架构设计尽量不要破坏这五个边界。
