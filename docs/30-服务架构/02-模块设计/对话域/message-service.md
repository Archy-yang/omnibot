## 1. 这个服务解决什么问题？

**核心问题**：
1. 对话是有上下文的，用户说「把刚才的改一下」，机器人需要知道「刚才的」指的是什么
2. 上下文不能无限长，超过 Token 限制 LLM 就处理不了
3. 历史对话应该永久保存，用于后续记忆提取、分析、训练

**解决方案**：
消息服务统一管理所有对话历史，自动构建符合 Token 窗口的上下文，滑动窗口策略。

## 2. 核心领域模型

### Message 实体

| 字段 | 类型 | 说明 |
|------|------|------|
| ID | int64 | 主键 |
| UserID | int64 | 所属用户 ID，索引 |
| Role | string | 消息角色：user / assistant / system / tool，索引 |
| Content | string | 消息内容 |
| MsgID | string | 通道消息 ID（如微信 MsgID），唯一索引，用于去重 |
| CreatedAt | time.Time | 创建时间 |
| UpdatedAt | time.Time | 更新时间 |

### 角色定义

| 角色 | 说明 |
|------|------|
| `user` | 用户发送的消息 |
| `assistant` | AI 回复的消息 |
| `system` | 系统提示词，每次对话前自动插入 |
| `tool` | 工具调用结果（v1.4+ 预留） |

## 3. 服务接口

### 保存用户消息

```go
SaveUserMessage(userID int64, msgID string, content string) error
```

**行为**：
1. 自动去重：如果 msgID 已经存在，静默返回，不重复处理
2. 保存失败只打日志，不中断对话流程（降级策略）

### 保存 AI 回复

```go
SaveAssistantMessage(userID int64, content string) error
```

**行为**：
1. 没有去重（每次回复都是新的）
2. 同样是失败降级，不中断对话

### 构建上下文消息

```go
BuildContextMessages(userID int64, currentContent string) ([]llm.ChatMessage, error)
```

**核心算法：滑动窗口策略 + 长期记忆注入**

```
输入：用户 ID、当前消息
输出：LLM 可以直接用的 messages 数组

1. 查询用户最近 10 条长期记忆，构造 system message
2. 查询用户最近 N 条消息（默认 20 条 = 10 轮对话）
3. 按时间正序排列（旧的在前，新的在后）
4. 自动在最前面插入 system prompt
5. 返回完整的 messages 数组
```

长期记忆 system message 内容格式：

```text
以下是用户长期记忆，请在回答时自然参考，不要主动提及"我参考了记忆"：

1. 我偏好简洁直接的回答
2. 我正在开发 OmniBot 项目
```

**Token 控制**：
- v1.2 简化处理：固定最近 20 条消息，假设平均每条 100 Token，总 2000 Token
- v1.4+ 计划：真实 Token 计数 + 动态截断

### 统计用户消息数

```go
CountByUser(userID int64) (int64, error)
```

## 4. 上下文构建详细流程

```
用户发送新消息
    ↓
调用 BuildContextMessages(userID, 新消息)
    ↓
┌─ 查询最近 10 条长期记忆 → 构造 system message
│   "以下是用户长期记忆，请在回答时自然参考..."
│   1. 我偏好简洁直接的回答
│   2. 我正在开发 OmniBot 项目
└─
    ↓
┌─ 查询最近 20 条历史消息（按时间正序）
│   1. user: "你好"
│   2. assistant: "你好，有什么可以帮你？"
│   3. user: "怎么用微信登录？"
│   4. assistant: "点击右上角菜单..."
│   ...
└─
    ↓
自动插入 system prompt 到最前面
    ↓
┌─ 最终 messages 数组
│   0. {role: "system", content: "你是一个友好的客服..."}
│   1. {role: "system", content: "以下是用户长期记忆..."}
│   2. {role: "user", content: "你好"}
│   3. {role: "assistant", content: "你好，有什么可以帮你？"}
│   4. {role: "user", content: "怎么用微信登录？"}
│   5. {role: "assistant", content: "点击右上角菜单..."}
│   6. {role: "user", content: "刚才说的是哪个菜单？"}  ← 新消息
└─
    ↓
传给 LLM 客户端调用
```

## 5. 可靠性与降级策略

### 消息去重

- 依赖微信 MsgID 的唯一索引
- 重复消息：数据库唯一约束报错 → 捕获错误 → 打日志 → 正常处理
- 防止微信重试导致同一条消息被处理 N 次，用户收到重复回复

### 失败降级

**原则**：宁可丢失上下文，也不能让用户用不了

| 场景 | 降级策略 |
|------|---------|
| 保存用户消息失败 | 记录 WARN 日志，继续处理对话，上下文从这次开始断了就断了，下次再重新开始 |
| 保存 AI 回复失败 | 记录 WARN 日志，正常返回给用户，只是这次回复不会进入上下文 |
| 查询历史消息失败 | 记录 ERROR 日志，只返回 system prompt + 当前消息，不影响对话 |
| 查询长期记忆失败 | 记录 ERROR 日志，只使用短期上下文，不影响对话 |

## 6. 设计决策记录

### 决策1：为什么用滑动窗口，不是总结式记忆？
- **背景**：有两种常见的记忆策略：滑动窗口 vs 历史总结
- **决策**：v1.x 先用最简单的滑动窗口
- **原因**：
  - 滑动窗口实现最简单，零额外成本，不需要额外调用 LLM 总结
  - 90% 的场景最近 10 轮对话足够用了
  - 总结式记忆会引入新的错误源（总结错了反而更糟）
  - 未来可以叠加长期记忆（向量检索），两者不冲突

### 决策2：为什么消息保存失败不中断流程？
- **背景**：数据库挂了怎么办？让用户等吗？
- **决策**：保存失败只打日志，不影响对话
- **原因**：
  - 用户体验是第一位的，先能对话，记忆没了下次再补
  - 记忆是增强功能，不是核心功能
  - 数据库挂了一般是暂时的，恢复后还能继续记录
  - 如果把记忆当成核心依赖，反而会导致整个系统因为数据库挂了而不可用

### 决策3：为什么 MsgID 是唯一索引？
- **背景**：微信会重试最多 3 次，怎么防止重复处理？
- **决策**：数据库唯一索引兜底
- **原因**：
  - 应用层去重可能有竞态条件（两个请求同时进来，都没查到，都插入）
  - 数据库唯一索引是最可靠的去重方案
  - 性能影响可以忽略（索引查询很快）

### 决策4：为什么不分 channel 存消息？
- **背景**：多通道架构下，消息要不要和通道关联？
- **决策**：只关联 UserID，不关联 Channel
- **原因**：
  - 记忆是用户的，不是某个通道的
  - 用户在微信说的话，Web 端应该也能看到
  - 跨通道的记忆打通才是核心价值

## 7. 性能考虑

### 索引设计

| 索引 | 用途 |
|------|------|
| `user_id` | 按用户查询历史消息 |
| `role` | 按角色统计 |
| `msg_id` 唯一 | 消息去重 |

### 查询优化

- 只查需要的字段：UserID、Role、Content、CreatedAt
- 只查最近 N 条，LIMIT 20
- 按时间倒序查，然后反转（数据库索引优化）
