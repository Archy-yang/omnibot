## 1. 这个服务解决什么问题？

统一管理用户的生命周期：创建、查询、更新。所有通道共享同一个用户体系。

## 2. 核心领域模型

### User 实体

| 字段 | 类型 | 说明 |
|------|------|------|
| ID | int64 | 主键，全平台唯一 |
| Status | int | 用户状态：0=正常，1=禁用，2=已删除 |
| CreatedAt | time.Time | 创建时间 |
| UpdatedAt | time.Time | 更新时间 |

**设计说明**：User 实体极度精简，只保留最核心的信息，所有其他属性都通过关联表实现：
- 用户通道身份 → UserChannel 表
- 用户 LLM 配置 → LLMConfig 表
- 用户对话记录 → Message 表

## 3. 服务接口

### v1.3 以后推荐使用（多通道通用）

```go
GetOrCreateByChannel(
    channelType string,
    channelUserID string,
) (
    user *domain.User,
    channel *domain.UserChannel,
    isNew bool,
    err error,
)
```

**行为**：
1. 根据通道类型和通道用户 ID 查找关联
2. 找到 → 返回对应关联的用户
3. 没找到 → 创建新用户 + 创建通道关联
4. 微信通道会自动双写旧表（兼容 v1.2 数据）

### 兼容接口（v1.0 - v1.2 遗留）

```go
GetOrCreateByOpenID(openID string) (*domain.User, bool, error)
```

内部直接调用 `GetOrCreateByChannel("wechat", openID)`，行为完全一致。

**注意**：新代码请不要再用这个接口，未来会废弃。

## 4. 用户状态管理

### 状态枚举

| 状态值 | 含义 | 说明 |
|--------|------|------|
| 0 | 正常 | 可以正常使用所有功能 |
| 1 | 禁用 | 无法使用机器人，回复「您的账号已被禁用」 |
| 2 | 已删除 | 软删除标记，数据保留但不再使用 |

### 状态转换规则

- 新创建的用户默认状态 = 0（正常）
- 禁用用户可以重新启用
- 删除是软删除，不物理删除数据
- 状态变更需要记录审计日志（v1.4+ 实现）

## 5. 数据一致性策略

### 双写策略（v1.3 - v1.4）

微信通道创建用户时，同时写入两张表：
1. ✅ `users` + `user_channels`（新表）
2. ✅ `wechat_accounts`（旧表）

**读取策略**：优先读新表，读不到降级读旧表，读到后自动迁移。

### 最终一致性保证

- 创建用户是单数据库事务，原子性
- 双写失败不影响主流程（旧表写入失败只打日志）
- 有后台定时任务校验两张表的一致性（v1.4+ 实现）

## 6. 设计决策记录

### 决策1：为什么 User 实体这么「空」？
- **背景**：User 实体要不要加昵称、头像、邮箱等字段？
- **决策**：不加，User 只保留最核心的状态字段
- **原因**：
  - 不同通道的用户属性不一样（微信有 UnionID，飞书有 TenantID）
  - 统一放在 User 里会变成大杂烩，不同通道的字段都塞进去
  - 通道专属的属性放在 UserChannel 的 ChannelRawData 里
  - 未来可以扩展 UserProfile 表，按需加字段，不污染核心 User 表

### 决策2：为什么用软删除？
- **背景**：用户取消关注了，要不要删除数据？
- **决策**：软删除，只标记状态，不物理删除
- **原因**：
  - 用户可能重新关注，之前的对话记忆应该保留
  - 数据是宝贵资产，分析用户行为需要历史数据
  - 合规要求：用户主动要求删除时才物理删除
  - 存储成本很低，不值得省这点空间

### 决策3：为什么 GetOrCreateByChannel 返回 4 个参数？
- **背景**：接口返回参数是不是太多了？
- **决策**：就是要返回 4 个参数
- **原因**：
  - `user`：肯定要返回
  - `channel`：调用方经常需要通道关联的 ID 或额外数据
  - `isNew`：新用户需要触发欢迎语、埋点统计等
  - `err`：错误信息
  - 如果把这些拆开，调用方需要额外查好几次数据库，反而更慢
