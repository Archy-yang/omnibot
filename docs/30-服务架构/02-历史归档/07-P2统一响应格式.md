## 1. 问题

后端两套响应格式并存:
- **老端点**(memories/llm-config/chat 等):`{"success":true,"data":{...}}` / `{"success":false,"error":"..."}`
- **新端点**(v2.1 auth、v2.2/v2.3 channel-binding):裸对象 `{"token":"..."}` / `{"error":"..."}`

前端 axios 拦截器(request.ts)要求 `data.success===true` 才放行。新端点不满足,
导致 `auth.ts` / `channelBinding.ts` 不得不用裸 fetch 绕过拦截器,行为不一致。

## 2. 统一方向

**新端点向老端点看齐**:全部包 `{success, data, error?}` 外壳。
理由:老端点是多数派,前端拦截器 + `ApiResponse<T>` 类型契约都已就位;
让 2 个新端点改,比让 N 个老端点改 + 改拦截器代价小。

**不动 SSE 流式端点**(HandleSendMessageStream / HandleSendMessageAgentStream):
响应是 `text/event-stream`,不走 JSON,前端裸 fetch 单独处理,与本次统一无关。

如 `assert.Contains(w.Body, "token":"signed-token")` -> `assert.Contains(w.Body, "success":true)` + 解析 data.token。

## 4. 前端改动

### 4.1 删裸 fetch,回归 axios

`services/auth.ts`:删 postJSON 裸 fetch,改用 request(axios):
```ts
import { request } from '../utils/request';
// request.post 返 AxiosResponse<ApiResponse<T>>,拦截器已解包
const resp = await request.post<ApiResponse<{token:string}>>('/auth/register', body);
return resp.data.data.token;  // 拦截器保证 success=true
```
失败时拦截器 reject(Error(msg)),catch 里取 err.message 即原 toast 文案。
**401 特殊处理**:auth 端点本身可能返 401(登录失败),拦截器现会 `window.location.href='/login'`--
登录页本身就在 /login,会循环。需在拦截器或 auth service 里豁免 /auth/* 的 401 跳转。

`services/channelBinding.ts`:同款,删 authedJSON 裸 fetch,改 request。
401 豁免同上(channel-binding 不应返 401,但拦截器统一行为要稳)。

### 4.2 拦截器 401 豁免

`utils/request.ts` 的 401 分支:对 `/auth/*` 路径不跳转(登录失败不该把用户踢去登录页--
他就在登录)。判断 `error.config.url` 是否以 `/auth/` 开头。

### 4.3 测试/类型

`types/api.ts` 已有 ApiResponse 契约,无需改。
auth.ts 的 AuthResponse / channelBinding.ts 的接口类型调整为 `ApiResponse<T>` 解包后的 T。

  若要严格统一,middleware 也可包 success,但收益低,本次不做)
