## 三、新发现问题

### 🔴 P0-1 `manual` 记忆被静默截断 —— 行为回归

**位置**：`internal/service/chat/message_service.go:286-296`（`buildLongTermMemoryMessages`）

```go
// 预算内组装:manual 全量 → pinned auto 依次保留,超预算截断
kept := make([]string, 0, len(inj.Manual)+len(inj.PinnedAuto))
truncated := 0
used := 0
appendItem := func(item string) bool {
    cost := EstimateTokens(item) + 2 // 编号与换行开销
    if used+cost > s.memoryBlockMaxTokens {
        return false          // ← 不 append，整条丢弃
    }
    used += cost
    kept = append(kept, item)
    return true
}
for _, m := range inj.Manual {
    appendItem(m) // manual 全量优先:超预算也不截断(继续尝试下一条)   ← 注释与代码矛盾
}
for _, p := range inj.PinnedAuto {
    if !appendItem(p) {
        truncated++
    }
}
```

**四个问题叠加**：

1. **行为变了**：改造前 `manual` 是无预算全量注入（`git diff` 可见旧代码直接 `for i, memory := range manual`）；现在受 `DefaultMemoryBlockMaxTokens = 2000` 约束，超出的**整条丢弃**。
2. **注释说谎**：`message_service.go:296` 写「超预算也不截断」，实际 `appendItem` 返回 `false` 的分支就是不追加。这不是措辞问题——它会让后续维护者据此认为 manual 是安全的。
3. **丢弃无感**：存在性提示行只统计 auto（`message_service.go:302`：`inj.AutoCount - len(inj.PinnedAuto) + truncated`），**被丢掉的 manual 不产生任何提示**。用户亲口交代的记忆凭空消失，本人与排查者都无从察觉。这违反了项目「宁漏勿错」红线在可观测性上的推论。
4. **预算不可配**：`MessageServiceDeps` 没有对应字段，`message_service.go:146` 的 `if <= 0` 分支在生产路径恒真，`DefaultMemoryBlockMaxTokens` 实际是硬编码常量；只有测试能通过改私有字段覆盖（`turn_sink_test.go:216`）。

**与两处契约冲突**：

- 12 号文档 §6.5：「手动记忆（manual）= 常驻……**每轮全量注入**（小而有界）」
- 12 号文档 §14.2.4：「超限截断优先级：**manual 全量优先保留**（用户意志 > 助手笔记）」

**触发条件现实**：规范为「单条内容最大 200 个 Unicode 字符」，2000 token ≈ **10 条上下**，重度用户必然踩到。

**现有测试为何没发现**：`TestBuildContextMessages_PinnedBudgetTruncation`（`turn_sink_test.go:206`）的预算被刻意设为 `manualCost + pinCost + 1`，即"manual 恰好装得下"的情形——**恰好绕开了这个 bug**。建议补一个 `manual` 单独超预算的用例。

### 🟠 P2-5 loop 关闭缺"人工逃生口"（文档承诺未实现）

**位置**：12 号文档 §14.2.2 两处承诺 vs 实际路由表

§14.2.2 写：

> 「……**窗口外 loop 暂不可自动关闭，管理面提供手动关闭入口**」
> 「关闭 = 置 closed，检索过滤 closed，**可人工回滚**」

**实际**（`internal/api/routes.go:110-118`）：记忆路由只有 `GET` / `POST` / `DELETE` / `DELETE /:id` / `PUT /:id` / `PUT /:id/pin`。

- **没有任何 close/reopen 的 API**；
- 前端 `MemoryDrawer.vue` 本轮只加了置顶按钮，**没有关闭/重开 UI**。

**后果**（比"缺个入口"更严重）：

1. `ListOpenLoops`（`memory_repo.go:193`）按 `created_at ASC` 取**最旧** 20 条 → 语义恰好反了：**新 loop 最难被看到**，而新 loop 才是最可能刚被了结的；
2. 用户有 >20 个未决 loop 且模型未给出关闭信号时，第 21 条起**永远关不掉**；
3. 关闭后若要恢复，**也没有重开入口**——而 §14.2.2 把「可人工回滚」写成了安全垫。

**建议**：快照改为两端各取（或按 `updated_at DESC`），并补管理面关闭/重开 API + UI。这是 §14.2.2 承诺的组成部分，不是新增需求。

### 🟠 P2-6 loop 状态迁移的 DB 错误被完全吞掉

**位置**：`internal/service/memory/digest_reconcile.go:161-170`

```go
for _, id := range result.LoopCloses {
    if ok, err := p.memoryRepo.TransitionLoopStatus(id, userID, ...Open, ...Closed); err == nil && ok {
        stats.LoopsClosed++
    }
}
```

- `err != nil` 时：**不计数、不打日志、不重试**；
- 而 `RunOnce` 随后**照常推进水位**（`digest_pipeline.go` 水位推进在工作之后）→ 这条关闭指令**永久丢失**，用户不会看到任何异常。

**风格不一致**：同一函数的 matter upsert 失败有完整日志与 `continue`：

```go
if err := p.matterRepo.UpsertByTitle(matter); err != nil {
    logger.WarnWithFields("memory: 事项 upsert 失败,跳过该事项", ...)
    continue
}
```

「静默忽略不存在的 ID / 状态不符」是**有意设计**（幂等、防幻觉关闭），但**把 DB 错误与"未命中"合并处理**并非有意——二者的可观测性需求完全不同。

**建议**：拆开两类结果，`err != nil` 走 `logger.WarnWithFields`，并把失败计数写进 `artifact` 留痕。

文档写：

```go
func NormalizeKind(s string) string {
    switch s {
    case MemoryKindLoop:
        return s
    case MemoryKindEpisode:
        return MemoryKindFact
```

## 五、总体判断

**骨架没有恶化，问题与上轮同构，但这一轮的性质值得警惕。**

| 维度 | 判断 |
|------|------|
| **分层纯度** | ✅ domain 零内依赖、repository 不越层；问题仍集中在 api/service/channel 三层 |
| **模块边界** | ⚠️ service→service 边未收敛且本轮加深（P1-4） |
| **代码质量** | ✅ M8 四项实现扎实、测试先行、逻辑正确（`selectBatchCount`、CAS 迁移、closed 三态均经核对） |

| **文档治理** | ❌ 删旧彻底、立新滞后，并把权威指针指向最陈旧的一层（P0-2） |

**根因判断**（与上轮一致，但形态演进）：架构迭代速度持续快于文档同步。上轮的形态是"某份文献掉队"；本轮的形态是"**治理动作把掉队的文献扶成了权威**"。

> 文档整理不是「删掉旧的」，而是「**每一条被删的都必须有一个更新的继承者**」。本轮的删除动作缺少这一步校验。
