# lark-cli 多用户授权隔离调研（2026-10-11）

| 项 | 内容 |
|----|------|
| 问题 | 当前 feishu_tool 用系统级单一 lark-cli 授权（个人账号）；如何让 lark-cli 授权与 omnibot 登录用户关联，做到不同用户不同授权 |
| 方法 | 实机探针（lark-cli v1.0.94）：help 逐项核对 + 实际创建/删除测试 profile 验证隔离行为 |
| 结论 | **CLI 原生能力足够，无需 fork/hack**；推荐 per-user profile 路线，建议随"多用户化"整体立项（16 号 §16.1 同批） |

---

## 1. 现状

- `feishu_tool.go`（13 号 §7.5）：`exec.CommandContext` 直调 `lark-cli`，参数数组直传，**零凭证管理**——CLI 的 token 完全自管（device flow 一次授权 + 系统钥匙串自动刷新）。
- 授权身份 = 部署者本人的飞书账号（`cli_aaca2d8cb0a15ce1` / 杨琦）。所有 omnibot 用户共享这一个身份。
- 多用户数据基础已存在：`user_channels`（v2.2 飞书绑定：omnibot 用户 ↔ 飞书身份）、mcp_servers.UserID（按人隔离先例）。

## 2. lark-cli 能力事实（全部实测）

| 能力 | 实测结果 |
|------|---------|
| **Profile 机制** | `profile add --name X --app-id Y`（secret 走 stdin）/ `use` / `list` / `remove`；全局 `--profile` flag **按调用指定**，实测两 profile 完全隔离（whoami 各自独立、appsecret 分文件），remove 后文件即清 |
| **token 存储** | `~/Library/Application Support/lark-cli/`：`cli_<appId>_<openId>.enc`（按身份分文件）+ `appsecret_<appId>.enc`；加密 master.key 默认在 macOS 钥匙串 |
| **服务器场景钥匙串** | `config keychain-downgrade`（官方支持）：把 master.key 落为本地文件，供无钥匙串的沙箱/CI/无桌面 Linux 环境使用 |
| **非交互授权** | `auth login --no-wait --json` 发起后立即返回 verification URL；`--device-code` 二段完成——**官方注明为 AI agent 场景设计**，天然适配"URL 发给对应用户 → 用户浏览器确认 → 后台完成"的异步授权流 |
| **身份默认** | `config default-as [user\|bot\|auto]`（**profile 级**默认，非 per-call）；`strict-mode` 可限制身份策略 |

## 3. 方案对比

| 方案 | 思路 | 判断 |
|------|------|------|
| **A. per-user profile（推荐）** | 每个 omnibot 用户一个 profile（`user-<id>`）；feishu_tool 执行时按当前用户传 `--profile user-<id>`；授权走 `--no-wait` 发起 + URL 投递到该用户渠道 + `--device-code` 完成 | ✅ CLI 全部原生支持；隔离粒度干净；探针已验证 |
| B. 单 profile 多飞书身份 | 同一 appId 下 `auth login` 多次，token 按 openId 分文件 | ❌ 执行时**无 per-call 身份选择**（default-as 是 profile 级）——多用户会串身份，实测机制上不可行 |
| C. HOME 重定向隔离 | 每用户独立 HOME → 独立 Application Support | ❌ master.key 在系统钥匙串（与 HOME 无关），跨平台行为不确定；过度工程 |

## 4. 方案 A 的三个关键点

1. **共享 appId vs 各自 appId**：自建应用是租户内的——同企业多用户可共享一个 app（每用户一个 profile、同 appId）；跨租户用户必须各建应用。单用户/家庭部署场景基本是前者。
2. **工具执行链需要 user 上下文**：feishu_tool 现为静态 builder，Execute 签名无 user_id。改造点：把当前请求 user_id 传入工具执行 ctx（与记忆按人隔离的上下文同源），Execute 内拼 `--profile user-<id>`。
3. **授权编排**：新表（如 `user_larkcli_auth`：user_id ↔ profile_name/openId/状态）+ 授权流（对话触发 → `--no-wait` 拿 URL → 经该用户绑定渠道发出 → 用户确认后 `--device-code` 收尾落库）。与 v2.2 飞书绑定的 user_channels 数据同源。

## 5. 建议

- **不立即做**：当前单用户，方案 A 的收益要等第二个真实用户出现；且"按用户隔离授权"本质上属于**多用户化**工程（16 号路线图挂起项 §16.1 System MCP Admin 门禁明确"随登录/权限体系整体考虑"——lark-cli 授权与之同批最合适）。
- **立即可做的小步**（向后兼容，半小时级）：feishu_tool 增加可配置的 `--profile` 透传（config 默认空=现状），先把 CLI 调用层的口子留出来。
- 正式立项时按 16 号多用户化批次设计（user 上下文贯通 + 授权编排 + mcp Admin 门禁一起）。
