## 零、结论摘要

**做对了**：从开放式场景枚举改为封闭式判定流程，是唯一正确的结构性修法；并首次在 prompt 里显式建模了"子 Agent 拥有主 Agent 没有的执行能力"这一不对称性。

**核心问题**：`content.go:77-79` 仍然硬编码着两张能力清单——

```
   你的直调工具只覆盖"单点查询"级(mcp_call 查连接器、calculator 算式)。
   子 Agent 拥有大量**你没有的执行能力**——批量抓取、阅读网页、跑脚本/数据处理/
   精确计算(沙箱执行 Python/Shell)等;例如你自己没有代码执行能力。
```

这两句就是枚举，只是换了个维度。而这批数据**代码里全都有**（`ResolveSubAgentTools`、`toolcore.CapCode/CapWeb`、`RegisterBuiltinSubOnly`），属于"手工维护的代码数据镜像"。

**最有说服力的证据**：`content.go:77` 声称主 Agent 的直调工具"**只**覆盖 mcp_call、calculator"，但同一段 `:99` 的**第一个例子**"明天北京天气怎么样? → 直调"所依赖的 **`weather` 工具，恰恰不在这个清单里**（`wire.go:309` 明确以 `RegisterBuiltin` 注册给主 Agent）。**枚举在同一提交内就已腐烂。**

**解法**：prompt 中**不得出现任何会随工具/能力增减而变化的清单**。工具清单每轮由 `tools` 参数权威下发，prompt 只需给判据，并把"我知不知道对手方能力"从**断言**改为**默认保守**（拿不准就派活）。

## 三、核心问题：枚举上移了一层

### 3.1 新的能力清单依然是硬编码

`content.go:77-79` 的"直调工具清单"与"子 Agent 能力清单"，与代码中的权威数据一一对应：

| prompt 文本 | 代码中的权威来源 |
|-------------|-----------------|
| "批量抓取" | `wire.go:329` `RegisterBuiltinSubOnly(CreateRSSReaderTool)` |
| "阅读网页" | `wire.go:331` `RegisterBuiltinSubOnly(CreateWebReadTool)` |
| "跑脚本/数据处理/精确计算" | `wire.go:333` `RegisterBuiltinSubOnly(CreateSandboxRunTool)`，`toolcore.CapCode` |
| "子 Agent 拥有你没有的执行能力" | `tool_provider.go:13` `DefaultSubAgentCapabilities = {CapResearch, CapCode, CapInteractive}` |

**后果**：将来新增一个子 Agent 专属能力（图像理解、浏览器自动化…），仍需回来改这段 prompt——**与"加一个能力就补一个场景枚举"是同一耦合，只是表面积更小**。

### 3.2 它**已经失准了**（同一提交内的自相矛盾）

`content.go:77` 的断言 vs 主 Agent 工具池实测（`agentToolRegistry`，`wire.go:298-349`）：

| 工具 | 装配点 | 是否在 prompt 的"直调工具"枚举里 |
|------|--------|--------------------------------|
| `get_current_time` | `wire.go:303` | ❌ |
| `calculator` | `wire.go:305` | ✅ |
| `search_memories` | `wire.go:307` | ❌ |
| **`weather`** | `wire.go:309` | ❌ |
| `manage_subscriptions` | `wire.go:311` | ❌ |
| `feishu`（CLI 桥接） | `wire.go:327` | ❌ |
| `mcp_call` / `mcp_search` | `wire.go:348-349` | 只提 `mcp_call` |
| `delegate` / `query_task` / `update_task` / `cancel_task` | `wire.go:412-416` | 另段 |

最刺眼的是 **`weather`**——`content.go:99` 的**第一个例子**就是

```
- "明天北京天气怎么样?" → 直调,查完一句话答。
```

而 `wire.go:309-311` 的代码注释明确论证过天气为什么该给主 Agent：

> 天气(内置,NMC 中央气象台 REST,零 key):主 Agent 直调即答("今天穿什么")……**天气是单点结构化查询,不属"管家不亲自抓网页"的边界**

**代码注释把边界讲清楚了，prompt 的枚举却漏掉了它。** 后果是真实的：模型读到"我的直调工具只有 mcp_call 和 calculator"，遇到"明天天气"或"我订了哪些源"时，完全可能**推理出"我没有这个能力"**——正是本次重构要治的"宣布无能"，只是从"子 Agent 能力"那侧，换到了"主 Agent 能力"这侧。

> 这一条不需要推测：**枚举漏项是结构性的，不是偶然的**。清单与代码是两份真相，谁先改谁就对不上。

## 四、逐条优化建议

### 🔴 P0-1 —— 把枚举**删掉**，而不是换一个大一点的枚举

#### 方案甲（推荐）：删枚举，零架构改动，且不可能再腐烂

- **删掉主 Agent 工具清单**：它本来就在每轮请求的 `tools` 参数里，是实时、权威的。prompt 再抄一份只会腐烂。
- **删掉子 Agent 能力清单**：改为"另有一批你没有的执行能力，清单不在此列举"——把"我知不知道对手方能力"从**断言**变成**默认保守**（拿不准就派活）。

这样以后新增任何能力，**prompt 一个字都不用改**。这才是本次重构真正想要的效果。

#### 方案乙（可选进阶）：数据驱动注入

若确实希望 prompt 里展示子 Agent 能力，就不该手写，而应由代码生成：

```go
// 机制已具备，但生产代码零调用（DynamicSection / RegisterVariable 全仓无生产用法）
DynamicSection("delegation_capabilities", ScopeMain, 100, func(c PromptCtx) string {
    return c.Request["sub_agent_capabilities"] // 装配点从 ResolveSubAgentTools 渲染
})
```

> ⚠️ **分层代价（本方案不推荐）**：`agentprompt` 目前是**纯内容包**（仅依赖 `domainagent`），让它依赖
> `ToolRegistry` 会把 prompt 包耦合进工具层，违反 CLAUDE.md 分层约束。正确做法是由**装配点**
> （`wire.go` / `service/agent`）渲染成文本传入，`agentprompt` 只做插值：
>
> ```go
> BuildMainAgentSystemPrompt(hasSubAgents, MainPromptData{ SubAgentCapabilities: "…" })
> ```
>
> 代价：需改 `BuildMainAgentSystemPrompt(hasSubAgents bool)` 签名（`main.go:33`），并让
> `TestMainAgentMigration_Golden_*` 的输出变成运行时相关（确定性下降）。
> **收益（自动同步）与成本（签名变更 + 测试确定性下降）我判断不划算**——除非能力清单将来真长到需要展示。

### 🔴 P0-2 —— 把"无能宣言"升格进【铁律】

现状：禁令是**埋在能力关第 1 问里的一段长从句**（`content.go:80-81`）。而这个 prompt 自己在 `:62-63` 就总结过：

> 铁律必须短、狠、前置，禁令不重复

两件事故的严重性也是对称的——**编造 task_id** 与**虚假无能声明**是同一枚硬币的两面：都是**在没有工具证据的情况下，断言一个关于后台状态的事实**。

建议把铁律改为两条式（完整替换文本见 §七 PA）：

```
【铁律——只此两条,优先级最高】
一、说了就得做过: …delegate 真实调用 + task_id 来自返回值…
二、做不了就得有证据: …真的派活且后台也没做成之后才能说"做不了"…
```

好处：两件真实事故放在同一优先级、同一处、同样短狠；形成可记忆的总原则（"关于后台的断言必须有工具证据"），比两条散落的规则更不容易被风格段稀释。

---

### 🟠 P1-3 —— 两问其实不正交，"能力关"把"量级关"吃进去了

现状第 1 问是：

> 我手上的工具,**一次调用就能产出它要的结果吗**?

"**一次调用**"是量级维度，却被塞进能力维度。两问边界模糊，模型会重复判断同一件事。

建议改为真正正交：

- **能力关（有没有）**：我有没有能达成这个结果的工具？没有 → 派活。
- **量级关（值不值）**：有，但几步/多大？多步或大产出 → 派活。

同时建议**把真正的判据说白**——现在整段缺一句交代"为什么要在意"，导致"拿不准就派活"和"不要为这种小事派活"在同一段里互相拉扯，模型只能靠猜：

```
判据不是"我能不能",而是"多快能给用户有用的答复":
派活异步(先收一句确认、结果稍后到,能办大事);直调即时(一句话答完,但办不了大事、占上下文)。
```

### 🟠 P1-4 —— 新的"标准差"例子与第 1 问自相矛盾

`content.go:105` 新增：

```
- "用脚本算一下这组数据的标准差" → 派活(子 Agent 沙箱执行,你答不了)。
```

但 `:77` 说主 Agent **有 `calculator`**。模型完全可能推理："标准差是个公式，我有计算器，为什么要派活？"

真正区分二者的是**"用脚本"与"成批数据"**，而例子没写出来。建议点明判据，让它从"又一个要背的例子"变成"**原则的一次示范**"：

```
- "用脚本算一下这组数据的标准差" → 派活(calculator 只算单个算式;
  成批数据、要写脚本处理/验证的,走子 Agent 沙箱)。
```

### 🟠 P2-5 —— 同样的病还长在另外两段里

病灶不只派活规则一处。**凡"prompt 抄了 tool description"的地方，都会与工具实现脱节。**

#### `MainSubscriptionRulesPrompt`（`content.go:137-143`）

`subscription_tools.go:28` 的 `Description` 已包含：

> action=add 订阅(...工具自动发现其 RSS 地址...);action=list 查看订阅清单(含每个源的主题描述);action=remove 退订;action=pause/resume 暂停/恢复(按 id)。**用户说'订阅X/我关注X的博客/帮我盯着X'时调用 add;用户问'我订了哪些'时调用 list。**

而 prompt 又说了一遍 action 列表、feed 自动发现、触发语。**改工具 action 集合 → 两处都要改。**

#### `MainTaskMgmtToolsPrompt`（`content.go:122-134`）

`task_tools.go:17/71/107` 的 `query_task`/`cancel_task`/`update_task` 描述里已写了职责与触发时机。prompt 该留的是**策略**（"不要凭记忆回答任务状态"）与**跨工具工作流**（`input_required` 补 note 不会自动续跑、需重新 delegate），而不是三个工具各自的触发语。

#### 建议固化为一条原则（写进 11-Prompt 管理 §3.5）

> **prompt = 策略 / 判据 / 跨工具工作流；工具名、参数、单工具用法与触发时机 = 该工具的 `Description`。**
>
> 理由：tool description 随每轮 `tools` 参数权威下发，与实现天然同步；prompt 里的副本一定会脱节。

### 🟡 P2-6 —— `agent_base` 是英文通用助手，与管家人设打架

`content.go:9-12`：

```go
var DefaultSystemPrompt = `You are a helpful AI assistant with access to tools.
When you need information, use the available tools to get it.
After receiving tool results, use them to provide a complete and helpful answer.
If a tool call fails, try a different approach or let the user know.`
```

两个问题叠在一起：

1. **人格冲突**：它是 order `-100`、整个 system prompt 的**第一段**——模型对"我是谁"的第一印象说"helpful AI assistant"；紧接 `-90` 的 `MainResponseStylePrompt` 却说"你是用户的私人管家"。且产品为全中文场景，第一段是英文。
2. **一物两用**：注释说明它同时是"ReActAgent 在未显式配置 SystemPrompt 时的兜底默认"。一个常量要同时满足"主 Agent 人格底座"与"无配置兜底"，两边互相牵制，谁都不敢改。

建议二选一：
- **甲**：主 Agent 拆出 `MainAgentBasePrompt`（中文、管家、无派活假设），`DefaultSystemPrompt` 退回纯兜底；
- **乙（本 patch 给出，改动更小）**：把 `DefaultSystemPrompt` 改为中文并与管家定位一致，兜底场景复用同一份（接受它带管家色彩）。

### 🟡 P3-7 —— 回归手段：现有守护测试锁的是"措辞"，不是"行为"

`main_test.go:71-106` 的方式是断言**关键句字符串存在**（`"先问能力,再问量级"`、`"替它宣布无能"`…）。价值是"防手滑删句"，但它：

- **锁不住语义**——改写同义句就红，行为变坏却可能全绿；
- **与重构强耦合**：本次就把 10 个关键句换了一遍（`main_test.go` 改了 20 行）。**每次改 prompt 都要改测试**，测试成了改动的税。

两个更划算的补充（不替代现有断言）：

1. **冻结 golden 文件**：把 `BuildMainAgentSystemPrompt(true)` 的完整输出落成 `testdata/main_prompt.golden`，逐字节比对。这样**任何 prompt 变化都会在 code review 里显示成一段 diff**——让人看见改了哪句话。
   > 现有的 `TestMainAgentMigration_Golden_*`（`main_test.go:16-30`）是"组装结果 == 同一批常量的朴素拼接"，**自指**，只能防 registry 回归，防不了内容漂移。
2. **行为回放集**：准备 20~30 条真实请求 + 期望决策（直调/派活），跑真实模型看命中率。本次两个事故（游玩规划被直调、计算被拒答）本该是这个集合的头两条。**只有它能回答"改完是变好还是变坏"**，字符串断言永远回答不了。

---

### 🟡 P3-8 —— 结构：这块该拆了

`MainDelegationRulesPrompt` 已是 **~50 行**的单常量，内含 7 段（铁律 / 判断原则 / 直调的样子 / 派活的样子 / 派活自检 / 例子 / 怎么派）。而 registry **本就支持拆 section**。

拆的好处不是"好看"，是**可独立演进与测试**：铁律改一行不必动例子；例子可以单独替换为回放集驱动的版本。当前 `MainAgentSections`（`main.go:12-29`）只用 `StaticSection`，拆 section 是零成本的（改几个 order 常量 + 拆常量）。

### PA —— 派活段落：铁律两条式 + 判断原则去枚举（P0-1 + P0-2 + P1-3）

**目标位置**：`internal/agentprompt/content.go:66-92`（`== 派活规则==` 起，到 `【派活的样子】` 段末；**不动**其后的 `【派活自检】`、`【例子】`、`【怎么派】`）

**现状原文**：

```
== 派活规则==

【铁律——只此一条,优先级最高】
"已安排 / 已让后台处理 / 稍后汇报 / 任务 #N"这类话,**只有当你本轮真实调用了 delegate 工具、
且引用的正是它返回的 task_id 时才能说**。没调工具就说"还没安排,我现在派活"。
task_id 只能来自 delegate 的返回值,**严禁编造、推算(如"上次编号+1")或沿用历史编号**——
后台没有那个任务,用户一追问你就当场穿帮。

【判断原则——先问能力,再问量级,不按场景套】
每条请求先过两问,组合起来决定直调还是派活:
1. 能力关:我手上的工具,一次调用就能产出它要的结果吗?
   你的直调工具只覆盖"单点查询"级(mcp_call 查连接器、calculator 算式)。
   子 Agent 拥有大量**你没有的执行能力**——批量抓取、阅读网页、跑脚本/数据处理/
   精确计算(沙箱执行 Python/Shell)等;例如你自己没有代码执行能力。
   所以**不具备的能力不要硬答**:"没有 python 环境""这个我做不了"这类无能宣言,
   必须发生在确认后台执行器也做不了之后;拿不准就派活让它试,而不是替它宣布无能。
2. 量级关:即使能力够,总共要几步、产出多大?
   一两次调用、一句话能答 → 直调;三处以上、需要编排成方案,或产出会撑满上下文
   (整页正文、成批列表、多步检索跨来源汇总) → 派活——**即使手上连接器工具能查,
   也不要自己连查带算**:边查边答既拖慢回复又占满上下文。并发一次发多个查询也算
   多处,不要自欺。

【直调的样子】单点实时查询,现场一句话答:查个天气、找某一家店、看某地怎么走、
查某物的价格、算一个式子。不要为这种小事派活。
【派活的样子】凡是"先查/先算一大批,再整理成成果"的活,第一步就 delegate:
研究调研、总结汇总、抓网页、行程规划、对比分析、代码执行、数据处理,等等——
这个清单只是示例,拿不准时回到上面两问重新判断。
```
