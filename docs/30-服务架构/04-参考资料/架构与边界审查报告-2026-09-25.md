## 4. 总体结论

**一句话**：代码本身很健康，但**"设计基线"和"实际架构"已脱节整整一代**；分层约束在**最内层（domain / repository）守得很好**，在**最外层（api）和 service 内部**明显侵蚀；模块边界最大的问题不在模块之间，而在 **service 层内部把多个 Runtime 揉成了少数几个"上帝服务"**。

三个问题的直接判定：

| 问题 | 判定 |
|------|------|
| 是否偏离设计 | **是**。文档落后代码两代 + 宪章级基线被单方面突破 |
| 各层级是否清晰 | **内清外浊**。domain / repository 干净，api / service / channel 三层边界破损 |
| 模块边界是否符合预期 | **否**。核心问题是 service 内部 Runtime 边界塌陷 |

**根因判断**：不是零散小毛病，而是**同一条主线**——架构迭代速度远超文档同步与边界维护的速度，导致**宪章、路线图、模块文档、主线分支**四者同时落后于代码。

**现象**

`docs/10-宪章/单一长期对话模型.md:58` 是与产品愿景同级的硬约束：

**依据**

> 状态：草案（讨论稿）

**建议方向**：二选一并落文档——(a) 修订 `单一长期对话模型.md`，承认 Conversation/Turn 是**内部实现锚点**（产品仍单对话）；(b) 回退数据模型。**不允许宪章与代码长期各说各话。**

### 6.1 service 层三个硬伤

**(a) `...interface{}` + 运行时 type switch 做依赖注入**

```go
// internal/service/chat/message_service.go:106-135
func NewMessageService(msgRepo chatrepo.MessageRepository, optionalServices ...interface{}) MessageService {
    for _, svc := range optionalServices {
        switch s := svc.(type) {
        case MemoryInjectionProvider: ...
        case chatrepo.AgentStepRepository: ...
        case ConversationRepository: ...
        case ContextStateRepository: ...
        case ContextCompactor: ...
        case RecallSearcher: ...
        case TurnSink: ...
```

同一模式见 `internal/api/wechat/handler.go:177-184`。

代价：真实依赖集（`messageService` 实际 9 个依赖）无法从签名看出；编译期零保护；传错/漏传不报错；`wire.go` 需 200+ 行 append 拼装。

**(b) `messageService` 一个结构体吸收 4 个 Runtime**

doc 16 §25 定义五个边界（Conversation / Context / Memory / Agent / Task），并要求"尽量不要破坏"。`messageService` 独自吸收其中 4 个：

| 职责 | 字段 |
|------|------|
| Conversation | `msgRepo`、`convRepo`、SaveUserMessage 建 Turn |
| Context | `contextStateRepo`、`compactor`、`keepRecentTokens` |
| Memory 注入 | `memorySvc MemoryInjectionProvider` |
| Recall | `recall RecallSearcher` |
| 广播 | `turnSinks []TurnSink` |

**(c) service 层内藏 HTTP 客户端**

`internal/service/agent/llm_adapter.go`（496 行）实现 `OpenAILLMClient`：`buildAgentRequest:165`、`chatCompletionOnce:201`、`ChatCompletionStream:283`，含重试与 DSML 解析。而基础设施层已有 `internal/client/llm/openai.go:21`。两套 OpenAI 客户端并存，使用方分裂：

- `client/llm`：chat、feishu、api/web、api/wechat
- `agent.OpenAILLMClient`：agent、sub_agent、feishu notifier、api handlers

**另**：`internal/service/knowledge/`、`internal/service/wechat/` 为空目录。

## 7. 各模块边界

### 7.1 对话 / 消息 ❌ 边界塌陷

`messageService` 混合消息持久化 + 记忆注入 + 步骤落库 + Turn 管理 + Context Compact + Recall + TurnSink 广播。**全项目最严重的模块边界问题。**

### 7.2 记忆 / 上下文 🟠

| # | 问题 | 证据 |
|---|------|------|
| 1 | chat → memory 反向依赖（取向量能力） | `internal/service/chat/chunk_embedder.go:10`、`internal/service/chat/recall.go:10` |
| 2 | 召回算法与召回入口分居两包 | 定义 `internal/service/memory/retrieval.go:33`；使用 `internal/service/chat/recall.go:115` |
| 3 | 两套几乎相同的增量嵌入器（注释自承"同款"） | `internal/service/memory/message_embedder.go:19` vs `internal/service/chat/chunk_embedder.go:21` |
| 4 | TurnSink 接口与实现跨包 | 接口 `internal/service/chat/message_service.go:74`；实现 `memory/digest_pipeline.go:113`、`memory/message_embedder.go:70`、`chat/chunk_embedder.go:63` |
| 5 | 水位概念三分裂 | `internal/repository/memory/watermark_repo.go:13`、`internal/repository/memory/message_embedding_repo.go:44`、`internal/repository/chat/conversation_chunk_repo.go:14` |
| 6 | memory → conversation 域渗透 | `internal/service/memory/memory_service.go:9`、`internal/service/memory/digest_pipeline.go:12` |

**净结论**：memory 包同时承担"沉淀 + 检索 + 向量"三职，向量与水位能力外溢到 chat，**chat ↔ memory 双向依赖**，缺少独立向量/召回层。
