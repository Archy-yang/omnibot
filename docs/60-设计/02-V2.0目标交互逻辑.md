> **文档地位**：本文档是 V2.0 所有 UI 迭代的基线参考。后续每一次页面设计、组件开发、交互优化都必须与此文档保持一致。如有冲突，需先修改本文档。

## 一、产品本质

OmniBot 不是"聊天工具"，是**一个有记忆的、跨平台的私人助理**。

类比对象不是 ChatGPT，而是**微信里的一个始终在线的好友** — 打开就是对话，不用选择会话、不用新建话题、所有入口共享同一个"关系"。

---

## 二、核心交互模型

```
用户 ──(任意入口)──→ OmniBot
                      │
                      ├─ 对话（主循环）
                      ├─ 记忆（持久层）
                      └─ 工具（能力层）
```

三条主线的优先级：**记忆 > 对话 > 工具**

---

## 三、主交互流程（对话循环）

```
用户发送消息
  │
  ▼
构建上下文（最近 N 轮对话 + 最近 10 条长期记忆）
  │
  ▼
LLM 推理（是否需要调用工具？）
  │
  ├── 不需要 → 直接生成回复 → 保存消息 → 返回用户
  │
  └── 需要 → 进入 Agent 循环：
              │
              ▼
         调用工具 → 获取结果 → 回传 LLM → 继续推理
              │
              ▼（重复，直到最终回复）
              │
              保存消息 → 返回用户
```

### 3.1 对话循环说明

- 用户发送消息后，系统自动构建上下文（短期对话 + 长期记忆）
- LLM 根据上下文推理，判断是否需要调用工具
- 如果不需要工具，直接生成文本回复
- 如果需要工具，进入 Agent ReAct 循环（思考 → 行动 → 观察 → 思考）
- 循环终止条件：LLM 返回无 tool_calls 的文本 / 达到最大步数（10）/ 超时（120s）/ 用户取消
- 所有对话消息按 `user_id` 落库，不引入 session 概念

---

## 四、记忆交互流程

记忆是 OmniBot 与 ChatGPT 的根本区别，分为两个方向：

### 4.1 记忆使用（对用户透明）

```
用户发消息
  → 系统自动注入最近 10 条长期记忆到上下文
  → LLM 基于记忆生成更贴合用户的回复
  → 用户无感知
```

- 记忆注入是自动的、静默的，界面不额外提示"已参考长期记忆"
- 记忆注入失败时降级为无记忆对话，不影响正常回复

### 4.2 记忆管理（用户主动操作）

```
查看记忆 → 列表展示已保存的全部长期记忆
新增记忆 → 输入内容 → 安全校验（敏感信息提醒）→ 保存
编辑记忆 → 修改内容 → 保存
删除记忆 → 单条删除 / 清空全部（二次确认）
```

- 单条记忆最大 200 字符
- 安全校验：保存时展示"不要保存密码、API Key、身份证号等敏感信息"提醒
- 记忆与对话历史是两套独立数据，互不影响

## 五、工具交互流程（Agent 能力）

```
用户提出需求（如"帮我查一下现在的北京时间"）
  │
  ▼
LLM 判断需要调用工具 → 发起 tool_call
  │
  ▼
Agent 执行工具（如 get_current_time）
  │
  ▼
工具结果回传 LLM → LLM 生成最终回复
  │
  ▼
前端展示：
  - 折叠的思考过程（可展开查看详情）
  - 最终回复
```

### 5.1 当前内置工具

| 工具名 | 功能 | 参数 |
|--------|------|------|
| `search_memories` | 搜索用户的长期记忆 | `query: string` |
| `search_history` | 搜索对话历史 | `query: string, limit?: int` |
| `get_current_time` | 获取当前时间 | 无 |
| `calculator` | 数学计算 | `expression: string` |

### 5.2 前端展示规则

- 工具调用过程折叠显示（可展开查看详情）
- 思考过程用不同颜色/图标区分
- 最终回复正常展示
- 通过 SSE 实时推送 agent_step 事件

## 六、Web 端页面交互流程

基于"单一长期对话"决策，Web 端的核心交互路径：

```
打开 Web 页面
  │
  ▼
直接进入对话界面（不是空白输入框，而是"继续上次"）
  │
  ├── 有历史消息 → 展示最近对话，底部输入框待命
  │
  └── 无历史消息（新用户）→ 展示简短的欢迎引导 + 输入框
  │
  ▼
用户输入消息 → 对话循环开始
  │
  ▼
对话过程中，助理可能：
  - 直接回复文字
  - 调用工具（展示思考过程）
  - 引用记忆（用户可感知或无感知）
  │
  ▼
管理入口（通过导航，非侧边栏会话列表）：
  ├── 模型配置（服务商、模型、API Key）
  ├── 长期记忆管理（查看/新增/编辑/删除）
  └── 关于（版本、接入入口、源码）
```

### 6.1 Web 端禁止事项

| 禁止 | 原因 |
|------|------|
| 不提供"新建对话"按钮 | 违反"单一长期对话"决策 |
| 不提供会话列表/会话切换 | 对话即关系，不需要选择 |
| 不引入 session/conversation 概念 | 数据模型按 `user_id` 索引 |

### 6.2 Web 端核心页面

| 页面 | 类型 | 说明 |
|------|------|------|
| 对话主页 | 主页面 | 单一对话界面，直接进入，无选择 |
| 设置面板 | 弹窗/抽屉 | 模型配置 + 记忆管理 + 关于信息 |

## 七、关键设计原则

| 原则 | 来源 | 含义 |
|------|------|------|
| 单一对话 | `单一长期对话模型.md` | 每个用户只有一个永久对话，不可新建、不可切换、不可删除 |
| 记忆优先 | `product-vision-v2.0.md` | 任何功能与记忆冲突时，优先保证记忆正确性 |
| 入口无关 | `product-vision-v2.0.md` | Web/微信/飞书/API 共享同一用户的记忆和对话 |
| 渐进式增强 | `product-vision-v2.0.md` | 每个版本在前一版本基础上平滑升级，无破坏性变更 |
| 记忆与对话分离 | `单一长期对话模型.md` | 清空对话历史不影响长期记忆，反之亦然 |

## 八、与 V1.x 页面的核心冲突

以下 V1.x 设计元素违反 V2.0 目标交互逻辑，必须在迭代中移除或改造：

| V1.x 设计 | 冲突点 | V2.0 方向 |
|-----------|--------|-----------|
| 侧边栏会话列表 | 违反"单一对话"决策 | 移除，改为导航/工具入口 |
| "新聊天"按钮 | 违反"不提供新建对话" | 移除 |
| 空白输入框冷启动 | 不是助理体验 | 展示上下文延续感 |
| 记忆藏在设置面板 | 记忆是核心能力，应是一等公民 | 记忆管理提升为独立入口 |
| 纯对话无 Agent 展示 | 忽略工具调用思考过程 | 需要思考过程可视化 |

## 九、后续迭代指引

### 每次迭代前的检查清单

- [ ] 本次改动是否符合"单一对话"原则？
- [ ] 是否引入了 session/conversation/会话列表 等概念？
- [ ] 记忆相关功能是否保持独立于对话历史？
- [ ] 是否保持了入口无关性（Web 端改动不影响微信/飞书）？
- [ ] 是否为渐进式增强（不破坏现有功能）？

### 迭代优先级建议

1. **移除会话列表**：删除侧边栏中的历史会话列表和"新聊天"按钮
2. **重构导航**：将会话列表侧边栏改为功能导航（对话/记忆/设置）
3. **记忆管理提升**：将记忆管理从设置面板中独立出来
4. **Agent 展示优化**：完善工具调用过程的可视化展示
5. **欢迎体验改造**：从空白输入框改为有上下文延续感的欢迎页
