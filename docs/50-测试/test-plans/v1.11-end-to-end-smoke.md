## 测试目标

把 v1.5 ~ v1.10 累积 6 个迭代的**真实运行验证**一次性还清。每个迭代都在 master,
但都没跑过真实端到端 smoke——本计划把这笔技术债清空,为 v2.0 发布扫清前置阻碍。

**核心原则**(来自 `verify` 技能):
> verification 是运行时观察。你建好 app,跑起来,把变更代码驱动到执行,记录你看到的。
> 那记录就是证据。其他都不是。

## Phase 1:准备凭证(必做,几小时)

### 1.1 LLM 凭证(走 Web UI,不进 config.yaml)

**重要修正(2026-06-28)**:v1.4 / v1.4.1 已经把「用户自定义 LLM 配置」做完(设置面板 →
保存到 `user_llm_configs` 表,加密存储,命中时覆盖 system default)。**真实凭证全程走 Web UI**,
不写进 `configs/config.yaml`,避免误提交真实密钥、也顺手把 v1.4.1 的核心入口路径再走一遍。

`configs/config.yaml` 的 `llm` 段保持**占位**即可,后端启动需要这块能解析但不必能调通:

```yaml
llm:
  routing:
    default: openai
    fallback_order: []
  providers:
    openai:
      api_key: ""           # 留空,凭证走 Web 设置面板
      base_url: "https://api.openai.com/v1"
      model: "gpt-4o-mini"
      timeout: "30s"
```

启动后,**Phase 2.2 进设置面板**配真实凭证(DeepSeek / 豆包 / 通义,任选一家便宜稳定的
OpenAI 兼容服务商)→ 保存 → 加密落 `user_llm_configs` 表。Phase 2.3 ~ 3.x 全部命中
这份自定义配置(顺带把 v1.8 跨入口配置共享也验证了)。

> **预算估算**:整个 smoke 走下来大约 10~30 次 LLM 调用,DeepSeek 不到 1 块钱。

> **已部分验证(2026-06-28)**:用户已经在本地真实跑过 Web 端「自定义 LLM 配置 + 调用」
> 路径,访问没问题——这条最关键的子链路已绿,Phase 2.2 / 2.3 复跑时主要看 Provider 预设
> 的分组、disabled 拦截、保存持久化等**未覆盖的边界**。

### 1.2 飞书自建应用(Phase 3 用)

在飞书开放平台:

1. 创建**自建应用**(企业内部应用,无需审核)
2. 开启**机器人能力**,配置**长连接**接收(无需公网 URL)
3. 添加事件订阅:`im.message.receive_v1`
4. 添加权限:`im:message`(接收单聊消息)、`im:message:send_as_bot`(发消息)
5. 把应用上架到企业内,加机器人到通讯录

`configs/config.yaml` 加:

```yaml
feishu:
  app_id: "cli_xxx"
  app_secret: "your_secret"
  enabled: true
```

### 1.3(选做)微信测试号 + ngrok

只有要做 Phase 4 才需要:

1. 申请[微信公众平台测试号](https://mp.weixin.qq.com/debug/cgi-bin/sandbox?t=sandbox/login)(无需备案)
2. 安装 ngrok 或 cloudflared
3. `ngrok http 8080` 拿到公网 URL
4. 测试号后台配置 URL 为 `https://xxx.ngrok.io/wechat/callback`,Token 与 config 对齐

```yaml
wechat:
  app_id: "wx_test_xxx"
  app_secret: "your_test_secret"
  token: "your_token"
  callback_url: "https://xxx.ngrok.io/wechat/callback"
```

### 1.4 数据库

Postgres 推荐(项目已支持双驱动)。docker 跑一个就行:

```bash
docker run -d --name omnibot-pg \
  -e POSTGRES_PASSWORD=test123 \
  -e POSTGRES_USER=test \
  -e POSTGRES_DB=omnibot_test \
  -p 5433:5432 \
  pgvector/pgvector:pg16
```

`configs/config.yaml`:

```yaml
database:
  driver: postgres
  dsn: "host=localhost port=5433 user=test password=test123 dbname=omnibot_test sslmode=disable"
  max_conns: 10
```

### 1.5 启动

```bash
./start.sh dev
```

日志应见:
- `Database initialized successfully`(驱动 = postgres)
- `Server starting on :8080`
- 若飞书启用:`feishu: starting long connection`
- 浏览器开 http://127.0.0.1:5173/

### 2.3 v1.5 Agent 真流式 + 工具调用

打开聊天页,**直接命中 Phase 2.2 刚配的自定义 LLM**(不需要切回 system default):

| 用户输入 | 预期 Agent 行为 | 验证点 |
|---------|---------------|--------|
| `你好` | 不调工具,直接流式输出 | token 实时出现 |
| `现在几点了` | 调 `get_current_time` 工具 → 文本回复 | 状态条「正在调用 获取当前时间」→ 折叠;最终文本是真实时间 |
| `帮我算 (123+456)*7 等于多少` | 调 `calculator` 工具 → 文本回复 4053 | 状态条「正在调用 计算器」;答案正确 |
| `我有哪些长期记忆` | 调 `search_memories` 工具 → 文本回复 | 列表对应 Phase 2.4 添加的记忆 |

**SQL 验证**(Postgres):
```sql
SELECT id, role, substring(content, 1, 50) AS content_preview, msg_type, created_at
FROM messages WHERE user_id = 1 ORDER BY id DESC LIMIT 10;

SELECT id, message_id, seq, kind, tool, status, duration_ms
FROM agent_steps WHERE user_id = 1 ORDER BY message_id DESC, seq ASC LIMIT 20;
```

- ✅ `messages` 表 user/assistant 消息成对,segments JSON 列完整
- ✅ `agent_steps` 表每轮 Agent 一条完整链:`llm_call`(用工具决策) → `tool_call` → `llm_call`(最终回复)
- ✅ `tool_call` 的 `response` 字段是**原始未脱敏**结果(v1.5.5 决策)

## Phase 3:飞书端真实 smoke(必做,半天)

> **LLM 凭证**:飞书端**不需要单独配 LLM**——Phase 2.2 已在 `user_llm_configs` 表加密落了
> 用户自定义配置,只要把飞书 OpenID 通过 Phase 3.2 的 SQL 改成同一 user_id,跨入口就会自动
> 共享同一份 LLM 配置。这是 v1.8 UserChannels 架构能力的核心卖点之一,本 Phase 顺手验证。

### 3.1 单聊基础对话

把机器人加为好友,**单聊**发消息:

| 输入 | 预期 |
|------|------|
| `你好` | 机器人回复,不调工具 |
| `现在几点了` | 调 `get_current_time`,回复真实时间 |
| `帮我算 999 * 88` | 调 `calculator`,回复 87912 |
| `你能做什么` | 介绍能力,可能调工具或不调,取决于 LLM |

**SQL 验证**:
```sql
SELECT id, user_id, channel_type, channel_user_id FROM user_channels WHERE channel_type = 'feishu';
SELECT count(*) FROM messages WHERE user_id = (上面查到的 user_id);
SELECT * FROM agent_steps WHERE user_id = (上面查到的 user_id) LIMIT 10;
```

- ✅ `user_channels` 表新增一条 `channel_type=feishu` 记录
- ✅ `messages` 落库,user/assistant 成对
- ✅ `agent_steps` 同步路径也落库(v1.6 关键决策:同步 Run 是 RunStream 聚合层)

### 3.2 跨入口能力共享(v1.8 核心)

**前提**:Web 端和飞书端目前是两个独立 user_id(因为没做跨入口绑定流程)。
**但同一 user_id 内,通道路径已经统一**——这一点能否验证看下面。

方法:**在飞书端先用一个新 OpenID,然后用 SQL 把它的 user_id 临时改成 Web 用户的 user_id**,验证跨入口记忆是否真的共享。

```sql
-- 假设 Web 端 user_id = 1,飞书端某 OpenID 创建出来 user_id = 5
UPDATE user_channels SET user_id = 1 WHERE channel_type = 'feishu' AND user_id = 5;
DELETE FROM users WHERE id = 5;  -- 清掉孤儿
```

然后飞书端发:`我有哪些长期记忆`

| 预期 | 验证点 |
|------|--------|
| 飞书端能看到 Phase 2.4 在 Web 端记的「我偏好简洁直接的回答」 | 跨入口记忆共享生效 |
| 在 Web 端配的自定义 LLM 也应用到飞书对话 | 跨入口配置共享生效 |

> **注意**:这只是验证「**架构能力**」可用,不是「**用户可用**」的功能——后者需要 v2.x
> 跨入口主动绑定流程。本步骤纯架构验证。

## Phase 5:问题整理 + 修复决策(必做,半天)

### 5.1 问题分级

把 Phase 2~4 发现的所有「不符合预期」整理成清单:

| 级别 | 定义 | 示例 |
|------|------|------|
| **P0** | 主流程崩溃 / 数据错乱 / 安全漏洞 | Agent 流式 panic;消息落错 user_id;密钥日志泄露 |
| **P1** | 非主流程错误 / 体验问题 / 边界 case 失败 | 边界 case 工具失败时回复不合理;UI 在某宽度错位 |
| **P2** | 视觉问题 / 文案不当 / 优化建议 | Tab 间距偏紧;某文案有歧义 |

### 5.2 修复决策

| 级别 | 处理 |
|------|------|
| **P0** | **立即修**,hotfix 独立提交,smoke 重跑 |
| **P1** | 列入 issue,v2.0 发布前修复 |
| **P2** | 列入 backlog,v2.0 之后处理 |

### 5.3 落地

- 把发现项写成测试报告:`docs/50-测试/test-reports/v1.11-smoke-report.md`
- 把 P0 修复以独立 commit 走 TDD 流程
- 把 P1 列入 PRD backlog 或 CHANGELOG 下一版
- 把 P2 列入 `docs/40-踩坑记录/` 或 backlog

### 5.4 完成标准

- [ ] Phase 2 Web 端必做项全部 ✅ 或 P0 已修复
