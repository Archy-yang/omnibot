## 发现的问题

### P2-1:响应格式不一致(体验问题,非阻塞)

**现象**:同一后端两套响应格式:
- memories / llm-config / chat 等老端点:`{"data":..., "success":true}`
- auth / channel-binding 等新端点:裸 `{...}`(无 success 字段)

**影响**:前端 axios 拦截器要求 `data.success===true` 才放行,导致新端点
(auth/channel-binding)前端不得不用裸 fetch 绕过拦截器(见 `auth.ts` / `channelBinding.ts`)。
功能能用,但风格不统一,后续加端点要每次判断走哪条路。

**根因**:v2.1 auth handler 直接 `c.JSON(status, struct{...})`,没包 success 外壳;
v2.2/v2.3 沿袭了这个做法。老端点是 `c.JSON(status, gin.H{"success":true,"data":...})`。

**建议**:本期不修(改动面广,且当前裸 fetch 方案能工作)。v2.0 发布前统一一次
响应规范(全部走 `{success, data, error}` 或全部裸对象),写进 API 规范文档。
记录为 P2,留 v2.0 发布阶段处理。

### 无 P0 / P1 问题

API 层冒烟未发现阻塞或功能性缺陷。v2.1/v2.2/v2.3 后端核心逻辑(鉴权/绑定/身份统一)
全部按 PRD 预期工作。
