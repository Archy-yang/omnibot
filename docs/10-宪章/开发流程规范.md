# 开发流程规范

本文档定义本项目所有开发人员必须遵守的流程规范。

---

## 一、核心开发流程

### 1. 修改前必须先出方案

任何代码改动之前，先输出修改方案说明：
- 改动背景和原因
- 涉及的文件列表
- 具体的修改思路
- 可能的影响范围

等待用户确认后再实施。

### 2. 复杂任务拆解

对于复杂功能，必须拆解为多个子任务：
- 使用 TaskCreate / TaskUpdate 进行任务追踪
- 每个子任务独立实现、测试、提交
- 完成一个子任务后再进行下一个

### 3. 最小改动原则

以最小改动完成当前目标：
- 不私自进行额外的重构或优化
- 不在功能开发中混入无关的代码清理
- 重构需求单独提出来，单独作为任务处理

### 4. 文档同步更新

**严格按顺序执行文档更新：
- **测试计划文档**：在写测试代码之前更新（TDD 流程要求）
- **PRD 文档**：开发前确认需求是否已在 PRD 中定义
- **架构文档**：代码修改完成后更新，保证文档描述与代码实现一致
- **CHANGELOG**：版本发布前更新版本变更记录

## 二、TDD 测试驱动开发流程

```
1. 编写/更新测试计划文档 → docs/50-测试/test-plans/...
       ↓
2. 编写测试代码 → 运行测试 → 确认测试失败（RED）
       ↓
3. 编写最小实现代码 → 运行测试 → 确认测试通过（GREEN）
       ↓
4. 必要的重构（不改变功能行为）→ 测试仍然通过（REFACTOR）
       ↓
5. 更新架构文档 → docs/30-服务架构/...
       ↓
6. 提交代码
```

### 测试分层规范

#### 1. 单元测试
- 测试单个函数/方法的行为
- 使用 mock 隔离外部依赖
- 文件名：`*_test.go`，与被测文件同目录

#### 2. 集成测试
- 测试多个组件配合
- 使用真实的数据库连接（SQLite in-memory）
- 测试完整的业务流程

#### 3. 端到端测试
- 启动完整的 HTTP 服务器
- 通过 `net/http/httptest` 发送真实请求
- 不使用 mock handler，走完整的路由链

### Go 测试特定约束
- **HTTP 接口测试**：启动测试 HTTP 服务器，通过 `net/http/httptest` 配合真实路由进行模拟访问，不使用 mock 处理器
- **数据库测试**：使用 SQLite in-memory 替代 MySQL/PostgreSQL，避免外部依赖
- **Redis 测试**：使用 `miniredis` 替代真实 Redis，内存式测试
- **测试命名**：`Test<Module>_<Function>_<Scenario>`，例如：`TestLLMConfigService_SetAPIKey_InvalidFormat`

## 三、PR 与发布流程

### PR 提交要求
- 每个 PR 只做一件事
- PR 描述必须包含：背景、改动内容、测试结果
- 所有测试必须通过
- 相关文档必须同步更新

### 发布流程
1. 更新 CHANGELOG.md
2. 更新版本号相关文档
3. 打 Git Tag
4. 发布 Release Notes

## 四、服务生命周期：只用 make（铁律）

上承 [CLAUDE.md 第五节](../../CLAUDE.md) 的同名规则，两处必须一致。

### 4.1 唯一入口

| 场景 | 唯一正确命令 |
|------|--------------|
| 本地进程：构建并启动 | `make` |
| 本地进程：只重启 | `make restart` |
| 本地进程：停止 | `make stop` |
| Docker：重建并重启 | `make docker-restart` |
| Docker：构建并启动（幂等） | `make docker-up` |
| Docker：停止 | `make docker-down` |
| 验收 | `make status` / `make docker-status` |

### 4.2 明确禁止

即使"效果完全一样"也不允许：
`docker build`、`docker compose up/down/restart`、`kill`、`pkill`、`nohup`、`go run`、
`./bin/server` 直接拉起或停止服务。

理由不是"命令丑"，而是：Makefile 里封装了构建顺序（前端先于后端，`go:embed` 才不会嵌入旧前端）、
幂等停机、PID 管理、启动健康检查。绕过 make 就等于跳过这些，还会让复现依赖"某人当时敲了哪些参数"。

### 4.3 make 失败时怎么办（最容易出错的环节）

1. **先读错误**，区分「代码/配置问题」与「环境限制」（端口占用、沙箱或权限、缓存目录不可写、
   缺少生成配置文件如 `configs/config.docker.yaml`）；
2. 环境限制 → 就地修通前置条件（释放端口、生成配置），或**为这一条 make 命令申请所需权限**，
   然后**重跑同一条 make**；
3. **禁止**把 make 拆成一串底层命令"等价"执行；
4. 确实修不通 → 停下来讲清卡点并问用户，**不许自行绕过**。

### 4.4 动手前自检

我要敲的这条起停命令，在 Makefile 里有没有对应目标？
有就必须用目标名；没有就先加目标（并在回复里说明加了什么）。
