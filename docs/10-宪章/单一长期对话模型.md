# 单一长期对话模型

本文档是 OmniBot 的产品基线决策，定义了「对话」这个核心概念在我们产品中的形态。
后续所有功能、架构、UI 设计都必须遵循本决策。

> **修订记录 v1.1（2026-09-25）**：引入 Conversation/Turn **持久化锚点**。
> 16-架构迭代路线图 Phase 1 起，持久层新增 `conversations` / `conversation_turns` 表，
> `messages` 增加 `conversation_id` / `turn_id` 字段。这是**内部实现锚点**（上下文压缩、
> 历史召回、任务回挂以 Turn 为粒度），**不是会话概念**：`(user_id, agent_id)` 全局只有
> 一个 active 对话（`EnsureActiveConversation` 保证），不可新建/切换/删除，产品体验与
> 本决策 v1.0 完全一致。见 §三.1 修订。

---

## 一、决策

**每个用户在 OmniBot 中只有一个永久存在的对话，不可新建、不可切换、不可删除。**

这条对话跨所有入口（微信、Web、飞书/钉钉、API）共享，是该用户和 OmniBot 之间所有
交互的唯一载体。**对话即关系，对话即记忆。**

类比：用户在微信里和「OmniBot」这个好友有且只有一个聊天窗口，永远停在那里。

---

## 二、为什么这样定

### 1. 直接源自产品愿景

`product-vision-v2.0.md` 第 7 行定义本产品是「**自带记忆的全平台智能助手**，永久
记住用户的偏好、历史和上下文」。

愿景里**没有「会话」「Session」「新建对话」**这些词——这不是疏漏，是定位本身就
不需要这层抽象。

### 2. 「记忆优先」原则的极致表达

愿景设计原则第一条：「**记忆优先**：任何功能如果和记忆冲突，优先保证记忆的正确性」。

多会话模型和「记忆」是天然冲突的——每开一个新会话，上下文就从零开始。市面上的
多会话产品（ChatGPT 等）都是后来打补丁加 Memory 功能。我们从零开始，可以**直接
让对话本身就是记忆的容器**。

### 3. 划清和 ChatGPT 的界线

愿景第 10 行：「不是又一个 ChatGPT 客户端」。

ChatGPT 的左侧无限会话列表是它的核心交互，但本质是早期上下文窗口太小的工程妥协，
不是产品最优解。我们的差异化恰恰是**取消这层抽象**。

### 4. 跨入口体验只在单一对话下成立

路线图 v3.0 里 v1.7（Web 记忆管理）、v1.9（跨通道记忆打通）、v1.10（统一配置中心）
都默认「同一用户在所有入口共享一份连续上下文」。多会话模型会让这些版本无法实现，
因为没法回答「跨通道记忆打通到哪个会话」「统一配置对哪些会话生效」这些问题。

## 三、设计含义

本决策落到具体设计上的硬约束：

### 1. 数据模型层面（v1.1 修订）

- **产品层不变**：每个用户只有一条对话，上下文构建以 `user_id` 为唯一维度
- **持久层锚点（v1.1）**：`conversations`（`(user_id, agent_id)` 唯一 active）与
  `conversation_turns` 作为**内部实现锚点**，`messages.conversation_id` / `messages.turn_id`
  关联归属——它们服务上下文压缩（Compact 水位）、历史召回（turn 粒度 chunk）、任务汇报
  回挂原始意图，**不构成可操作的会话**（无新建/切换/删除/列表）
- **禁止的是"会话语义"而非"conversation 字段"**：任何把 Conversation/Turn 暴露为
  用户可操作会话（新建/切换/分组）的改动，都违反本决策，需回到 §七 流程
- `memories` 表只按 `user_id` 索引（不变）

### 2. 入口层面

- 每个入口（微信/Web/飞书/API）的「身份」最终都映射到同一个 `user_id`
- 该 `user_id` 下所有消息属于同一条对话，无论从哪个入口产生

### 3. UI 层面

- **不提供「新建对话」按钮**
- **不提供会话列表/会话切换**
- 用户进入 Web 端就直接看到与 OmniBot 的对话界面，类似打开一个微信好友
- 命名上：现有前端代码中的 `sessionId` 实际是「用户标识」，命名误导，后续应渐进
  改名为 `userIdentifier` 或类似名称（但不是阻塞性重构）

### 4. 功能层面

- **对话清空 ≠ 新建对话**：用户可以选择「清空对话历史」（功能可选），但清空后
  仍是同一条对话，只是历史被清掉
- **长期记忆和对话历史是两套数据**：清空对话历史不会清空长期记忆，反之亦然
- 长期对话长度增长后的上下文构建（最近 N 轮 + 向量召回历史片段）属于实现细节
  演进，不影响本决策

## 四、必然带来的衍生价值

### 1. 风格沉淀（强烈推荐做）

单一长期对话天然是用户回答偏好的稳定信号源——回答长度、语气、格式偏好、emoji
使用习惯等都可以从历史中稳定提炼。这是多会话模型做不到的差异化能力。

后续可考虑在 `users` 或独立 `user_style_profile` 表中沉淀这类「风格记忆」，作为
事实型长期记忆之外的第二类记忆。

### 2. 关系感

对话越长，OmniBot 越懂用户。这种「关系沉淀」是用户留存的护城河，类似 Replika、
Character.AI 的核心体验，但聚焦点是「助手」而不是「角色扮演」。

---

## 五、需要警惕的问题

### 1. 长期对话的性能与成本

一个用户使用一年后，`messages` 表中可能有数万条记录。需要演进的方向：

- 上下文构建从「最近 10 轮」进化为「最近 N 轮 + 向量召回相关历史片段」→ 已由《[12-记忆系统技术方案](../30-服务架构/01-高层设计/12-记忆系统技术方案.md)》承接（三层记忆 + search_history 语义召回）
- 历史搜索能力（当前 Agent 已预埋 `search_history` 工具，待实现）→ 12 方案 M1 落地
- DB 索引和分页查询优化

这些是渐进演进项，不是阻塞项。

### 2. 不要被「类似 ChatGPT」的需求拉偏

后续可能有用户/团队成员提出「能不能加一个分会话」「能不能像 ChatGPT 那样有
project」之类的需求。**默认拒绝**，需要先讨论是否要修改本文档。任何带「会话」
「分组」「主题」概念的功能改动都必须先回到这里。

如果确实需要某种分组能力（例如长期使用后想分类查看历史），优先考虑「**单一对话
内的标签/检索**」而不是「**拆成多条对话**」——单一对话模型的根基不能动。

## 七、决策修改流程

本决策属于产品基线，修改门槛**等同于产品愿景**：

1. 必须先讨论清楚为什么要修改、对其他版本规划的影响
2. 修改后必须同步更新 `product-vision-v2.0.md` 和路线图
3. 已发布版本不得引入「新建会话」类破坏性变更（违反愿景的「渐进式增强」原则）
