# 代码风格规范

本文档定义本项目 Go 代码的风格、命名约定和最佳实践。

---

## 一、命名规范

### 包命名
- 全小写，不使用下划线或驼峰
- 简短但有意义，避免过于泛化的名字（如 util, common）
- 包名和目录名保持一致

### 文件名
- 全小写，使用下划线分隔单词
- 测试文件以 `_test.go` 结尾

### 变量命名
- 局部变量：驼峰命名，小驼峰
- 公开变量：大驼峰
- 常量：大驼峰
- 缩写保持一致：HTTP 而非 Http，URL 而非 Url

### 结构体命名
- 使用名词或名词短语
- 避免使用 Manager、Manager 等后缀
- 领域实体直接使用名词：User、Message、LLMConfig

### 函数命名
- 动词或动词短语
- 公开函数：大驼峰
- 私有函数：小驼峰
- 获取函数名清晰表达行为：Create、GetByID、Update、Delete

---

## 二、代码组织

### 导入分组
导入分为三组，空行分隔：
1. 标准库包
2. 第三方包
3. 内部包

```go
import (
    "fmt"
    "time"

    "github.com/gin-gonic/gin"
    "go.uber.org/zap"

    "wechat-bot/internal/domain/user"
    "wechat-bot/internal/service"
)
```

### 函数长度
- 单个函数不超过 50 行
- 超过的必须拆分

### 文件长度
- 单个文件不超过 500 行
- 超过的必须拆分

---

## 三、错误处理

- 永远不要忽略错误，除非明确不需要处理
- 错误信息不需要大写开头
- 错误信息不需要句号结尾
- 使用 fmt.Errorf 包装错误时，使用 ": %w" 保留原始错误
- 业务错误必须定义成 sentinel error 类型

---

## 四、注释规范

- 包注释：每个包都应该有包注释
- 公开函数必须有注释
- 注释应该解释为什么，而不是做什么
- 避免无意义的注释

---

## 五、架构分层规范

本项目采用 DDD（领域驱动设计）分层架构：

```
┌─────────────────────────────────────────┐
│         API 层 (internal/api/)          │
│  Handler / Controller / Router          │
│  负责：请求解析、参数校验、响应格式化      │
└────────────────────┬────────────────────┘
                     │
┌────────────────────▼────────────────────┐
│       Service 层 (internal/service/)    │
│  Business Logic / Use Case              │
│  负责：业务逻辑编排、事务边界、权限校验    │
└────────────────────┬────────────────────┘
                     │
┌────────────────────▼────────────────────┐
│    Repository 层 (internal/repository/) │
│  Data Access Object                      │
│  负责：数据读写、查询构建、数据库操作      │
└────────────────────┬────────────────────┘
                     │
┌────────────────────▼────────────────────┐
│      Domain 层 (internal/domain/)       │
│  Entity / Value Object / Domain Service │
│  负责：领域模型定义、核心业务规则          │
└────────────────────┬────────────────────┘
                     │
┌────────────────────▼────────────────────┐
│    Infrastructure 层 (internal/db/)     │
│  Database / External Client             │
│  负责：数据库连接、外部服务客户端          │
└─────────────────────────────────────────┘
```

### 分层依赖规则
- API 层只能依赖 Service 层，不能直接依赖 Repository 或 DB
- Service 层只能依赖 Repository 层和 Domain 层
- Repository 层只能依赖 Domain 层和 DB 层
- Domain 层不依赖任何其他层（纯 Go struct + 方法）
- **所有跨层调用必须通过接口，不能直接依赖具体实现**

### 新增模块标准流程
1. 在 `internal/domain/<module>/` 定义领域实体和接口
2. 在 `internal/repository/<module>/` 实现 Repository
3. 在 `internal/service/<module>/` 实现 Service 逻辑
4. 在 `internal/api/<module>/` 实现 Handler 和路由
5. 配套的测试和文档同步更新

## 六、数据库设计规范

### 表命名规范
- 全小写，下划线分隔
- 复数形式：`users`, `wechat_accounts`, `user_llm_configs`
- 关联表：`<table1>_<table2>_rels`

### 必备字段
所有表必须包含：
```go
ID        int64     `gorm:"primaryKey;autoIncrement"`
CreatedAt time.Time `gorm:"not null"`
UpdatedAt time.Time `gorm:"not null"`
```

### AutoMigration 规范
- 所有表结构变更必须通过 GORM AutoMigration 实现
- 在 `internal/db/database.go` 的 `autoMigrate()` 函数中注册
- 新增表必须同时更新 `docs/30-服务架构/00-系统设计总览.md` 的数据存储章节
- 破坏性变更（删表、删字段、改类型）必须单独提方案评审

### 索引规范
- 外键字段必须建索引：`user_id`
- 唯一业务字段必须建唯一索引：`open_id`, `union_id`
- 查询条件字段必须建普通索引
- 复合索引顺序按区分度从高到低排列
