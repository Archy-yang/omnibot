## Context

当前项目已实现一个基于 Go + Gin 的微信公众号智能对话客服系统。系统架构采用分层设计：

```
┌─────────────────────────────────────────────────────┐
│                    cmd/server                        │
│              应用入口与初始化                        │
├─────────────────────────────────────────────────────┤
│              internal/api                           │
│  ├─ wechat/handler     微信回调处理                 │
│  ├─ admin/handler      管理端 API                   │
│  └─ routes             路由注册                     │
├─────────────────────────────────────────────────────┤
│            internal/client/llm                      │
│  ├─ types.go          统一接口定义                  │
│  ├─ factory.go        客户端工厂与自动降级          │
│  ├─ qwen.go           通义千问实现                  │
│  └─ doubao.go         字节豆包实现                  │
├─────────────────────────────────────────────────────┤
│                pkg/                                  │
│  ├─ config            Viper 配置管理                │
│  └─ logger            Zap 结构化日志                │
└─────────────────────────────────────────────────────┘
```

**当前状态**：
- 微信回调接口：完整实现（验证、接收消息、响应）
- 大模型客户端：支持通义千问、字节豆包双厂商，自动降级
- 管理 API：健康检查、指标、配置管理
- 基础设施：配置、日志、中间件已完善

## Goals / Non-Goals

**Goals:**
- 从现有代码反向生成准确的规范文档
- 确保规范文档与代码实现 1:1 对应
- 为后续功能开发提供可追溯的契约
- 覆盖 API 端点、数据结构、业务流程、验收标准

**Non-Goals:**
- 不修改任何业务代码
- 不新增功能或修复 bug
- 不重构现有架构
- 不创建新的测试用例

## Decisions

### 1. 文档组织方式
**决策**：按能力域（capability）组织规范文档，每个能力域一个独立目录

**理由**：
- 与代码模块边界对齐，便于定位和维护
- 每个能力域独立演进，互不干扰
- 符合 openspec 规范驱动开发的最佳实践

**备选方案**：按文件层级组织 → 否决，跨文件能力难以聚合

### 2. 反向工程方法
**决策**：先阅读代码 → 提取 API 签名 → 推导业务规则 → 编写验收标准

**理由**：
- 确保规范准确反映实际实现
- 避免"文档说一套，代码做一套"的偏差
- 基于真实代码路径推导边界条件

### 3. 规范粒度
**决策**：每个能力域规范包含：接口定义、数据结构、业务流程、验收示例

**理由**：
- 完整的规范需要覆盖从"是什么"到"怎么验证"的全链路
- 验收示例采用 BDD 风格，可直接转化为测试用例

## Risks / Trade-offs

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 代码与规范不一致 | 后续开发误解契约 | 建立文档更新检查清单，每次代码变更同步更新 |
| 过度规范化抑制创新 | 灵活度降低 | 规范仅定义外部契约，不限制内部实现细节 |
| 反向工程遗漏边界条件 | 规范不完整 | 重点关注错误处理路径和边缘情况 |
