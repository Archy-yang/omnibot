## Context

**当前状态：**
- 微信回调接口已实现，但所有消息返回固定文本"客服在开发中，敬请期待"
- 大模型客户端 `internal/client/llm` 已开发完成，支持通义千问 + 字节豆包双厂商自动降级
- 处理器创建方式：`wechat.NewHandler(wechat.Config{...})`
- 路由创建方式：`routes.SetupRouter(cfg *config.Config)` 内部创建处理器

**约束条件：**
- 必须保持对所有消息类型的向后兼容（文本、图片、语音、视频、位置、链接、事件）
- 大模型调用超时已由 llm.Client 层处理，无需重复实现
- 必须记录大模型调用日志（成功/失败、耗时、厂商等）

**相关代码：**
- `internal/api/wechat/handler.go`: 微信消息处理器
- `internal/api/routes.go`: 路由注册与依赖注入
- `internal/client/llm/factory.go`: 大模型客户端工厂

## Goals / Non-Goals

**Goals:**
- 微信处理器正确注入 llm.Client 依赖
- 用户发送任意支持的消息类型都能获得大模型生成的智能回复
- 大模型调用失败时优雅降级，返回友好提示
- 保持与现有微信接口的完全兼容
- 单元测试覆盖所有主要场景

**Non-Goals:**
- 不实现多轮对话上下文记忆（后续迭代）
- 不实现回复长度截断（后续优化）
- 不支持大模型视觉识别（图片消息只提示类型）
- 不实现语音转文字（语音消息只提示类型）
- 不将系统提示词移至配置文件（当前硬编码）

## Decisions

### 1. 依赖注入方式
**决策：** 修改 `wechat.NewHandler` 签名，增加 `*llm.Client` 参数

**理由：**
- 构造函数注入是最清晰的依赖注入方式
- 依赖关系在编译期检查，避免运行时 nil pointer
- 方便单元测试时注入 mock 客户端

**备选方案：** 使用 Setter 方法注入 → 否决，可能出现未初始化状态

### 2. 消息处理流程
**决策：** 在 dispatchMessage 之后、返回 XML 之前调用大模型

**理由：**
- 现有消息分发逻辑保持不变，各类型消息正常解析
- 在统一位置调用大模型，避免代码重复
- 便于集中处理大模型调用失败的降级逻辑

### 3. 消息类型到 Prompt 的映射
**决策：** 为每种消息类型构造不同的 user role 内容

| 消息类型 | Prompt 内容 |
|----------|-------------|
| 文本消息 | 直接使用用户输入的文本 |
| 图片消息 | "用户发送了一张图片" |
| 语音消息 | "用户发送了一条语音消息" |
| 视频/小视频 | "用户发送了一条视频消息" |
| 位置消息 | "用户发送了位置信息" |
| 链接消息 | "用户发送了一个链接" |
| 订阅事件 | "用户刚刚关注了公众号，请生成友好的欢迎语" |
| 取消订阅/VIEW | 不回复 |

**理由：** 大模型可以根据消息类型生成合适的回复，无需在微信层处理复杂逻辑

### 4. 系统提示词
**决策：** 硬编码系统提示词

**内容：** "你是一个友好的智能客服助手，请用简洁的中文回应用户的问题。"

**理由：** 当前阶段快速上线优先，后续迭代可迁移至配置文件

## Risks / Trade-offs

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 大模型调用超时导致微信服务器重试 | 重复调用大模型，浪费 token | 依赖 llm.Client 的超时配置（默认较短），后续考虑幂等设计 |
| 大模型返回内容过长导致微信截断 | 用户体验下降 | 后续迭代添加截断逻辑（当前记录警告日志） |
| 错误处理不当导致 panic | 服务不可用 | 保持现有 defer-recover 中间件，单元测试覆盖错误路径 |
| Mock 客户端设计复杂影响测试 | 单元测试难以维护 | 使用接口抽象，简单 mock 实现 ChatCompletion 方法 |

## Migration Plan

**部署步骤：**
1. 部署新代码，无需数据库变更
2. 确保配置文件中 LLM 相关配置正确（API Key、默认厂商、降级顺序）
3. 启动服务，观察日志确认大模型调用正常

**回滚策略：**
- 出现问题时直接回滚至上一版本，大模型集成是纯增量功能，无数据依赖
