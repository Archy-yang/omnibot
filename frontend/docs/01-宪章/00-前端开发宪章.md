# OmniBot 前端开发宪章

⚠️ **极其重要：所有前端开发人员（包括 AI）必须严格遵守本宪章的所有规定。**

---

## 一、核心价值观

### 1.1 用户体验优先
- **性能**：页面加载 < 1s，消息发送无感知延迟
- **简洁**：界面只保留必要元素，避免视觉噪音
- **流畅**：动效克制、自然，不干扰用户
- **可访问**：支持键盘操作，支持屏幕阅读器

### 1.2 代码质量优先
- **类型安全**：全程 TypeScript，禁止 `any`
- **可维护**：清晰的架构，统一的规范，完善的注释
- **可测试**：组件职责单一，易于单元测试
- **渐进式**：小步迭代，每个阶段都可交付、可回滚

### 1.3 技术克制
- **不追新**：技术选型以稳定、生态成熟为首要标准
- **不过度设计**：够用就好，避免为了"优雅"而增加复杂度
- **少依赖**：能自己实现的就不引入第三方库
- **重原生**：优先使用浏览器原生 API

## 二、架构约束

### 2.1 分层约束

```
┌─────────────────────────────────┐
│           View (页面)            │  只负责渲染，不包含业务逻辑
├─────────────────────────────────┤
│       Components (组件)          │  通用 UI 组件
├─────────────────────────────────┤
│      Composables (组合式)        │  可复用逻辑封装
├─────────────────────────────────┤
│        Stores (状态管理)         │  全局状态管理
├─────────────────────────────────┤
│       Services (服务层)          │  API 调用、业务逻辑
├─────────────────────────────────┤
│       Types (类型定义)           │  TypeScript 类型
├─────────────────────────────────┤
│       Utils (工具函数)           │  纯函数工具
└─────────────────────────────────┘
```

**依赖方向只能由上往下，禁止反向依赖：**
- ✅ View → Components → Composables → Stores → Services
- ❌ Services 不能依赖 Stores
- ❌ Stores 不能依赖 Components
- ✅ 同层之间可以互相依赖（如 Composables 之间）

### 2.2 组件约束

| 组件类型 | 允许依赖 | 禁止依赖 |
|---------|---------|---------|
| 基础组件 (Base*) | 只有 props | 任何 Store、任何 Service |
| 业务组件 (Chat*) | Composables、Props | 直接调用 axios、直接操作 localStorage |
| 页面组件 (*Page) | Stores、Services | 直接写 API 调用逻辑 |

### 2.3 状态管理约束

**什么状态应该放在 Store：**
- ✅ 跨组件共享的状态（用户信息、配置）
- ✅ 需要持久化的状态（聊天历史、设置）
- ✅ 复杂的状态变更逻辑

**什么状态不应该放在 Store：**
- ❌ 组件内部的临时状态（loading、input value）
- ❌ 只有一个组件使用的状态
- ❌ 不需要持久化的 UI 状态

## 三、开发流程约束

### 3.1 提交前检查清单

每次提交代码前必须完成以下检查：

- [ ] `npm run type-check` 无类型错误
- [ ] `npm run lint` 无 ESLint 错误
- [ ] `npm run build` 构建成功
- [ ] 核心功能自测通过
- [ ] 代码不包含 `console.log`、`debugger` 等调试代码
- [ ] 不包含 `any` 类型（必要时需加注释说明原因）

### 3.2 Git 提交规范

严格遵守 [Git 提交规范](./03-Git提交规范.md)：

- feat: 新功能
- fix: 修复 bug
- docs: 文档更新
- style: 代码格式
- refactor: 重构
- perf: 性能优化
- test: 测试相关
- chore: 构建/工具变动

### 3.3 Code Review 标准

CR 必须检查以下内容：

1. **类型安全**：是否有 `any`、类型是否正确
2. **架构合规**：是否违反分层约束
3. **性能影响**：是否有明显的性能问题
4. **可维护性**：命名是否清晰、注释是否充分
5. **测试覆盖**：核心逻辑是否有测试覆盖

## 四、技术栈约束

### 4.1 核心技术栈（锁定，不允许随意更换）

| 技术 | 版本要求 | 说明 |
|------|---------|------|
| Vue | ^3.4+ | Composition API，禁止 Options API |
| TypeScript | ^5.0+ | 严格模式，`strict: true` |
| Vite | ^5.0+ | 构建工具 |
| Pinia | ^2.1+ | 状态管理，禁止 Vuex |
| Vue Router | ^4.0+ | 路由 |
| Tailwind CSS | ^3.4+ | 样式方案，禁止 CSS-in-JS |
| Naive UI | ^2.38+ | UI 组件库 |
| Axios | ^1.6+ | HTTP 客户端 |

### 4.2 第三方库引入约束

引入新的第三方库必须满足以下全部条件：

1. ✅ Star 数 > 5000，社区活跃
2. ✅ 最近 3 个月有更新，无人维护的库不引入
3. ✅ 体积 < 50KB（gzip 后）
4. ✅ 有完善的 TypeScript 类型定义
5. ✅ 经过技术选型讨论，至少 2 人同意

**禁止引入的库：**
- ❌ Lodash（用 ES6+ 原生 API 或自定义工具函数）
- ❌ Moment.js（用 date-fns 或原生 Date API）
- ❌ jQuery（用原生 DOM API）
- ❌ 任何 CSS-in-JS 方案

## 五、性能红线

### 5.1 性能指标

| 指标 | 红线标准 |
|------|---------|
| 首屏加载时间 | < 1s |
| JS 打包体积 | < 200KB (gzip) |
| CSS 打包体积 | < 30KB (gzip) |
| Lighthouse 性能分 | > 90 |
| 消息列表滚动帧率 | > 50 FPS |

### 5.2 性能约束

- ✅ 长列表必须使用虚拟滚动（> 100 条消息）
- ✅ 大组件必须使用 `defineAsyncComponent` 懒加载
- ✅ 图片必须懒加载，必须有 width/height
- ✅ 禁止在 `onMounted` 中做重计算
- ✅ 复杂计算必须用 `computed` 缓存
- ❌ 禁止在 `v-for` 中使用复杂函数
- ❌ 禁止频繁的强制重渲染

---

## 六、安全红线

### 6.1 XSS 防护

- ✅ 用户输入的内容必须经过 sanitize
- ✅ `v-html` 只能用在经过 sanitize 的内容上
- ✅ Markdown 渲染必须开启 XSS 防护
- ❌ 禁止直接 `eval` 用户输入
- ❌ 禁止直接拼接 HTML 字符串

### 6.2 数据安全

- ✅ 敏感信息（API Key）必须加密存储
- ✅ 不能在 localStorage 中存储明文密钥
- ✅ 不能在前端日志中打印敏感信息
- ❌ 禁止把敏感信息暴露在 URL 中

### 6.3 其他安全约束

- ✅ 所有用户输入必须做长度校验
- ✅ 特殊字符必须转义
- ✅ CSP 策略必须开启
- ❌ 禁止使用 `innerHTML`，除非万不得已且经过 sanitize

---

## 七、可访问性约束

- ✅ 所有按钮、输入框必须可以通过 Tab 聚焦
- ✅ 所有图片必须有 `alt` 属性
- ✅ 颜色对比度必须符合 WCAG AA 标准
- ✅ 支持键盘快捷键（Enter 发送、Ctrl + Enter 换行等）
- ✅ 动画可以被关闭

## 九、违反宪章的处理

1. **轻度违反**（如命名不规范、缺少注释）：CR 打回修改
2. **中度违反**（如类型错误、分层违规）：打回重构，计入代码质量统计
3. **重度违反**（如引入未授权的库、安全漏洞）：直接 Revert，讨论后重新提交
